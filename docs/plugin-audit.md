# Plugin and extension packaging audit

Baseline audited 2026-09-24 against repository commit `d50803a` and the linked first-party documentation. The platform and repository-contract sections below describe that baseline; the implementation status records the subsequent [plugin implementation](https://github.com/ajnart/selfhost-skills/pull/6), [audit update](https://github.com/ajnart/selfhost-skills/pull/7), [private Git marketplace fix](https://github.com/ajnart/selfhost-skills/pull/8), and `v1.0.0` release. The repository ships one public Agent Skill, `self-host`; the other `selfhost-*` names are internal workflow IDs and `GUIDE.md` files.

## Executive finding

The existing skill can already be installed into Claude Code, Codex, Pi, and OpenCode through the Skills CLI. The generated release ZIP is a portable [Agent Plugins 1.0](https://agent-plugins.org/specification) package with root `plugin.json`, `skills/self-host/SKILL.md`, and a Claude compatibility manifest. That does **not** by itself establish a native marketplace/install path for each client. Each client uses its own distribution and discovery contract; OpenCode's executable plugins are a different feature from its Agent Skills. Preserve one canonical skill tree and generate any client-specific wrapper from it.

| Target | Baseline direct skill route | Native plugin/package route | Baseline gap |
| --- | --- | --- | --- |
| Claude Code | Skills CLI into `.claude/skills` | Claude plugin directory and marketplace | Release has plugin metadata; marketplace and native install proof pending |
| Codex | Skills CLI into `.agents/skills` or `~/.codex/skills` | Portable plugin and Codex marketplace | Portable manifest exists; marketplace-addressable source and native install proof pending |
| Pi | Skills CLI into `.pi/skills` or `~/.pi/agent/skills` | Pi package containing skill assets | No Pi package descriptor or package install proof |
| OpenCode | Skills CLI into `.agents/skills` | JS/TS hook plugin via local file or npm | No executable hook is needed for the skill; npm plugin would be a separate product |

The templates are not installed manifests in the source checkout. ## Claude Code

Claude's native plugin root has `.claude-plugin/plugin.json` and root-level components such as `skills/<name>/SKILL.md`. Only the manifest belongs inside `.claude-plugin/`; skill scripts and references remain beside their `SKILL.md`. Plugin skills are namespaced, so the generated archive's plugin name `selfhost-skills` and skill name `self-host` imply `/selfhost-skills:self-host`. The direct Skills CLI installation still uses `/self-host`. The generated ZIP already has this layout. Its internal `GUIDE.md` files remain support material, not extra public skills. No separate Claude command, agent, hook, MCP server, or LSP server is required for the current skill. [Claude plugin guide](https://code.claude.com/docs/en/plugins), [plugin reference](https://code.claude.com/docs/en/plugins-reference), [Claude skills](https://code.claude.com/docs/en/skills)

Claude distributes plugins through **marketplaces**. An [archive marketplace source](https://code.claude.com/docs/en/plugin-marketplaces) can use the existing release ZIP: it points at an HTTPS ZIP URL and may pin `sha256`. The archive must have `.claude-plugin/` at its root or exactly one folder below; Claude rejects archives over 256 MiB. Archive sources require Claude Code 2.1.224+. The selected Git-relative source works with a private repository and has no public ZIP dependency. A marketplace needs `.claude-plugin/marketplace.json` with a public marketplace name, owner, and plugin entry. Users add it with `/plugin marketplace add <marketplace-source>` and install with `/plugin install selfhost-skills@<marketplace-name>`. User, project, local, and managed installation scopes have distinct sharing behavior. Self-hosted marketplace availability is separate from Anthropic community or curated marketplace inclusion. [Marketplace format, relative and archive sources, and scopes](https://code.claude.com/docs/en/plugin-marketplaces), [install flow](https://code.claude.com/docs/en/discover-plugins)

The source checkout has no `.claude-plugin/marketplace.json`, and its [validator](../scripts/lib/skillpack.ts) explicitly rejects one at the repo root under the current source contract. The release exporter puts the catalog and verified plugin tree together on `plugin-claude`. A direct GitHub plugin source aimed at editable `main` would fail because the root has no `.claude-plugin/plugin.json` or root `skills/` directory. [Claude marketplace sources](https://code.claude.com/docs/en/plugin-marketplaces)

**Selected private-capable route:** Claude also supports a Git marketplace whose entry uses the relative string source `"./plugins/selfhost-skills"`. The `plugin-claude` branch contains the same verified plugin tree generated for Codex, and users with repository access add that Git ref through an existing Git credential helper. A local relative source is not an object with `source: "directory"`; Claude 2.1.246 rejected that object shape in a disposable validator check. The public archive URL is not needed for Claude installation. Claude documents relative sources and private Git credential handling in [its marketplace source and private repository sections](https://code.claude.com/docs/en/plugin-marketplaces).

Claude uses plugin manifest `version` as the update signal. Keep it synchronized with the release version; avoid a second marketplace-entry version unless needed. Validate the generated plugin root and catalog with `claude plugin validate <path> --strict`, install from the Git marketplace in a disposable project, invoke the namespaced skill, and check its linked guide. Marketplace refresh/plugin update and `/reload-plugins` are separate from validation. Git marketplace plugins are cached copies, so editing source after installation is not a live update. [Claude versioning and validation](https://code.claude.com/docs/en/plugins-reference), [marketplace lifecycle](https://code.claude.com/docs/en/discover-plugins)

The selected Git marketplace entry is:

```json
{
  "name": "selfhost-skills",
  "source": "./plugins/selfhost-skills"
}
```

It belongs inside a marketplace file with `name`, `owner`, and `plugins` fields, and the plugin directory must be within that marketplace's Git root. [Claude marketplace schema and relative sources](https://code.claude.com/docs/en/plugin-marketplaces)

## Codex and OpenAI plugins

OpenAI's current plugin packaging accepts the portable root `plugin.json` plus fixed root `skills/` and optional `mcp.json`; **skills-only plugins can be submitted**. The repository's generated ZIP already follows this layout. The `.codex-plugin/plugin.json` produced by the bundled `plugin-creator` scaffold is a supported compatibility layout, not a requirement to replace this package's portable manifest. For a portable manifest, `skills` entries under a Codex overlay do not replace the fixed `skills/` discovery path. Bundled `scripts/`, `references/`, and assets are supported inside the skill. [Package your plugin](https://developers.openai.com/plugins/build/plugins), [build skills](https://developers.openai.com/plugins/build/skills), [submit plugins](https://developers.openai.com/plugins/deploy/submission)

OpenAI-specific listing metadata can be added under `extensions.com.openai.interface` in the root manifest: display name, short/long description, publisher, category, capabilities, URLs, starter prompts, and optional imagery. This is presentation metadata, not needed for the existing portable skill to load. `extensions.com.openai` replaces rather than merges with a `.codex-plugin/plugin.json` overlay. Do not add `apps`, hooks, or MCP files until there is a real integration to register; the current Homarr connection is configured per target stack at runtime and must not be bundled with credentials. [OpenAI manifest fields](https://developers.openai.com/plugins/build/plugins)

Codex's **marketplace** is a separate catalog: a repo catalog belongs at `.agents/plugins/marketplace.json`, with entries containing `name`, source, `policy.installation`, `policy.authentication`, and `category`. A local source path such as `./plugins/selfhost-skills` is relative to the marketplace root and must stay inside it. Git sources can point at a plugin at repo root (`url`) or a checked-in subdirectory (`git-subdir`). `codex plugin marketplace add/list/upgrade/remove` manages catalogs; local marketplace plugins are installed and tested in the ChatGPT desktop Plugins Directory. Marketplace-backed installs use cached plugin copies rather than the source path. [Marketplace format and CLI](https://developers.openai.com/plugins/build/plugins)

A disposable or separately published Codex marketplace could contain the generated plugin tree at `plugins/selfhost-skills/` and an entry like this; the current source checkout does not have that tree:

```json
{
  "name": "selfhost-skills",
  "source": { "source": "local", "path": "./plugins/selfhost-skills" },
  "policy": { "installation": "AVAILABLE", "authentication": "ON_INSTALL" },
  "category": "Productivity"
}
```

This is one entry inside `.agents/plugins/marketplace.json`. The marketplace's own top-level `name`, optional `interface.displayName`, and `plugins` array wrap it. A Git-backed entry would replace `source` with a supported `url` or `git-subdir` form. [OpenAI marketplace examples](https://developers.openai.com/plugins/build/plugins)

The current Git checkout cannot itself serve as a Codex plugin source: root `plugin.json` and root `skills/` exist only inside the generated ZIP, and the source validator explicitly rejects a committed repo marketplace. Codex's documented marketplace sources are local folders and Git; the docs do not describe a ZIP URL marketplace source. Consequently, the concrete native choices are: unpack the generated artifact into a local marketplace plugin folder for development; host the generated tree in a dedicated Git source or stable generated subdirectory for repo marketplace installs; or submit the generated skills-only package to OpenAI's public plugin review. The direct Skills CLI installation remains available independently. The absence of ZIP URL marketplace support is an inference from the documented source list, not a tested rejection. [Marketplace sources](https://developers.openai.com/plugins/build/plugins), [public submission](https://developers.openai.com/plugins/deploy/submission)

Public OpenAI submission is a separate review through the plugin portal. It supports skills-only packages; a workspace-published plugin has a narrower audience than the public directory shared by ChatGPT and Codex. Submission requires a verified publisher identity and appropriate organization permission. Do not describe a locally valid ZIP as an approved public listing. [Submission rules](https://developers.openai.com/plugins/deploy/submission)

## Pi

Pi distinguishes a **skill** (instructions and supporting files) from an **extension** (executable TypeScript/JavaScript code for tools, commands, event handlers, and UI). `self-host` is a skill. Pi advertises skill metadata first and loads the full file on demand; `/skill:self-host` forces it. An extension adds executable access to the host and session, so adding one solely to distribute the present skill has no functional benefit. [Pi skills](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md), [Pi extensions](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)

Pi's **package** is a distribution unit that may contain skills, extensions, prompts, and themes. It accepts npm, Git, and local-directory sources: `pi install npm:<package>`, `pi install git:github.com/ajnart/selfhost-skills@<tag>`, or `pi install ./directory`. A package exposes resources through conventional root directories such as `skills/` or explicit `package.json` `pi.skills` paths. Its current root has neither a top-level `skills/` nor a `pi` manifest, so a native Pi Git package install has no declared skill root. The portable ZIP has the conventional `skills/self-host/` directory after extraction, but ZIP is not one of the documented `pi install` source types. [Pi packages](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md)

The smallest source-repo change for Pi Git installs is to declare `"pi": {"skills": ["./.agents/skills"]}` in root `package.json`, then validate that Pi discovers exactly `self-host`. The leading-dot resource path needs an explicit declaration. Keep `private: true` if npm publication is not intended. A separate generated npm package would need its own `package.json` and `skills/self-host/` payload; `private: true` on the current root prevents publishing that root. The `pi-package` keyword makes an npm package eligible for the Pi gallery, but is not needed for Git installs. These are packaging proposals, not changes made by this audit. [Pi package manifest and gallery](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md)

Pi records personal packages in `~/.pi/agent/settings.json` and local project packages in `.pi/settings.json` with `--local`; project package declarations load only after project trust. `pi list`, `pi remove`, and `pi update --extensions` manage them. A versioned npm spec or Git tag/commit remains pinned when updated. Local directory packages load in place. Pi can also scan standalone skill directories, so the existing Skills CLI route remains independent of `pi install`. Test the native route in a disposable Pi home and project; check startup diagnostics, `/skill:self-host`, a bundled guide read, and behavior after source checkout removal for copied installs. [Pi package lifecycle](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md), [Pi skills](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md)

## OpenCode

OpenCode uses **plugins** for executable JavaScript/TypeScript host behavior and **skills** for on-demand Markdown instructions. The URL supplied for this audit, [the V1 plugin page](https://opencode.ai/docs/plugins/), documents local `.opencode/plugins/` files or npm packages in the singular `plugin` array, using `@opencode-ai/plugin`. Current [V2 plugin docs](https://opencode.ai/v2/docs/plugins) use the plural `plugins` array, `@opencode/plugin`, and `Plugin.define({ id, setup })`; `opencode plugin add/list/check/update/remove` manages package plugins. These APIs and config keys must not be mixed. Neither generation needs a hook plugin to load this repository's skill. [V2 plugin authoring](https://opencode.ai/v2/docs/build/plugins), [V1 migration](https://opencode.ai/v2/docs/build/plugins/migrate-v1)

Both V1 and V2 discover skills from project `.agents/skills/` and global `~/.agents/skills/`, as well as their OpenCode and Claude-compatible skill directories. Thus the canonical `.agents/skills/self-host/SKILL.md` is already an OpenCode skill when the source project is open; the Skills CLI can install its full directory elsewhere. OpenCode advertises skills by ID/description and loads the full instructions through its `skill` tool on demand. Supporting guides/scripts are resolved relative to the skill directory. V1 requires/recognizes specific frontmatter fields and has `permission.skill` controls; V2 derives the ID from the path and treats `name` as a display label, accepts portability metadata without interpreting it, and uses its own permissions model. The current `self-host` ID/description fit both. [V1 skills](https://opencode.ai/docs/skills/), [V2 skills](https://opencode.ai/v2/docs/skills)

An npm OpenCode plugin does **not** automatically register `SKILL.md` files bundled inside its npm package. This conclusion is supported by the separate documented plugin loader and skill discovery paths and [OpenCode's skill scanner](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/skill/index.ts); it is an inference about the current implementation, not a published guarantee against future plugin features. Creating a plugin that copies skill files into a discovered directory would add an executable install side effect without improving the existing direct skill route. Do not label the release ZIP an OpenCode npm plugin. [V2 plugins](https://opencode.ai/v2/docs/plugins), [V2 skills](https://opencode.ai/v2/docs/skills)

V2 also supports extra local skill directories and HTTP skill catalogs through `opencode.json(c)` `skills`. An HTTP catalog has `index.json` with skill names, versions, and file lists; changing files requires a version bump for cache refresh. That route would need a hosted catalog and careful transformation because V2 currently gives a root `SKILL.md` catalog entry the literal ID `SKILL`; a named Markdown entry is recommended for a stable `self-host` ID. It is an optional new distribution channel, not a prerequisite for the Skills CLI or `.agents/skills` installation. [V2 skill sources and catalogs](https://opencode.ai/v2/docs/skills)

For current distribution, install with Skills CLI or keep the canonical project skill path. Verify a fresh V1/V2 OpenCode session lists and loads `self-host`, then reads a bundled guide using only its installed path. Check skill permissions and duplicate skill IDs in the fixture. The repository package validator alone does not prove OpenCode runtime discovery.

## Cross-client packaging decision

Keep `.agents/skills/self-host/` as the only editable workflow. The release generator may project the same bytes into client-native package layouts; it should not introduce another maintained copy or make internal guides discoverable. Publish package-specific artifacts only after their own validator and a disposable install/activation check pass. Where native marketplaces require registration or review, distinguish a locally installable artifact from a published listing.

### Distribution and trust boundaries

Plugins and packages can carry executable code, and `self-host` includes scripts that operate on a user-selected host. Distribution must retain the skill's approval gates and avoid shipping target-specific API keys, passwords, `.sessions/`, `.env*`, browser profiles, or generated project state. A static MCP declaration would be a new product boundary: the current Homarr bridge is configured per installation with its own authentication and permissions. Public listings should describe the skill's actual managed/guided/discovery support levels rather than imply that every catalog app is automatically deployed.

## Full delivery plan: installed and working in all four clients

This is the implementation and maintenance sequence. It uses **one canonical `main` source branch plus two generated distribution refs** in the existing repository: `plugin-claude` and `plugin-codex`. ### Definition of done and scope of “working”

| Level | Required evidence | Claim allowed |
| --- | --- | --- |
| A. Package | One `self-host` entry, complete bundled files, valid manifests/catalogs, reproducible archive and matching SHA-256 | The release artifact is structurally valid |
| B. Client | Fresh install through each route below, visible skill, successful invocation, bundled guide/helper resolution after source checkout is unavailable, update and removal checks | The skill is installed and usable in that client |
| C. Self-host workflow | A separate approved host/project run reaches the selected workflow's verification criteria, including real UI/API checks where applicable | That selected stack works on that host |

Level B is the target for four-provider packaging. Level C is not established by any plugin installer: the skill asks for a target host, creates a plan, obtains approval, applies only the approved Compose project, and verifies the chosen services. If a new catalog commit fails client smoke, revert the affected **generated branch commit** and retain both immutable source releases; do not mutate a published ZIP under the same version. This ordering is necessary because Claude caches explicit plugin versions, Codex loads marketplace snapshots/cached plugins, and Pi pins Git refs. [Claude version management](https://code.claude.com/docs/en/plugins-reference), [Codex marketplace upgrade](https://developers.openai.com/plugins/build/plugins), [Pi pinned refs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md)
2. On upgrade, repeat the one-skill/no-duplicate check and one read-only plan smoke per client. Verify the new installed path before retiring old direct Skills CLI entries or old native packages. The `.selfhost` project record, private handoff, Compose data, and user services are outside plugin cache ownership and must not be removed by plugin uninstall. The repository's migration rule is in [`.agents/install.md`](../.agents/install.md); client removal/update surfaces are documented by [Claude](https://code.claude.com/docs/en/discover-plugins), [Pi](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md), and [Skills CLI](https://github.com/vercel-labs/skills#readme).
3. Maintain an acceptance ledger per version: source tag/commit, archive digest, distribution commit, Claude CLI version, Codex app/CLI version, Pi version, OpenCode V1/V2 version, exact scope and invocation, each proof level, and outstanding blockers. This is local release evidence, not a reason to embed telemetry, secrets, or project state in a plugin. Source/package provenance follows [Agent Plugins 1.0](https://agent-plugins.org/specification); publishing and caching behavior follows each client page cited above.

### Final completion checklist

- [x] Source version and changelog agree; only `.agents/skills/self-host/SKILL.md` is public.
- [x] Pi `package.json` declares `.agents/skills` and a pinned Git install loads `self-host`.
- [x] Generated ZIP, release manifest, and SHA-256 match a durable GitHub Release asset.
- [x] Both generated refs contain byte-matched plugin trees and their separate catalogs. Both branch commits identify the same release.
- [ ] Claude Git marketplace installs the relative plugin tree and invokes `/selfhost-skills:self-host` from its installed copy.
- [x] Codex marketplace installs the generated portable plugin and explicitly invokes `$self-host` in a new read-only task; its cached planning guide is read.
- [ ] OpenCode finds and loads the full installed skill via the supported skill path; V1/V2 compatibility is recorded for the versions actually tested.
- [ ] Each client can open one bundled guide/helper after the source checkout is unavailable; each update/removal path is checked.
- [x] Public OpenAI/Anthropic/Pi listings are labeled separately from native local/team availability until approved and visible.
- [ ] Any live self-host claim names the approved host/stack and carries its own verification evidence.
