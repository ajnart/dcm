# Homarr coverage outside the Catalog

Decision-ready research for [#263](https://github.com/ajnart/selfhost-skills/issues/263), **11 October 2026**. Recommendations below are proposals, not approved implementation, installation, account creation, licence purchases or additional tickets. No person's Project, live Homarr configuration, credentials or profiles were inspected.

## Recommendation

Preserve the separate **39 shipped-App integration** work. Expand the Catalog selectively: start with **Miniflux, Homebox, Mealie, Spoolman and Komga**, one App and one useful read-only Homarr widget per independently accepted slice. Keep appliances and existing deployment/network controllers external; keep legacy products, privileged collectors and provider-dependent Apps manual until their specific gates are met. Plan an explicit external-connection boundary before automating any of those connections. Neither generic tiles nor successful connection tests establish useful-widget acceptance.

The classification is **29 container-capable products, 11 external/manual connections, one feed**, plus **three separate infrastructure/discovery guides outside the 41**. Of the 29, **26 are possible new Apps**; Jellyseerr, Overseerr and Readarr are existing-instance-only recommendations. A container route is not maintained-image compatibility, automatic Setup or an approved default. External/manual includes three promotion-blocked products: Anchor, Plant-it and Syncthing Relay.

## Matrix conventions

- **C**: documented container route; **first/next/gated** are possible new Apps, **defer** means existing instances only. **E**: connect an existing external instance manually by default; **F**: feed, never an App. Priorities are proposals, not facts about shipping.
- Every connection needs a Homarr integration ID. **S** means native `stats`: select meaningful metrics and unique entry `id`, `integrationId`, `metric`; an empty Stats widget is not coverage. The [widget map][widgets] admits Stats for every non-iCal kind, but the [provider registry][stats-providers] and [existing adapters][stats-existing] have **no native metrics for Bindery or Wazuh**; the [Stats resolver][stats-resolver] returns an empty list for them. In those two rows S means nominal compatibility only, **not a useful native Stats widget**. Other widget names are exact upstream kinds. Unless named, there is no extra object-ID selector beyond the integration and widget options. [Stats schema][stats].
- **ACL?** means the verified guide establishes the credential type/route but **does not establish a narrower minimum privilege or read-only token**. Do not invent a scope, call an account-wide key least-privilege, or silently substitute administrator credentials. Any unattended credential acquisition remains unverified unless explicitly stated.
- All Apps still need a pinned image/architecture and licence review, persistent-data/Backup design and own Setup acceptance before Catalog inclusion. A row without a special paid/hardware gate is not a certification that every edition, architecture or use is unrestricted. Homarr-auth requirements and install feasibility are separate evidence.

## Independently verifiable follow-up shapes

These are ticket proposals only; **no additional issues have been published**.

1. **Compatibility/ownership contract**: choose supported Homarr version or capability check before broad automation (current App uses mutable `:dev`). Acceptance: validate exact kinds, secret alternatives, widget schemas and server ports; fail with a Manual step on unsupported capability; preserve manual resources, stable IDs, `--json` and unrelated board items. [Current image/Setup][homarr], [ownership][targets]. Does not block writing this report or unrelated shipped-App work.
2. **One Catalog App at a time**, first the five recommended above: pin image/architecture, licence and persisted-data boundary; prove own Setup/Admin login or explicit Manual step, negative auth and Backup inclusion. **Separate Homarr Link acceptance**: one chosen S metric (e.g. Miniflux unread entries, Spoolman remaining weight) matches authoritative peer data; Homebox group/Mealie household/Komga library permissions are tested. Repeat leaves IDs/resources stable; removal touches only owned resources. An empty installation or HTTP 200 is insufficient. No dependency on implementing every other candidate.
3. **External connection input decision**, then **Proxmox-only pilot**: present competing choices—leave Homarr manual (recommended until approved), or introduce explicit typed external inputs owned by Homarr. Current `app.Link` scheduler requires a Catalog peer; do not fake an installed App or repurpose Unmanaged app tiles. Before implementation decide secret ownership under `internal/project`, named identity/Address/TLS trust, approval, adoption, opt-in widgets and removal (Homarr records only, never external host). Acceptance: PVEAuditor reads a known node/guest, rejects invalid credentials, survives reconnect without duplicates, leaves manual resources/external infrastructure unchanged. [Link contract][link-contract], [scheduler][scheduler], [Unmanaged inventory][installed].
4. **iCal-only input pilot**, independent of Proxmox protocol: existing feed secret, explicit privacy/board consent; verify a known recurring event/time zone/window and malformed/empty-feed outcomes, redact feed Address, repeat/revoke without disturbing other calendars. Requires the external-input ownership decision, never an install definition or automatic calendar publication.
5. **Conditional candidate slices**, independently selectable: NetAlertX network policy; Scrutiny web/collector separation and exact devices; Wazuh server-API agents first, indexer widgets later with separate credentials/CA; llama.cpp CPU/read-only server first with user-supplied model. Each acceptance names useful data and its unavailable state. Hardware, sysctl, enrollment and model downloads are separate approved operations, not implicit Setup.
6. **Existing-instance/legacy/manual guidance**, no new default Apps: Readarr retirement, exact Jellyseerr/Overseerr versions, Anchor product identity, Plant-it server/image provenance, Syncthing Relay public-pool/image policy. Acceptance is a documented version/auth/data contract or explicit unsupported reason. There is no evidence justifying automatic aliases or product replacement.
7. **Discovery security design**, then separate Docker inventory, labels, and Kubernetes slices. Acceptance demonstrates Project/context isolation, denied lifecycle/remove/Secrets actions, no secret labels, explicit adoption, and graceful missing endpoint/metrics. Requires explicit boundary approval/ADR where the single-Project invariant changes; no broad host inventory consent inferred from Homarr installation.

## Decisions and unavoidable blockers

Accepting this research closes a planning gap, **not 41 integrations**. Decide separately: which five Apps to prioritize; whether an external-input feature is wanted at all; supported Homarr version; opt-in widgets versus defaults; and permission/adoption policy. Implementation remains future approved work.

Genuine external blockers are existing NAS/router/hypervisor hardware and operator credentials; Synology/UniFi admin/non-MFA requirements; missing narrow TrueNAS role proof; user-owned Spotify application/consent/eligibility; FileFlows organizational licensing and existing Unraid licence; privileged collection/kernel changes; lawful media/models and upstream image/version evidence for promotion-blocked/retired products. Additional research can resolve missing evidence; it cannot grant privileges, create user accounts or make unsupported upstream software maintained.

Boundaries follow [CONTEXT][context], [ADR 0001][adr1], [ADR 0005][adr5] and [ADR 0007][adr7]: compiled Apps in one Compose Project, inspect/plan/approval/apply/verify, no migration of historical Projects. No code, dependencies, tests, installer, browser or Docker runtime were changed/run. Documentation validation is inventory arithmetic, source/link checks and `git diff --check`; no full Go gate is claimed for this docs-only change.
