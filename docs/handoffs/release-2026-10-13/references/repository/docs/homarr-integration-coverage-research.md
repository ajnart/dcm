## Research-baseline findings

**At the Go research baseline, the CLI did not wire every Homarr-supported integration.** It shipped **93 Catalog Apps**, of which **47 corresponded to Homarr's research-baseline service-integration kinds**. Homarr declared **9 Links: 8 actual integrations plus a Vaultwarden navigation tile**. Thus **39 shipped, upstream-supported Apps lacked native Homarr wiring at that baseline**. Generic navigation tiles covered installed Apps with an Address, not their authenticated integrations or widgets. Sources: [Catalog assembly][catalog], [registrations][registrations], [Go targets][targets], [generic tiles][tiles], and [upstream registry][upstream]. Counts are static historical source inventory, not runtime acceptance or a claim that 39 source slices remain absent.

On 11 October, the official website listed **91 integration guides**. The Homarr **v2.4.1 research baseline** had **89 registry entries, including development Mock: 88 real service/feed kinds**. The remaining three documentation entries were **Docker, Docker labels, and Kubernetes**, which used separate infrastructure/discovery mechanisms rather than the service registry. iCal is a feed, not installable software. Consequently neither “80 integrations” nor “91 installable Apps” was an accurate denominator. Sources: [documentation catalog observed during research][docs], [release][release], [registry][upstream], [creator registry][creators], [Docker][docker], [labels][labels], [Kubernetes][kubernetes]. Mutable documentation links are not a new 12 October inventory check.

The historical TypeScript implementation was substantially broader: **48 native descriptors**, a generic attachment engine, credential alternatives, and widget prerequisites. However its claimed coverage registry listed only **49 standard surfaces**, one external-only (UniFi), while its own cited upstream snapshot already contained **88 non-Mock kinds**. It did **not** cover every upstream integration. The Go research baseline had lost wiring for **39 Apps still shipped at that baseline**; a fortieth old descriptor, **Coolify**, had no Go Catalog App there. Descriptor existence did not imply successful automatic authentication or live widget acceptance. Sources: [old descriptors][old-descriptors], [old coverage registry][old-registry], [old seed engine][old-seed], [old credential resolver][old-mapping], [old pinned upstream][old-upstream].

Research-baseline idempotency/configuration ownership:

- Apps matched by server-side `pingUrl`; browser `href` drift was repaired, and IDs retained (`links.go:750–897`). Integrations matched by **kind + internal Address**; credential fingerprints triggered `integration.update`, otherwise existing IDs were reused ([connection reconciliation][reconcile]). Matching was not a universal ownership proof: an existing manually created matching integration could be adopted/updated; removal selected the same kind/Address. Expansion needed an explicit adoption policy.
- Connection creation checked Homarr's returned **body error**, not HTTP 200 alone (`links.go:245–257`). ntfy's changed/new token was separately checked against `/v1/account`, because Homarr's connection test could accept HTTP 401 (`links.go:560–565,619–633`). Routine unchanged checks did not publish test notifications.
- Widget ownership was stored per integration; ambiguous legacy widget sets stopped with a recovery hint rather than deleting user widgets (`links.go:423–493`). Removal preserved unowned widgets and removed only the target binding from shared widgets (`links.go:708–744`). [Source][widget-ownership].
- Generic tiles used `self-host tile:<id>` markers; they reconciled installed Apps, removed marked stale tiles, and preserved unrelated records ([`installed.go:15–156`][tiles]). Installed inventory came from Project Compose fragments, included Unmanaged apps, and did not require Setup readiness ([`installed_apps.go:12–79`][installed]). Notebook listed installed Apps and explicitly disclaimed tile/widget success as integration acceptance ([`notebook.go:30–74`][notebook]).
- Successful target removal invoked consumer `Link.Remove` and forgot both link/unlink records (`lifecycle.go:149–190`); integration/widget cleanup lived in Homarr (`links.go:916–1035`). [Removal sources][unlink].

The [Homarr proof available to the research][proof] was a **7 October** scoped runtime record at `374bd1c813aa6f2d32580f1ae4fe2711a0ecb427`: ntfy/Jellyfin functionality and Gatus **navigation** add/remove, plus reconciliation/recovery. ## Why absent-peer Links appeared in the baseline terminal UI

This was a **service scheduling/state problem**, not evidence that Homarr created ntfy/Beszel resources. The later #265 merge is recorded in the [index](homarr-ticket-index.md#related-work); this section retains the original diagnosis.

1. Baseline Homarr returned every target unconditionally (`Links()` at `links.go:130–137`). The contract only required `Apply` once both Apps had finished Setup ([`app.go:108–116`][link-contract]).
2. `runSetup` called `applyLink` for **every** declared Link after successful own Setup/Check (`service.go:404–429`). `readyPeer` returned nil both for an **absent** App and for an **installed but unready** App (`service.go:525–543`). [Scheduling source][schedule].
3. Both cases called `h.Skip(link.ID, "waiting for <target> (install it, or finish its Setup)")` (`service.go:464–470`). `H.Skip` emitted a step event and recorded a persistent `skip`; recorder put it into `Steps` and `StepOrder` ([helpers skip][skip], [`service.go:315–328`][recorder]). Thus an optional peer that was never selected became a visible remembered task.
4. Status included **all** `StepOrder` entries, without peer eligibility filtering (`status.go:138–155`). Apps → Setup iterated all steps; Activity iterated all remembered steps. The activity projection even reclassified a skipped Link whose text started `waiting for ` as **NotRun**, retaining its row/target rather than hiding it. Sources: [Status][status], [Setup render][setup-render], [Activity rows][activity-rows], [Activity projection][activity-projection].
5. `skip` was **not** `manual`/`fail`: only those two needed attention, and `setupResult` ignored skips. Homarr could therefore report Setup OK alongside irrelevant waiting rows. Do **not** hide all skips: idempotent already-done steps also used `StepSkip` (`helpers.go:140–141`). [Step semantics][step-semantics], [helper semantics][skip].
6. Onboarding plan preview already filtered Links to present targets (baseline `onboarding.go:542–564`), demonstrating a usable presence concept distinct from readiness. Target removal forgot Link records, but a later baseline Homarr Setup created absent-target skips again. [Preview][preview], [unlink][unlink].

No target `Apply` executed when `readyPeer` was nil. Generic tile reconciliation selected **installed** Project Apps, so this baseline absent-peer waiting-row bug did not by itself create a phantom Homarr tile or integration. If the complaint instead concerned Homarr's browser board, stale owned resources or inventory mismatch needed a separate investigation; no live state was inspected by this research.

## Historical TypeScript finding and migration limits

- Historical `.agents/skills/self-host/workflows/selfhost/references/catalog/apps/<id>/homarr.json` files owned `integrationKind`, required/alternative secrets, widgets, stats metrics and prerequisites: **48 native mappings**. `packages/cli/src/lib/homarr-stack-mapping.ts:186–205` loaded them, and `:148–183` resolved saved credentials, preferring usable key modes. [Descriptor and resolver sources][old-descriptors], [old-mapping].
- `packages/cli/src/lib/homarr-stack-seed.ts:133–178` checked live `integration.getKinds` and exact credential alternatives. `:251–320` checked a stale-proof approval, created missing integrations and widgets, read back resources, preserved unrelated board items, and reported `renderedContentVerified: false`. This was real generic wiring code, not just an icon/name registry. [Source][old-seed].
- `homarrNativeEligibility` additionally gated exact recipe hashes and private HTTPS proofs, and widget selection required chosen IDs. Some connections could be blocked/tile-only; no honest “48 automatically working connections” conclusion followed. The historical checkout's descriptors and test expectations also differed in places (e.g. stats selections), so old tests were not a fresh passing contract. [Eligibility][old-mapping], [historical synthetic tests][old-tests].
- Historical registry's `checkedAt: 2026-10-03`, **49 standard entries**, zero special, and `externalOnly: ["unifiController"]` supported **48 bundled native descriptors + 1 external surface**, not upstream completeness. Its cited `beffe794…` registry already contained the additional 39 non-Mock kinds it omitted. The coverage report calculated its denominator from this **curated list**, rather than querying all upstream kinds (`catalog.ts:2114–2186`). [Registry][old-registry], [coverage calculation][old-coverage], [upstream counterexample][old-upstream].
- “Homarr Link” is Go vocabulary. TypeScript had catalog descriptors and attachment jobs, not this Go `app.Link` implementation. Research-baseline generic tiles preserved broad navigation, while native wiring narrowed from 48 descriptors to 8 integration targets. ## Historical research recommendations

These were 11 October research recommendations and decision topics, **not new tickets, questions or authorization now**. Later source slices and decisions are tracked in the reconciled index.

1. **Absent-peer eligibility, separate from coverage.** `internal/service` should distinguish absent peers (no scheduled row) from installed/unready peers (visible wait). Decide a common rule for all Apps versus Homarr-only behavior. Preserve consumer ownership, failed/manual waits, future install-triggered inbound Links, existing JSON/persisted formats, and idempotent skip outcomes. Historical absent-peer records needed projection or cleanup semantics, and live Activity events should agree with remembered Status; TUI-only string hiding would leave underlying task pollution.
2. **Native wiring for the 39 baseline shipped candidates.** Keep declaration/connection/widget ownership in `internal/apps/homarr`; obtain credentials in the peer App's own Setup/helper boundary, not by bypassing `internal/project`. Define credential readiness, missing-key recovery, server routes/ports and least privilege per App before batches. Decide whether “coverage” means connection configured, chosen default widgets, or verified useful data. Navigation alone is not acceptance.
3. **Catalog expansion/external connections is separate.** Forty-one upstream kinds were outside the research-baseline Catalog, some host operating systems/appliances/feeds. Decide whether external and Unmanaged peers become typed connection inputs, remain manual, or get install definitions; do not promise a Compose App for every integration. Treat Docker/Kubernetes as separate, security-sensitive features: no casual socket mount under [AGENTS](https://github.com/ajnart/selfhost-skills/blob/5aafb4c1833fd4cd9caf0f7beaac31e625aafe22/AGENTS.md#L25-L31).
4. **Compatibility contract before completeness claims.** Baseline Go shipped `ghcr.io/homarr-labs/homarr:dev`, a mutable tag (`homarr.go:29,49`), and mixed REST with internal tRPC/board payloads. Pin a supported upstream version/source contract or define a narrow compatibility check. The older implementation's live `integration.getKinds` validation was reusable precedent, not a reason to reintroduce the TypeScript runtime. [Baseline Go image][image], [old validation][old-seed].
5. **Widget policy and adoption.** Choose defaults versus opt-in, shared Stats/Calendar layout, and ID-dependent selectors (album/system/website/entity/automation). Preserve manually authored resources; define when matching integration records may be adopted, updated or removed. Broader wiring multiplies API/schema/credential churn and dashboard clutter even after absent-peer rows are fixed. [Baseline widget ownership][widget-ownership], [old prerequisites][old-mapping], [research-baseline widget compatibility][widget-map].
6. **Native versus arbitrary API access.** Baseline qBittorrent's Go username/password connection supported native downloads, but Homarr's research-baseline generic requests required an API key on qBittorrent 5.2+; iCal and TrueNAS could not be generic HTTP sources at all. A working native Link does not imply all MCP/Custom Widget actions work. [Official source-security guidance](https://homarr.dev/docs/management/custom-widgets/requests-and-security/), [baseline registry limitations][upstream].

Unknowns at the research date: deployed Homarr image digest/version; whether reported rows were terminal Setup/Activity or stale browser resources; baseline peer credential availability for every candidate; historical live acceptance outside scoped proofs; exact desired external-service/default-widget scope. None was inferred from private state. Later reference identities and bounded acceptance are recorded separately above, not retroactively substituted into this snapshot.
