## Protocol and route contracts

- `packages/cli/src/homarr-attach.ts:187-214` sends a non-batched GET to `/api/trpc/<procedure>?input=<URL-encoded {json: input}>`, with `ApiKey`. Homarr uses the [fetch tRPC adapter and API-key session](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/apps/nextjs/src/app/api/trpc/%5Btrpc%5D/route.ts) and [SuperJSON transformer](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/packages/api/src/trpc.ts). These string/boolean/number/array inputs need no SuperJSON metadata. Batch envelopes (`0`, `batch=1`) are unnecessary here.
- The client returns `result.data.json` without deserializing `meta`. This loses rich output types such as Dates, but the verifier checks ordinary numeric/object/array fields. It cannot explain an HTTP 500 received **before** response parsing. Use real SuperJSON deserialization if future checks depend on Dates or other rich types.
- Authenticated inventory reads and widget reads use the same route-level API-key-to-session resolution. Normal missing auth is `UNAUTHORIZED`; integration permission denial is `FORBIDDEN`; missing/wrong-kind IDs are `NOT_FOUND`, not expected HTTP 500. Widget queries require their own [integration query-access check](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/packages/api/src/middlewares/integration.ts), so inventory success alone does not establish widget permission.

## Plausible causes and smallest discriminating evidence

1. **Homarr-to-service failure, not CLI-to-Homarr failure.** DNS summary, Beszel, Uptime Kuma, and notifications use [settleIntegrationQueries](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/packages/api/src/settle-integrations.ts) with `throwOnAllFailures: true`. The verifier supplies one integration: any adapter rejection becomes `INTERNAL_SERVER_ERROR` / HTTP 500. Immich/Paperless propagate handler rejection directly. Candidates include server URL/DNS/routing/TLS, wrong upstream credentials, or service/API-version/permission incompatibility. A passing Homarr inventory GET does not exercise any of these. Minimal fix: correct the one verified failing server target/auth contract; do not rewrite tRPC framing. Discriminator: a safely redacted exception category from the Homarr server (`ENOTFOUND`, connection refusal, TLS, upstream 401/403, schema error), associated only with the procedure.
2. **Saved-secret decryption failure shared by integration widgets.** The [middleware](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/packages/api/src/middlewares/integration.ts) decrypts **all** integration secrets before the adapter call. [AES-CBC decryption](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/packages/common/src/encryption.ts) can throw for mismatched `SECRET_ENCRYPTION_KEY`, malformed ciphertext, or invalid IV. API-key login uses password-hash comparison, not integration-secret decryption; inventory success therefore does not rule this out. [integration.byId](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/packages/api/src/router/integration/integration-router.ts) decrypts only public secret kinds, so success there weakens the hypothesis if public credentials were actually present but does not prove every private payload decrypts. Minimal fix: restore the original encryption key for the existing DB; do not rotate it or recreate credentials blindly. Discriminator: redacted `bad decrypt` / invalid-IV / ciphertext-format exception, or the same integration failing before any upstream request. This hypothesis cannot explain secret-free integration failures by itself.
3. **Deployed-image/runtime contract differs from inspected source.** `checkSharedHomarrServices` passes the compile-time pin into its context; it does not read the running image revision. The report correctly keeps `deployedSourceRevisionVerified: false`. Older/different image or widget-only lazy module/runtime failure remains possible even with working board reads. Minimal fix: first compare deployment image revision to the pin, then align only the verified mismatch. Discriminator: image revision plus redacted module-load/type-error category. No such runtime evidence was inspected here.

Ordinary Redis unavailability is a weaker explanation: the pinned [shared-cache implementation](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/packages/request-handler/src/lib/shared-cache.ts) catches generation/read/write/lock failures and falls back to non-shared operation. The [request handler](https://github.com/homarr-labs/homarr/blob/beffe794022c22c43dd458999ee2a016bb1df2e6/packages/request-handler/src/lib/request-handler.ts) can still reject on deadline/overload/lock contention; normal cache outage should not be equated with universal HTTP 500 without its exception evidence.

## Minimal diagnostic improvement

The transport currently cancels every non-2xx response body and retains only its HTTP status. Do not expose arbitrary response bodies/messages/cause stacks: they may contain URLs, IDs, or credentials. A future narrowly authorized change could parse a size-bounded tRPC error envelope and retain only allowlisted `error.json.data.code` / numeric status and the already-known procedure; retain the existing redacted reason contract. That separates protocol/auth/not-found errors, but `INTERNAL_SERVER_ERROR` still needs a redacted server exception category to distinguish DNS, upstream auth, decryption, and runtime failures. The 12-second client timeout versus the upstream handler's 60-second default is a separate limitation; it produces `endpoint did not respond`, not the observed `homarr-query-http-500`.
