# Authelia 4.39.25: source contract, not install readiness

Checked 2026-10-03 with Context7 `/authelia/authelia` and the exact pinned
official source. No Docker, deployment, secret-state inspection or broad tests.
Focused validation passed: Bun builds of `configuration.ts`, `bootstrap.ts` and
`login-contract.ts`; `authelia-identity-contract.test.ts`; and diff whitespace
checks. The shell had no Bun on PATH, so validation used `/home/habs/.bun/bin/bun`.

## Rechecked upstream boundaries

- File users are the login identities; no separate first-admin API token is
  created. The [file model](https://github.com/authelia/authelia/blob/v4.39.25/internal/authentication/file_user_provider_database.go)
  decodes the PHC digest and rewrites the YAML file via `os.WriteFile` with mode
  `0600`. It serializes empty profile fields, null address and empty extra;
  resume now tolerates those exact defaults without accepting changed identity.
- [Pinned password defaults](https://github.com/authelia/authelia/blob/v4.39.25/internal/configuration/schema/authentication.go)
  are Argon2id, memory 65536 KiB, iterations 3, parallelism 4, key length 32 and
  salt length 16. Existing bootstrap accepts bounded parallelism 1–4 with these
  other parameters and requires injected private hash-and-verify execution.
  The focused fixture uses a synthetic hasher, not a cryptographic/live proof.
- [Login handler](https://github.com/authelia/authelia/blob/v4.39.25/internal/handlers/handler_firstfactor_password.go)
  authenticates `username` and `password`, regenerates the session and records
  regulation state. [Request types](https://github.com/authelia/authelia/blob/v4.39.25/internal/handlers/types.go)
  permit `keepMeLoggedIn: false`. Fresh cookie-session
  [state readback](https://github.com/authelia/authelia/blob/v4.39.25/internal/handlers/handler_state.go)
  proves exact username, numeric one-factor level and password knowledge flag;
  these are checked by the source-only `login-contract.ts`.
- [User-info handler](https://github.com/authelia/authelia/blob/v4.39.25/internal/handlers/handler_user_info.go)
  returns display name and redacted email; its POST may create storage records.
  A display name or successful HTTP status alone is not account verification.
- [Session docs](https://www.authelia.com/configuration/session/introduction/)
  require HTTPS, a standard-use domain shared by the portal and target, and no
  public/special-use cookie suffix. [Pinned validator](https://github.com/authelia/authelia/blob/v4.39.25/internal/configuration/validator/session.go)
  checks scope and distinct default redirection. `.localhost` is not a safe
  workaround. The compiler fails closed on an absent/non-boolean classifier;
  injected synthetic fixture classification is not a real PSL implementation.
- [Storage](https://www.authelia.com/configuration/storage/introduction/) needs
  its encryption key. The app compiler retains local SQLite and the documented
  storage/session/reset secret-file bindings. The explicit filesystem notifier
  needs private writable custody for reset/enrollment notifications; it does
  not prove email delivery or an accessible recovery channel.
- [Pinned image](https://github.com/authelia/authelia/blob/v4.39.25/Dockerfile)
  defaults PUID/PGID to zero; its [entrypoint](https://github.com/authelia/authelia/blob/v4.39.25/entrypoint.sh)
  can recursively chown `/config` before dropping privileges. A future recipe
  must avoid changing ownership of mounted shared secret/config files and prove
  exact runtime user access to writable user/SQLite/notifier state.

## Current shared-engine gaps

Do not register a selectable recipe/setup adapter yet. Derived recipes do not
add writable private identity state. Static config files are non-secret and
read-only; private configs are immutable. Existing canonical-origin transitions
replace exact environment values, not this app's cookie/policy configuration.
Private HTTPS currently emits `.localhost` routes only and no forward-auth
policy wiring. Portal liveness would be a false success.

The smallest next engine requirement is a typed, private **writable derived
identity database**: save one generated password; derive/verify a supported
Argon2id PHC digest without argv/log exposure; create once atomically with exact
image-user access; record only provenance/path; parse installed YAML privately
and verify identity/digest on resume; never replace changed/reset users.
Its writable mount must keep hashes out of recipes, preferences, Compose,
approval/status records, logs and ordinary evidence.

Independently require a real PSL/special-use classifier plus approved real-domain
private portal/target routing, DNS/trust and a single proxy's forward-auth rules.
Only then bind the non-secret configuration to the owner revision and implement
fresh private-session login/readback. Acceptance still needs anonymous denial,
authenticated target access, intended-client DNS/trust and scoped restart
persistence. No app-local TLS or user-state write workaround was added.
