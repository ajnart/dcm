# Remaining identity setup — 2026-10-03

Scope: Authelia 4.39.25, Passbolt API 5.16.0, Vaultwarden 1.37.3. Source-only
review; no Docker, deployment, credentials, browser, trust mutation, image pull,
or account acceptance. Context7 resolve/docs succeeded for all three; directly
read the pinned public account/database/registration source to avoid treating
indexed main-branch examples as versioned contracts.

## Result

No honest useful-first-owner recipe fits the current shared interfaces. Retain
Authelia/Vaultwarden guided and Passbolt discovery; no new support promotion,
`no-account` disguise, pending-only adapter, or absence-only test. App-local
`setup-prerequisites.md` records inputs, minimal owner interfaces and acceptance.
Three manifest pitfalls were corrected to avoid the obsolete blanket claim that
HTTPS is necessarily planning-only; account and configuration blockers remain
independent of the applied host-only route.

The incoming HTTPS owner exports a revision-bound route/CA and narrow transport
proof for lowercase `*.localhost`; it does not install client trust, transition
an app's canonical-origin setting, or create an account. Authelia is explicitly
excluded. Passbolt and Vaultwarden therefore still need a stable-origin config
gate before sending enrollment data, even if host TLS succeeds.

## Reusable interfaces to implement next

These are proposals, not existing schema fields or verified adapters.

### Secret-derived writable identity file

For Authelia, a typed preparation declaration should name the app consumer,
generated password file ID, one supported hash format/parameters, bounded user
identity/email/groups, fixed target, and official source. The owner must perform:

1. Approved first creation: privately derive digest, serialize a bounded record,
   create atomically with exact runtime readability/writability, and save the
   recipe/owner/password-reference provenance without digest output.
2. Resume: verify the expected user and saved-password/digest relationship before
   continuing. Never rewrite changed user records or treat password-reset changes
   as permission to reseed. Fail for links, multiple links, ownership/mode drift,
   unexpected users, or incompatible hash parameters.
3. Independent config gate: derive only reviewed literal config from canonical
   portal/cookie topology, deny-first policy, protected target and notifier choice;
   bind secret-file references, not payloads. Validate Authelia's actual cookie
   rules rather than relaxing them for localhost TLS.

Current `privateConfigs.parts` only interpolate generated bytes and are mounted
read-only; `bcrypt-hash` only produces an environment value. Neither implements
the mutable hashed database. The [pinned database](https://github.com/authelia/authelia/blob/v4.39.25/internal/authentication/file_user_provider_database.go)
decodes digests and rewrites user data; the
[pinned session validator](https://github.com/authelia/authelia/blob/v4.39.25/internal/configuration/validator/session.go)
enforces portal/cookie topology. A static portal without a working user and one
protected forward-auth target is not useful acceptance.

### Typed private enrollment capture

Passbolt needs a private output profile distinct from `captureAdminPassword`:
fixed upstream command/runtime user, exact expected user/role, approved canonical
origin, bounded setup-path/UUID parser, and a dedicated mode-0600 handoff file.
Checkpoint before command execution; suppress ordinary stdout; capture before
further requests; verify record identity/role; stop after lost output instead of
creating another user. Return only a file reference, never token/path payload in
status, approvals or checkpoint data. Resume must preserve the same handoff and
origin; it cannot infer active-user login from a registration record.

The [pinned register command](https://github.com/passbolt/passbolt_api/blob/v5.16.0/src/Command/RegisterUserCommand.php)
prints `/setup/start/<user-id>/<token>`. The
[CE guide](https://www.passbolt.com/docs/hosting/install/ce/docker/) requires browser
completion, SMTP and correct time. Owner GPG key/passphrase/recovery-kit custody
and GPG-authenticated encrypted save/decrypt remain a separate gate. Server
GPG/JWT/database volumes must persist; no exact CE image was independently checked.

### Official-client encrypted enrollment/unlock

Vaultwarden needs a pinned compatible official client, not a new generic signup
request body. Bind client executable/version/server origin to the owner; privately
transport password and client state; checkpoint enrollment before send; verify
exact account and a decrypted harmless vault round-trip. A password-grant token
is narrower than unlock. Preserve the existing standalone official-web-client
gate until a proven headless client exists.

The [pinned account model](https://github.com/dani-garcia/vaultwarden/blob/1.37.3/src/api/core/accounts.rs)
requires KDF, authentication hash and wrapped key; the
[identity route](https://github.com/dani-garcia/vaultwarden/blob/1.37.3/src/api/identity.rs)
adds device fields/challenges. The
[file reader](https://github.com/dani-garcia/vaultwarden/blob/1.37.3/src/util.rs)
supports `NAME_FILE` and rejects simultaneous direct/file settings.
[ADMIN_TOKEN](https://github.com/dani-garcia/vaultwarden/wiki/Enabling-admin-page)
authenticates a separate server-admin page and may use Argon2id PHC; leave it
disabled and never count it as vault-account readiness. Closure still requires
effective-policy inspection for signup whitelist, invitations and saved config.

## Validation boundary

Owned JSON parses, source/diff checks only. No executable adapter or fixture was
created, so no tests/builds were run. Fresh setup/replay, exact-owner login,
encrypted round-trip/forward-auth, intended-client trust, restart persistence and
isolated restore remain unverified. Transport proof and health do not replace them.
