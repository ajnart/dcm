# Next installable route: WUD, after verified inventory authority

Checked 2026-10-03 against checkout `a76fef6` and the concurrent opt-in derived-loader change. Read the remaining-installability report and staged app sources first. No runtime, private stores, Docker, browser, tests, CI or source changes; only this note was written. Current documentation lookup used find-docs/Context7 for Pangolin and WUD, followed by exact release sources where indexed documentation was incomplete or different.

## Decision

**None of the six becomes a purpose-complete installable app solely by adding an opt-in declaration. Choose WUD next, but keep it staged until the shared Docker inventory authority owner can verify the endpoint's effective deny-write policy before startup.** WUD's real purpose—fresh registry update detection for an authorized running container—fits its staged recipe and existing private-file/HTTP/checkpoint interfaces. It does not require a new TLS application origin or an invented administrator/API-key flow. This is an implementation recommendation, not compatibility or live acceptance credit.

The new `SharedDerivedRecipeAdapter` discovery removes an app-ID allowlist, not operational prerequisites. `derived-recipe-adapter.json` remains the explicit activation gate; HAProxy, Headscale and MinIO are the enabled entries. WUD has a candidate `derived-recipe.ts` and `setup.ts`, but no activation declaration. Its setup correctly returns `ready() === false`.

## Exactly missing common capability

Extend the existing `docker-api-authority.ts`, `docker-api-authority-state.ts` and `docker-api-authority-probe.ts` owner, not WUD inputs:

1. Bind effective policy evidence to the exact private endpoint/Engine ID, peer/CA/client certificate fingerprints, imported-file identities, app recipe/setup/image hashes, shared owner revision and expiry. Establish enforced inventory reads and denied mutation through a separately reviewed endpoint-policy mechanism; a supplied hash or `approved: true` is not inspection.
2. Persist a verified inventory-authority observation and replay/revalidate it immediately before every initial start, add and recreate. The existing `/info` probe proves only transport/Engine identity. `requireDockerApiAuthorityForStart` currently rejects inventory mode with `policy-unverified` unconditionally.
3. Have shared status supply that trusted observation to WUD. Its app-owned authority claim records consent only. Enable discovery and readiness only when both authority and fresh scan proof exist; do not remove `ready() === false` first.

[Docker TLS guidance](https://docs.docker.com/engine/security/protect-access/) warns that ordinary client certificates convey daemon control; [authorization plugins](https://docs.docker.com/engine/extend/plugins_authorization/) supply a separate policy boundary. Current [WUD remote TLS documentation](https://getwud.app/docs/configuration/watchers/remote-tls/) and the pinned watcher confirm TLS files plus label filtering, not read-only authority. This verifier does not authorize provisioning a daemon/socket/proxy or destructive denial probes; those require exact separate approval and ownership.
