# WUD remote TLS recipe audit — 2026-10-03

Pinned `getwud/wud:9.1.0`. No deployment or private file reads performed.

Context7 lookup used `library "What's Up Docker"` then `/websites/getwud_github_io_wud` docs. The official index describes watcher-fed inventory but has no remote-TLS details; implementation decisions below use pinned publisher source.

## Remote inventory boundary

The [Docker watcher](https://raw.githubusercontent.com/getwud/wud/9.1.0/app/watchers/providers/docker/Docker.ts) accepts host/port and `cafile`, `certfile`, `keyfile`; it reads these files into Dockerode TLS options. A supplied host avoids its socket fallback. `watchbydefault=false` selects `wud.watch=true` labels after listing containers; it is not an API ACL or per-container authorization boundary. Events are disabled in this recipe. No update trigger or socket proxy is provisioned.

The derived compiler takes exact DNS name, decimal port and one full expected container ID. CA/certificate/key inputs are fixed opaque owner-file references, imported only at the private apply boundary. The configuration declares a fingerprint of endpoint, file identities and expected inventory scope. A separate exact remote-Docker authority approval must be enforced before start: ordinary Compose approval cannot confer it. TLS credentials may grant powerful Docker access; mutating API denial needs an endpoint-owner observation, not a recipe claim.

## Secret and administrator configuration

Pinned [configuration loading](https://raw.githubusercontent.com/getwud/wud/9.1.0/app/configuration/index.ts) supports `__FILE` suffix replacement. This reads contents, so use `WUD_AUTH_ADMIN_PASSWORD__FILE` for the generated password, but direct `CAFILE`/`CERTFILE`/`KEYFILE` private path bindings for TLS material. The common `file-path` owner-file contract is required; `CAFILE__FILE` would incorrectly pass PEM contents where a filename is expected.

[Bootstrap source](https://raw.githubusercontent.com/getwud/wud/9.1.0/app/store/auth_bootstrap.ts) creates or updates the named admin on every startup. This is ongoing declarative credential ownership, not an empty-database seed. [Basic authentication](https://raw.githubusercontent.com/getwud/wud/9.1.0/app/authentications/providers/basic/Basic.ts) verifies local users against stored hashes. No personal token is created. [Store source](https://raw.githubusercontent.com/getwud/wud/9.1.0/app/store/index.ts) defaults to `/store/wud.sqlite`; the recipe persists `/store`. The [official Dockerfile](https://raw.githubusercontent.com/getwud/wud/9.1.0/Dockerfile) publishes 3000 and starts Node; this recipe keeps host publication loopback-only.

## Setup and remaining acceptance

The setup adapter requires exact retained derived metadata plus owner-issued `remoteDockerAuthority` approval with matching fingerprint. It observes anonymous inventory rejection, authenticated local admin identity through `/auth/user`, and exactly the expected container with watcher `approved` and image inventory from [GET container API](https://raw.githubusercontent.com/getwud/wud/9.1.0/app/api/container.ts). It does not request an active watch or invoke mutating Docker operations.

Ready is explicitly administrator-and-inventory observation, never Docker authorization, scan freshness, update correctness or restart persistence. Stored inventory can be stale. Real acceptance requires authorized endpoint ACL checks, current image/update comparison and separately approved restart/readback. A different observed watched scope fails closed instead of silently broadening authority.

Do not register this derived adapter for ordinary add/apply until the common separately approved authority gate is wired. Private file contents are not catalog inputs or reports. Homarr publication remains separate.
