# Coolify traps

## Pitfalls

- Installing a second deployment platform can duplicate proxy and port ownership.
- A running dashboard is not proof that the first administrator, local server SSH connection, or API access is configured. The official installer can pre-create the root user with ROOT_USERNAME, ROOT_USER_EMAIL, and ROOT_USER_PASSWORD; API tokens are created after sign-in and are not an install-time bootstrap secret.
- Coolify instance backups exclude deployed application data and require the separately saved APP_KEY for secret recovery.
- Pinned root-user seeding validates a DNS-resolvable owner email and a mixed-case, numeric, symbol-bearing password, then disables registration. It skips an existing root rather than resetting it. Generic generated bytes or a synthetic .test email do not establish that bootstrap succeeded.

## Security

- Coolify controls connected Docker hosts over SSH. Its official production Compose does not mount the host Docker socket; host SSH access and Docker-resource authority still require explicit approval and isolation beyond the generic scoped Compose recipe.
- Keep the dashboard private during first-admin registration. Public DNS, TLS, ports 80/443, and proxy ownership require a separate ingress approval.
- Protect the instance database, APP_KEY, SSH private keys, API tokens, and off-host backups as privileged recovery material.
