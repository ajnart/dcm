# PeaNUT shared-Compose assessment — 2026-09-30

Decision: add a v2 shared recipe and first-run adapter for a private, authenticated dashboard only. A private container can start without a UPS; readiness here means the generated administrator credential works, not that UPS monitoring works. Keep discovery support until live setup and restart evidence exist. No Docker or live instance was run.

The [upstream README](https://github.com/Brandawg93/PeaNUT#installation) shows a PeaNUT container with persistent `/config`, port 8080, and `WEB_PORT=8080`. It explicitly requires the mounted directory to be writable by the container's UID/GID 1000:1000 (or a selected matching numeric Compose user); `PUID`/`PGID` are unsupported. Its [v6.0.0 pinned Compose file](https://github.com/Brandawg93/PeaNUT/blob/v6.0.0/docker-compose.yml) instead defines only a `brandawg93/nut-upsd:latest` test NUT server with `API_PASSWORD=nut_test`, a local config mount, and port 3493. That file is not a pinned production PeaNUT-plus-UPS topology and its example password must not be reused.

PeaNUT reads UPS data from a NUT server. A real installation first needs an operator-owned UPS and a reachable NUT server, plus the selected server address, UPS name, and a credential/permission scope appropriate to monitoring or control. The [NUT user manual](https://networkupstools.org/docs/user-manual.chunked/index.html) separates driver, `upsd`, and client configuration; PeaNUT's dashboard cannot create or validate the physical device. Treat an existing NUT server as an explicit dependency, not an assumed `localhost` service. Publishing 3493 or granting UPS command rights needs separate review.

The [upstream README environment table and Authentication section](https://github.com/Brandawg93/PeaNUT/blob/v6.0.0/README.md) document `WEB_USERNAME` and `WEB_PASSWORD` for initial user auto-creation and HTTP Basic authentication for API calls. The recipe supplies a generated private password, fixed `admin` username, loopback-published 8080, and a project-owned named volume for `/config`; `AUTH_DISABLED` is not set. The [pinned Dockerfile](https://github.com/Brandawg93/PeaNUT/blob/v6.0.0/Dockerfile) uses UID/GID 1000 and does not set `AUTH_FILE_PATH`. The [v6 storage defect](https://github.com/Brandawg93/PeaNUT/issues/423) means the recipe cannot claim auth-file or restart persistence; the environment bootstrap is kept so the dashboard can authenticate on first start.

The headless adapter checks anonymous and incorrect-password rejection, then the generated Basic credential against the documented `/api/v1/info` endpoint. It sets `nutMonitoringVerified: false` and makes no API-key claim. A later UPS-monitoring feature requires an exact user-selected NUT endpoint and device identity, a safe private reachability model, and actual readings. Monitoring acceptance still would not prove load runtime, shutdown sequencing, or power-return recovery. No account, key, or NUT configuration was created on a live host in this pass.

The [pinned entrypoint](https://github.com/Brandawg93/PeaNUT/blob/v6.0.0/entrypoint.mjs) maps `WEB_HOST` to the server `HOSTNAME` and falls back to `0.0.0.0`; the [pinned Dockerfile](https://github.com/Brandawg93/PeaNUT/blob/v6.0.0/Dockerfile) also sets `WEB_HOST=0.0.0.0`. The recipe states it explicitly to avoid the README's misleading `localhost` default. That is container-internal listening only; shared Compose publishes the host port on `127.0.0.1`. The README documents `/api/v1/info` and Basic authentication but not the response body shape; the adapter therefore relies on a 200 after negative auth checks, not invented JSON fields. The pinned Dockerfile copies `/config` with owner `1000:1000`; [Docker volume initialization](https://docs.docker.com/engine/storage/volumes/) copies the image directory into a fresh named volume by default. Existing or non-local volumes still need a live writable-path check.
