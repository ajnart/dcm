Checked 2026-09-29. Source-only contract review for qBittorrent `5.2.3`, SABnzbd `5.1.3` (the recipe's 5.1 pin), Sonarr `4.0.19.2979`, and Radarr `6.4.4.10685`. No service was started, no live API call or secret access was made, and no provider/indexer, VPN, or proxy was configured. Pins are in the [qBittorrent](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/qbittorrent/recipe.json#L8-L35), [SABnzbd](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/sabnzbd/recipe.json#L8-L35), [Sonarr](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/sonarr/recipe.json#L8-L31), and [Radarr](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/radarr/recipe.json#L8-L31) recipes.

## Network and category contract

The four recipes use service IDs `sonarr`, `radarr`, `qbittorrent`, and `sabnzbd`; qBittorrent and SABnzbd listen on container port `8080`, Sonarr on `8989`, and Radarr on `7878`. On one Compose project's default network, containers resolve each other by service name and use the container port, not the host-published port. Thus Arr clients should target `qbittorrent:8080` and, if selected, `sabnzbd:8080`—not `localhost` or a host port. Separate Compose projects do not share that default network; cross-project service discovery requires an explicitly selected existing external network. The current per-app recipes don't declare that shared network, so its ownership must be resolved before apply ([Docker Compose networking](https://docs.docker.com/compose/how-tos/networking/)).

qBittorrent's v5.0+ WebUI API docs apply to the pinned 5.2.3 release. The minimal category sequence is:

1. `POST /api/v2/auth/login`, form fields `username` and `password`; retain the returned session cookie. The pinned 5.2.3 controller rejects bad credentials with unauthorized, while the older-format wiki example describes a 200 login response. Require a valid cookie and a subsequent authenticated read, not status alone ([pinned controller](https://github.com/qbittorrent/qBittorrent/blob/release-5.2.3/src/webui/api/authcontroller.cpp), [WebUI API](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-%28qBittorrent-5.0%29)).
2. `GET /api/v2/torrents/categories` with the cookie: `200`, JSON object keyed by category, each carrying `name` and `savePath`.
3. For each approved category that is absent, `POST /api/v2/torrents/createCategory` with URL-encoded `category` and `savePath`; `200` is success, `400` is an empty name, `409` an invalid name. After any create, repeat the GET and require exact name/path readback. The API docs do not define duplicate-create behavior, so a 200 is not proof that the requested category/path now exists. If a same-name category has a different path, `POST /api/v2/torrents/editCategory` is a separate mutation (`200` success, `400` empty name, `409` edit failure) and requires owner approval before use ([category endpoints/statuses](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-%28qBittorrent-5.0%29)).

The canonical harness currently chooses these mappings; they are harness choices, not defaults declared by each per-app recipe:

| Arr | Arr qBittorrent field | qBittorrent category | Category save path |
| --- | --- | --- | --- |
| Sonarr | `tvCategory` | `tv-sonarr` | `/data/torrents/tv-sonarr` |
| Radarr | `movieCategory` | `movies-radarr` | `/data/torrents/movies-radarr` |

Those names/paths are in [bootstrap-core.ts](../../scripts/bootstrap-core.ts#L214-L237) and its [Arr mappings](../../scripts/bootstrap-core.ts#L571-L589). The qBittorrent recipe pins the target/published port to 8080 and mounts the selected shared data root at `/data`; do not infer an alternate host path ([recipe](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/qbittorrent/recipe.json#L29-L50)).

## Arr API sequence

For each Arr app, send its own API key in `X-Api-Key` (not the URL). The pinned Sonarr and Radarr OpenAPI files both define `GET /api/v3/downloadclient/schema` as a `200` array, `GET /api/v3/downloadclient` as a `200` array, `POST /api/v3/downloadclient/test` with a `DownloadClientResource` JSON body and `200`, plus collection create / ID-specific update / GET-by-ID routes ([Sonarr spec](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/Sonarr.Api.V3/openapi.json), [Radarr spec](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/Radarr.Api.V3/openapi.json)). The pinned Sonarr provider base builds templates from each installed implementation's defaults; its resource mapper serializes `Fields` from that settings schema, and the download-client resource adds enable/protocol/priority/removal flags ([provider resource](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/Sonarr.Api.V3/ProviderResource.cs), [download-client resource](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/Sonarr.Api.V3/DownloadClient/DownloadClientResource.cs)). Runtime schema is therefore authoritative for plugin fields: select the exact implementation and carry `implementationName`, `implementation`, `configContract`, `fields` (`name`/`value` pairs), `name`, `enable`, `protocol`, `priority`, removal flags, and `tags`; include the existing `id` only for an update. Use the returned qBittorrent/SABnzbd schema rather than synthesizing a field list.

1. Read schema and existing client list (both `200`). Refuse an ambiguous duplicate and preserve unrelated clients.
2. `POST /api/v3/downloadclient/test` with the complete proposed resource (`forceTest` defaults false). Pinned `ProviderControllerBase` returns `200`/`{}` only after validation and client test succeed; errors fail the request. Save itself also tests enabled entries, so this explicit test is a deliberate pre-save gate, not a requirement to avoid the save-time test ([Sonarr controller](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/Sonarr.Api.V3/ProviderControllerBase.cs), [Radarr controller](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/Radarr.Api.V3/ProviderControllerBase.cs)).
3. If no exact selected entry exists, `POST /api/v3/downloadclient`; pinned controller code calls `Created(id)` (HTTP `201`). To change an owner-selected existing ID, `PUT /api/v3/downloadclient/{id}` calls `Accepted(id)` (HTTP `202`). Note a pinned-contract discrepancy: both generated OpenAPI specs advertise `200` for these writes, while Sonarr's pinned REST helper implements `Created`/`Accepted` via `CreatedAtAction`/`AcceptedAtAction` (201/202). Radarr's pinned provider controller uses the same helper calls; its 201/202 mapping is inferred from that source parity and the standard action helpers, not independently confirmed from the Radarr REST helper file. Treat 201/202 as source-derived expectations and stop to inspect if the pinned runtime disagrees—do not accept an arbitrary status range ([Sonarr REST helper](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/Sonarr.Http/REST/RestController.cs), [Radarr provider controller](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/Radarr.Api.V3/ProviderControllerBase.cs)).
4. `GET /api/v3/downloadclient` or `/api/v3/downloadclient/{id}` (`200`) and verify the unique saved non-secret configuration: ID, implementation, name, service host/port, category, enablement, and owner-chosen priorities/removal policy. Never emit request bodies or secret field values as evidence.

For both downloaders, the network fields are host `qbittorrent` or `sabnzbd` and container port `8080`. qBittorrent supports either API-key auth or username/password, not both; SABnzbd supports an API key or a username/password pair. SABnzbd's pinned-compatible 5.1 API requires its API key for ordinary API calls and accepts it as a query parameter; its `auth`/`version` operations are exceptions ([Sonarr qBittorrent settings](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/NzbDrone.Core/Download/Clients/QBittorrent/QBittorrentSettings.cs), [Sonarr SAB settings](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/NzbDrone.Core/Download/Clients/Sabnzbd/SabnzbdSettings.cs), [SAB API reference](https://sabnzbd.org/wiki/configuration/5.1/api)). Keep the API key or credentials as private secret references; do not put values in plans, logs, checkpoints, or screenshots. SAB categories are owner-selected existing categories (Sonarr's pinned implementation defaults to `tv` and treats a category as recommended); do not silently create/rename SAB categories. API test/readback proves connectivity/configuration only, not path import, restart persistence, or a download.

## Replay boundaries, owner choices, and adapter gaps

GETs and the Arr test endpoint are safe to repeat. Before each qBittorrent category create/edit and Arr client create/update, persist a one-time attempt checkpoint containing the target app, category/path or client ID/implementation and sanitized desired state—never credentials. On an uncertain result, read current state first and reconcile exact readback; do not blindly replay a category edit, Arr POST (which can duplicate a client), or a PUT against an uncertain ID. If the saved state conflicts or remains absent after an attempted mutation, stop for inspection. A pre-existing category with a different save path and an existing Arr client that differs from the requested target are owner decisions, not automatic corrections.

Confirm: whether to connect each Arr to qBittorrent and optionally SABnzbd; whether these category names and `/data` paths are acceptable; how to handle existing clients/categories; API-key versus username/password auth using only already-owned credentials; SAB category; and download priority plus `removeCompletedDownloads`/`removeFailedDownloads` behavior. The shared Compose project/network must also be explicit. Do not invent provider credentials or select indexers; Usenet provider setup, indexer/Prowlarr setup, proxy/public exposure, and VPN routing/fail-closed verification are separate workflows and approvals.

The [qBittorrent setup adapter](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/qbittorrent/setup.ts) now handles login, paths, API-key handoff, and category create/readback for Sonarr/Radarr selected in the same shared Compose owner. [Sonarr](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/sonarr/setup.ts) and [Radarr](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/radarr/setup.ts) adapters cover authentication/root-folder work but not download clients. [SABnzbd setup](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/sabnzbd/setup.ts) handles its own admin/API key/paths/provider handoff, not Arr wiring. By contrast, canonical [bootstrap-core.ts](../../scripts/bootstrap-core.ts#L206-L238) creates categories and [tests/saves qBittorrent Arr entries](../../scripts/bootstrap-core.ts#L346-L412), but it does not GET categories after writes or read back saved Arr clients, has no write-ahead checkpoints, silently edits conflicting category paths, picks the first matching implementation, hardcodes both removal flags true, and has no SABnzbd branch. This is harness functionality, not completed per-app adapter support or live acceptance.
