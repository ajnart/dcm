# Authentik catalog candidate — 2026-09-30

The pinned [upstream 2026.8.3 Compose file](https://github.com/goauthentik/authentik/blob/version/2026.8.3/lifecycle/container/compose.yml) uses `ghcr.io/goauthentik/server:2026.8.3` for server and worker, `postgres:16-alpine`, shared `/data`, and PostgreSQL health gating. This candidate uses one project-owned shared data volume and loopback-only HTTP. [Install guidance](https://docs.goauthentik.io/install-config/install/docker-compose/) permits removing the worker Docker socket when outposts are managed separately. No automatic Docker outpost deployment is claimed.

The shared engine generates the PostgreSQL password, signing key, initial administrator password, and bootstrap API token in owner-only private files. It binds their values through its owner-only env file into the worker/server environment. Docker operators can inspect container environment, so Docker daemon access remains privileged. [Automated installation](https://docs.goauthentik.io/install-config/automated-install/) supports `AUTHENTIK_BOOTSTRAP_PASSWORD` and `AUTHENTIK_BOOTSTRAP_TOKEN` on the worker, read only on first startup; it warns that the password remains plaintext in the environment and prefers a hash. This recipe accepts that explicit tradeoff because the shared preparation contract cannot invoke the pinned image's `hash_password` before apply or bind its output safely. A later restart must verify the saved token; it must not assume the bootstrap values reset an existing database.

The app adapter confirms an anonymous request does not identify an administrator, then requires the saved bootstrap token to identify `akadmin` as a superuser through the [current-user API](https://api.goauthentik.io/reference/core-users-me-retrieve/). The [pinned endpoint source](https://raw.githubusercontent.com/goauthentik/authentik/version/2026.8.3/authentik/core/api/users.py) serializes `request.user` without an authenticated-user permission, so a 200 anonymous identity is expected and is not an access-control failure. The adapter then runs the bounded [Flow Executor](https://api.goauthentik.io/flow-executor/) identification/password stages with in-memory cookies and verifies that the resulting session identifies the same superuser. It refuses unexpected or MFA stages; those need the protected browser flow. The checkpoint records only that this login was verified, not a live-session claim on future inspections. Break-glass access, app/provider setup, and restart persistence remain separate acceptance gates. A lost first-start token or database provenance mismatch must be investigated, not followed by blind re-bootstrap.

Only the catalog source was checked. No image pull, Compose apply, live login, or persistence check was performed.
