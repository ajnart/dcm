# Vaultwarden catalog assessment — 2026-09-29

Decision: keep guided support and do not publish a shared recipe or headless `setup.ts` yet. The existing `cliSetup` descriptor named an unregistered route and was removed. The missing primitive is a verified private HTTPS origin bound to `DOMAIN` before any account/bootstrap exchange, followed by an exact-owner, replay-safe first-account gate that leaves registration closed. A loopback HTTP Compose bind does not meet that boundary, and Compose liveness is not vault acceptance.

The upstream [container guide](https://github.com/dani-garcia/vaultwarden/wiki/Starting-a-Container) identifies `vaultwarden/server` as the image, container port 80, and `/data` as persistent state. It supports binding the host port to a chosen private IP. The upstream [configuration template](https://github.com/dani-garcia/vaultwarden/blob/main/.env.template) says `DOMAIN` must match the actual access address, recommends HTTPS through a reverse proxy, defaults `SIGNUPS_ALLOWED` to true, and disables `/admin` when `ADMIN_TOKEN` is absent. Its [HTTPS guide](https://github.com/dani-garcia/vaultwarden/wiki/Enabling-HTTPS) covers the secure-origin requirement. This means a recipe that merely binds loopback HTTP while leaving defaults would expose registration to any client with access to that private route.

`ADMIN_TOKEN` is for server administration, not a vault owner account. The [admin guide](https://github.com/dani-garcia/vaultwarden/wiki/Enabling-admin-page) recommends an Argon2id PHC token, warns that Compose requires escaping dollar signs, and notes that `config.json` can override environment settings. Do not put a plaintext admin token in catalog JSON or turn on `DISABLE_ADMIN_TOKEN`. Leaving the admin page disabled is the safer default until a separately reviewed administration need and secret path exist. The configuration template also documents that a signup domain whitelist can override `SIGNUPS_ALLOWED=false`; closed registration needs authenticated readback of effective settings.

Future implementation should choose a versioned official image, render `/data` persistence and private networking, require an exact HTTPS URL/certificate or verified private TLS ingress owner before enabling signup, create the first vault account through a source-pinned protocol with checkpoint/readback or an explicit manual-account gate, close signup and prove it closed, then verify login, export, and a vault-item round-trip through a compatible client. It must prove backup and isolated restore for database, attachments, and key material. No live deployment, TLS route, account creation, client compatibility, export, restart, or restore was tested here.
