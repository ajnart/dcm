# FreshRSS catalog evidence — 2026-09-29

- The [pinned 1.30.0 Docker guide](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/Docker/README.md) documents the official image, port 80, `TZ`, `CRON_MIN`, and persistent `/var/www/FreshRSS/data` and `/var/www/FreshRSS/extensions` volumes. It identifies SQLite as the built-in, simplest database. The [release](https://github.com/FreshRSS/FreshRSS/releases/tag/1.30.0) identifies the versioned tag; the owner's normal digest review is still required.
- The [FreshRSS CLI guide](https://github.com/FreshRSS/FreshRSS/blob/edge/cli/README.md) separates `do-install.php --default-user admin --auth-type form --db-type sqlite` from `create-user.php --user admin --password ...`: installation does not itself create the user. It also documents a distinct `--api-password` and `--api-enabled` for mobile API access. The [pinned Docker guide](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/Docker/README.md) explicitly offers either the browser installer or running these CLI scripts as the image's web user. `FRESHRSS_INSTALL` / `FRESHRSS_USER` run at first startup; the [pinned entrypoint](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/Docker/entrypoint.sh) passes their values to the CLI. The current recipe does not bind the generated password to either environment variable, so no first user is silently created.
- Follow-up after exact-container `exec({argv, stdin, approval, beforeSendCheckpoint})` landed: it prevents host Docker argv leakage and can checkpoint one-time CLI mutations, but does **not** make this pinned first-admin path secret-safe. The [1.30.0 `create-user.php` source](https://raw.githubusercontent.com/FreshRSS/FreshRSS/1.30.0/cli/create-user.php) accepts `--password` through `CliOptionsParser`; [that parser](https://raw.githubusercontent.com/FreshRSS/FreshRSS/1.30.0/cli/CliOptionsParser.php) calls PHP `getopt()`, which consumes the actual process command line. A fixed `sh -c` wrapper reading private stdin would still have to launch `create-user.php --password "$value"`, exposing the value in the in-container process argv. Fabricating a PHP `$argv` array does not solve it because `getopt()` reads the real argv. The CLI returns exit code 3 when a user already exists, which is useful for replay detection but is not proof that the saved generated password owns that user. `FRESHRSS_USER` likewise passes its value to the CLI at first start via the [pinned entrypoint](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/Docker/entrypoint.sh).
- Rechecked the pinned [CLI guide](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/cli/README.md), [create-user source](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/cli/create-user.php), [update-user source](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/cli/update-user.php), and [reconfigure-user source](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/cli/reconfigure-user.php). `reconfigure-user.php --value-stdin` does avoid argv for an existing configuration attribute, but the documented first-user and password commands remain `create-user.php --password` and `--api-password`. Creating a user with an empty password and then writing an internal hash attribute by stdin would be an undocumented credential-bootstrap sequence with a temporarily unprotected account. This does not meet the shared setup's source-backed, safely verifiable first-admin requirement. Keep `setup.ts` absent and the recipe's browser/CLI acceptance pending until upstream exposes a supported secret-safe first-user route or a bounded, verified private HTTP flow is established.
- The documented Web installer is interactive; no version-pinned, inspect-before-write HTTP creation contract with replay and independent form-login verification was established here. Therefore no `setup.ts` is added and shared setup remains pending. A future route needs an upstream-supported password-stdin/file CLI option or a verified HTTP installer contract, then saved-credential login readback and restart proof.
