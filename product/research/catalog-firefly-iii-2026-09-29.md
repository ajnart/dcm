# Firefly III shared Compose candidate — 2026-09-29

## Source-backed boundary

- The [upstream Docker Compose](https://github.com/firefly-iii/docker/blob/main/docker-compose.yml) runs the core image on container port 8080, a private database, an uploads volume, and a separate cron container. This candidate pins the catalog's `version-6.7.2` core image, uses the [documented PostgreSQL alternative](https://github.com/firefly-iii/docker/blob/main/database.env), and retains the app and database in one private Compose project. It does **not** claim to run the upstream cron container.
- The [upstream environment example](https://github.com/firefly-iii/firefly-iii/blob/main/.env.example) documents `APP_KEY_FILE`, `DB_PASSWORD_FILE` (via the `*_FILE` database variables), `STATIC_CRON_TOKEN_FILE`, `DB_CONNECTION=pgsql`, `APP_URL`, and `TZ`. The app key is a generated 32-character alphanumeric secret, not a base64-prefixed Laravel key. The cron token is exactly 32 characters. The PostgreSQL password is shared only between the app's file input and PostgreSQL's `POSTGRES_PASSWORD_FILE`.
- The [PostgreSQL image](https://hub.docker.com/_/postgres) supports `POSTGRES_PASSWORD_FILE`; its 18-series volume path is `/var/lib/postgresql`. The database has no host-published port. The app defaults to `127.0.0.1:8080`; `APP_URL` derives from that exact local origin. A different user-facing URL would require a separately reviewed ingress and matching app URL.
- The [multi-user documentation](https://github.com/firefly-iii/docs/blob/main/docs/docs/how-to/firefly-iii/features/multi-user.md) says the first registered user becomes owner and registration closes by default afterwards. The [versioned web routes](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/routes/web.php) expose registration and login as web-session actions, while personal access tokens are created behind full authentication at `/oauth/personal-access-tokens`. These sources do not establish a safe unauthenticated first-admin API or a direct API-key bootstrap. The generated admin password is reserved for a supervised first registration, with a real owner email supplied then; `admin` in the recipe is a handoff label, not a promised Firefly login identity.

## Remaining gates

The recipe is a validated *candidate* only. No `setup.ts` is installed, so shared setup must report first owner, credential verification, API token, and application acceptance as pending. Do not mark it ready from container liveness or HTTP 200. Complete private first registration and login, optional one-time token handoff, a finance-record readback, isolated backup restore, and restart persistence before claiming acceptance. Schedule and verify the upstream cron endpoint separately with the generated token; the recipe does not automate it. No Docker or live application check was run for this research.

The [version-pinned route table](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/routes/web.php) confirms `GET`/`POST /register`, `GET`/`POST /login`, and `POST /oauth/personal-access-tokens` behind `user-full-auth`; it does not establish a stable CSRF/session response contract or a safe replay rule after a lost registration response. A first-owner POST that succeeded while its response was lost could not safely be distinguished from an unrelated owner without independently proving login and identity. Token creation has a similar one-time-value loss boundary. Keep both actions supervised until those exact response, identity, and replay semantics are version-verified; do not infer readiness from the route names alone.

The [upstream registration controller](https://github.com/firefly-iii/firefly-iii/blob/main/app/Http/Controllers/Auth/RegisterController.php) accepts an email, password, and password confirmation through the web guard and logs in the newly registered user. The [users API route](https://github.com/firefly-iii/firefly-iii/blob/main/routes/api.php) is admin-authenticated, so it cannot bootstrap an empty instance. The [OAuth controller](https://github.com/firefly-iii/firefly-iii/blob/main/app/Http/Controllers/Profile/OAuthController.php) creates a personal access token for the authenticated user, not for an unauthenticated installer. These controller checks were available on upstream `main`, **not independently verified at the pinned v6.7.2 tag** in this pass; the versioned route table remains the pinned evidence. No documented password-on-stdin/container command or unauthenticated API route was found. Therefore the current shared transport may technically submit web-form requests, but a source-proven, replay-safe first-owner-and-token adapter cannot be supplied from this evidence. No `setup.ts` is added; the exact gap is the pinned web-session/CSRF contract, independent owner identity readback after an ambiguous registration response, and recoverable capture of the token's one-time value.
