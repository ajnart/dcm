# Umami private shared-Compose candidate (2026-09-29)

Decision: publish a private v2 two-service recipe and source-level seeded-admin-rotation adapter. Keep automation at guided support: neither live deployment nor tracker/restart acceptance has been proven. The exact loopback origin is the only published endpoint during setup; broader exposure must wait for verified rotation and separate approval.

The [official Compose example](https://github.com/umami-software/umami/blob/master/docker-compose.yml) uses an Umami service, PostgreSQL 15 Alpine, `DATABASE_URL`, `APP_SECRET`, and `TWO_FACTOR_ENCRYPTION_KEY`; it waits for PostgreSQL health and exposes port 3000. [Installation](https://docs.umami.is/docs/install) requires a PostgreSQL connection URL and documents the seeded `admin` / `umami` login. [Environment variables](https://docs.umami.is/docs/environment-variables) document the application secret and 2FA key. The [2FA guide](https://docs.umami.is/docs/two-factor-authentication) requires a unique 64-character hexadecimal key.

The [v3.4.0 release](https://github.com/umami-software/umami/releases/tag/v3.4.0) is the versioned image candidate; a platform-specific digest still needs verification at apply time. The published Compose example's fixed credentials are illustrative, not safe automation defaults.

The v2 `secretEnvironment` `postgres-url` binding constructs `DATABASE_URL` from a generated private password and uses the same private file as PostgreSQL's `POSTGRES_PASSWORD_FILE`. Separate generated bindings cover `APP_SECRET` and the hex 2FA key. The published recipe never copies the illustrative upstream Compose credentials, keeps PostgreSQL unpublished, and binds the web port to `127.0.0.1` by default.

The [login API](https://docs.umami.is/docs/api/authentication) exchanges username/password for a token and returns the authenticated user's ID and admin role. The [update-user API](https://docs.umami.is/docs/api-reference/update-user) changes that exact user's password with an authorized `POST /api/users/{userId}`. The adapter proves the seeded `admin` identity, rejects a generated-password login before any rotation, and checkpoints the exact ID before the one-time update. On a lost response it only retries login with the saved generated password, never repeats the update. It then verifies the same ID under the new credential and rejects a fresh login with the seed. A pre-existing modified admin fails closed. The [authentication guide](https://docs.umami.is/docs/api/authentication) documents API-key creation and its one-time display, but this adapter does not create a key.

The [login guide](https://docs.umami.is/docs/login) also documents manual password change as a fallback. Source-level adapter checks and catalog validation are narrower than a live fresh-instance result.

Before promoting support, prove fresh-instance and lost-response behavior against the pinned image, then verify tracker collection and restart persistence. API-key provisioning is a separate optional contract.
