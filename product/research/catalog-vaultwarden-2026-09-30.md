# Vaultwarden shared-recipe reassessment — 2026-09-30

Decision: retain guided support. Do not add `recipe.json` or `setup.ts` yet. The requested host-only Caddy HTTPS route and deterministic first-account lifecycle cannot be represented safely by the current shared recipe/setup contracts without choosing an unconfirmed hostname, client DNS path, and certificate-trust model. No LAN IP or client DNS capability was supplied; loopback reachability on the host does not prove the intended clients can resolve or trust a private HTTPS origin.

Pinned upstream reference: [Vaultwarden 1.37.3 release](https://github.com/dani-garcia/vaultwarden/releases/tag/1.37.3), [1.37.3 configuration template](https://github.com/dani-garcia/vaultwarden/blob/1.37.3/.env.template), [1.37.3 registration handler](https://github.com/dani-garcia/vaultwarden/blob/1.37.3/src/api/core/accounts.rs), and [1.37.3 identity/login routes](https://github.com/dani-garcia/vaultwarden/blob/1.37.3/src/api/identity.rs). The template requires `DOMAIN` to match the real access address and recommends HTTPS behind a reverse proxy; it defaults `SIGNUPS_ALLOWED=true`, while a nonempty `SIGNUPS_DOMAINS_WHITELIST` overrides a false signup flag. This is not a safe static default for a password vault.

The local [recipe schema](../../.agents/skills/self-host/workflows/selfhost/references/catalog/schemas/compose-recipe.schema.json) permits static generated files and a `local-origin` derived environment, but has no approved parameter for a private hostname, certificate identity/trust, or route reachability proof. The existing Caddy recipe serves only loopback HTTP readiness, not a TLS proxy. The [setup contract](../../.agents/skills/self-host/workflows/selfhost/references/catalog/types/setup.ts) restricts adapter HTTP to the exact saved loopback origin; it cannot inspect the client-facing HTTPS certificate or prove that signup/login used it. A Vaultwarden adapter on that transport would bypass the security property it needs to establish.

The missing primitive is an ingress-owned, approval-bound private HTTPS origin: select and verify a hostname and resolution path for each intended client, issue or import a certificate trusted by those clients, render the Caddy route and matching `DOMAIN` in the exact Compose owner, and verify the route/certificate before account data crosses it. Setup then needs a pinned client-compatible registration/login path with a private password boundary and a write-ahead checkpoint. It must close registration immediately after first-account proof, read back the effective setting (including whitelist and persisted `config.json` overrides), and reject a second signup. Account creation through `/admin` is not an equivalent shortcut: `ADMIN_TOKEN` controls server administration, not vault ownership.

Even after this gate, login is not vault acceptance. A vault-item round-trip, client compatibility, export, restart persistence, and isolated restore of database, attachments, and key material remain separately required. No live TLS, account, client, or recovery test was performed. The 2026-09-29 guided-support assessment remains in force.
