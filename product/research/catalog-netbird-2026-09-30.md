# NetBird catalog boundary — 2026-09-30

Decision: retain **guided** support. Do not publish a shared `recipe.json` or `setup.ts` yet. The current catalog cannot express a complete, safe NetBird deployment, although upstream now documents headless first-owner creation.

## Official deployment and identity

The [current quickstart](https://docs.netbird.io/selfhosted/selfhosted-quickstart) requires a public domain resolving to a Linux VM, inbound TCP 80/443 and UDP 3478, Docker Compose, and at least 1 CPU/2 GiB. Its installer generates `docker-compose.yml`, `config.yaml`, and `dashboard.env`. The default topology is `netbird-server` (management, signal, relay, and STUN), `dashboard`, and Traefik for ACME/TLS. The [configuration reference](https://docs.netbird.io/selfhosted/maintenance/configuration-files) describes `netbirdio/netbird-server`, `netbirdio/dashboard`, and `traefik:v3.6`; the server persists `/var/lib/netbird`. With an external proxy, dashboard and server HTTP listeners may bind loopback, but UDP 3478 remains externally reachable and the proxy must route API, OAuth, relay/WebSocket, and gRPC/h2c paths correctly. The quickstart's embedded Dex manages local users; an external IdP is optional, not a required dependency. The older [advanced guide](https://docs.netbird.io/selfhosted/selfhosted-guide) covers separate management/signal/relay/coturn containers and is not the new-install topology.

The [automated setup API](https://docs.netbird.io/selfhosted/automated-setup) accepts `POST /api/setup` with owner email, name, and password while no owner exists. `NB_SETUP_PAT_ENABLED=true` additionally permits a one-time returned PAT via `create_pat: true`; it is disabled by default and the unauthenticated setup endpoint must only be exposed during controlled bootstrap. The response must never be logged. After setup, the endpoint cannot recreate the owner or recover a lost PAT. A future adapter must checkpoint before the first write, verify an existing owner through authenticated API access on resume, and halt for reconciliation if the create response or credential provenance is lost. A PAT is optional for owner creation, but subsequent API automation requires one.

## Why no shared recipe yet

The official installer renders domain-dependent external URL, OIDC issuer/redirects, dashboard endpoint, proxy routing, and generated relay/datastore/session secrets into configuration. The shared v2 recipe can mount only fixed `configFiles` and derive limited environment values from a local loopback origin. It cannot render a reviewed public domain plus generated private values into a secret-bearing `config.yaml`, nor own the existing proxy's h2c/path routing or the public DNS/TLS/80/443/UDP-3478 approval. A fixed sample domain, loopback-only URL, or default Traefik with Docker socket/public ports would violate the current private-by-default and privilege boundaries. Choosing a pinned image tag alone does not close these gaps. No recipe or adapter was added; neither exists in this app folder.

To promote this app, add a typed, approval-bound configuration renderer with secret-safe mode-0600 output and exact resume checks, an explicit ingress contract for the selected domain and routes, a reviewed UDP port descriptor, and a pinned combined-server/dashboard topology. Keep proxy ownership separate and never silently adopt another project's port, DNS, certificate, or Docker socket. Then implement first-owner setup against the documented API, with bounded lost-response handling and credential-safe handoff.

Acceptance must separately prove trusted HTTPS and correct proxy routing, first-owner login/API readback, enrollment of an approved client, peer-to-peer or relay connectivity, the exact user-selected remote service/route, backup restore, and restart persistence. Do not invent a LAN/subnet route or treat a Compose start, HTTP 200, or first-account response as remote-access acceptance.
