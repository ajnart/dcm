# Homarr shared-owner first-run assessment (2026-09-29)

Decision: keep `sharedOwner: false` in `catalog/apps/homarr/setup.ts` until the direct shared-owner route passes isolated live acceptance. The transport exposes bounded multi-cookie responses. The adapter ports the standalone cookie session, checkpointed first administrator and setup writes, one-time API-key capture, isolated key verification, and private `personal` board API readback. A completed welcome step may resume at `user`, and a resumed `start`/`user` session refreshes its onboarding claim. These corrections are source-reviewed but have not passed fresh-container, replay, or restart checks.

The standalone implementation in `packages/cli/src/lib/homarr-onboarding-api.ts` uses a private cookie jar across `/api/onboarding/claim`, the credentials CSRF/callback/session endpoints, and tRPC onboarding/key procedures. It persists an attempted checkpoint before the one-time admin, setup, and key writes, saves the one-time key before another request, and verifies the key with an isolated `ApiKey` request. The shared interface provides approval-bound HTTP writes, pre-send checkpoints, and app-scoped password/key storage, so those parts can be ported without calling the standalone CLI.

The shared `SetupHttpResponse` now exposes `headers.getSetCookie?.()` for bounded multi-cookie responses. A port must maintain a private cookie jar for the credentials CSRF/callback/session exchange and authenticated tRPC calls. It must derive the callback URL from the exact `status.url` (validated by the transport against its saved loopback port), not hard-code port 7575. An attempted checkpoint must precede each one-time mutation, and a returned one-time key must be written through `context.secrets.writeApiKey` before any further request. The app must not become shared-ready on source inspection alone.

The moving `ghcr.io/homarr-labs/homarr-test:v2` image remains the selected recipe/manifest image. The [official v2 after-installation guide](https://v2.preview.homarr.dev/docs/getting-started/after-the-installation/) documents the first administrator/board flow and persisted `/appdata`, but does not promise these internal HTTP routes as a stable public API. Official Homarr source at local commit `dab5d36f7566a839378ecf5b2f8554f0c0987908` confirms `/api/onboarding/claim` issues the private cookie, `onboard.nextStep` requires the claim, `onboard.completeSetup` writes the board, `apiKeys.create` returns the one-time key, and `board.getAllBoards`/`board.getBoardByName` permit a private-board readback. This source commit is not a pin of the moving container image; the exact running image still needs an isolated live check before enabling shared setup. The shared HTTP transport now supports a bounded, approval-fingerprinted timeout of up to 120 seconds, and the shared Homarr adapter requests that limit only for `completeSetup`, matching the standalone route. This removes the known timeout mismatch but does not prove live compatibility.

Next boundary: independently review the port, then verify fresh setup, paused-session replay (including a renewed onboarding claim), private key readback, and restart in the exact shared Compose owner. Until then, shared setup must report Homarr pending, while standalone onboarding remains separate.
