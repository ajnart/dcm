# Tdarr shared setup boundary — 2026-09-30

Status: blocked for deterministic first-admin setup; no recipe or adapter added.

The [official Docker/Compose guide](https://docs.tdarr.io/docs/installation/docker/run-compose/) describes the upstream `ghcr.io/haveagitgat/tdarr` server image, `/app/server`, `/app/configs`, and `/app/logs` persistence, and web/API ports 8265 and 8266. It says `internalNode=false` disables the node in the server container. A future shared recipe can keep both ports private and omit media and cache mounts, device grants, and any worker; starting a worker or a library would exceed this scope. The guide itself uses a floating image, while the catalog currently records `2.85.01`; the first-run behavior of that exact image remains unverified here.

The [official authentication guide](https://docs.tdarr.io/docs/other/authentication/) says `auth=true` enables authentication but first startup prompts for username and password in the web UI. It documents `seededApiKey` for automatic node/API-key creation. The [variable reference](https://docs.tdarr.io/docs/installation/variables/) requires that key to begin `tapi_`, be at least 14 characters, and contain only alphanumerics and underscores. Seeding a key is not administrator creation or proof of account ownership. The [API guide](https://docs.tdarr.io/docs/api/) directs users of current versions to API Docs in the running web UI; it does not publish a first-user registration, login, or account-readback contract.

The official Compose example uses `auth=false`; it is not a secure shared-network default. An unauthenticated `no-account` recipe would allow peer containers to reach Tdarr even with loopback-only host publication. A complete recipe would need a matched, digest-pinned server image and keep both listeners private. It would need to prove registration closure and restart persistence. Workers and libraries must remain absent until the owner selects exact media paths, tests on copies, and has recoverable originals: the [transcode-cache guidance](https://docs.tdarr.io/docs/library-setup/transcode-cache/) describes replacing source files with completed output. GPU and device grants require separate approval.

The shared recipe schema can represent a manual first administrator and a private generated password, but doing so without a source-pinned first-user endpoint and replay/readback contract would leave setup pending, not deterministic. In particular, a retry after a lost registration response must distinguish an administrator created by this run from a pre-existing or competing account before submitting another password or declaring success. No such proof is established by these official pages. A future adapter needs a verified `2.85.01` registration/login contract, a checkpoint before the first write, authenticated readback using the generated password, and fail-closed handling of an unknown existing account. The current shared setup transport also targets the saved web-UI loopback origin; it must not silently treat port 8266 as the same authority.

No Docker pull, deployment, browser registration, media processing, or tests were performed. This note does not promote Tdarr from guided support or claim that interactive deployment is impossible.
