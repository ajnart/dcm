# PeaNUT catalog decision — 2026-09-29

The [upstream README](https://github.com/Brandawg93/PeaNUT#readme) documents the `brandawg93/peanut` image, `/config` persistence, port 8080, and `WEB_USERNAME`/`WEB_PASSWORD` first-run account creation. The [v6.0.0 release](https://github.com/Brandawg93/PeaNUT/releases/tag/v6.0.0) says authentication is on by default, bootstrap credentials are used only before an account exists, and the bcrypt account record persists in `/config/auth.yaml`. The container normally writes `/config` as UID/GID 1000:1000; `PUID`/`PGID` are not supported. The README documents authenticated `GET /api/v1/info` and `GET /api/v1/devices`, but also UPS-command endpoints. A private bind and monitoring-only NUT permissions are therefore important.

No v2 recipe or headless `setup.ts` is published in this change. A generated PeaNUT admin account alone would leave an empty dashboard: the app needs an owner-selected, reachable NUT server and a real UPS with a known device identifier. The catalog has neither those facts nor a source-backed, bounded input/configuration contract for them. The [NUT manual](https://networkupstools.org/docs/user-manual.chunked/index.html) treats server, driver, user privileges, and network access as separate configuration boundaries. Fabricating a server, UPS, or control credential would make a Compose-start observation look like monitoring acceptance.

To promote this to a shared recipe, first model explicit owner-supplied NUT endpoint/device choices and a safe read-only connection path, then pin and verify the image and implement a read-before-write setup that authenticates the generated admin and proves the selected UPS appears through the private API. The generated password would need the shared private-file-to-environment bridge, with the usual Docker-inspection visibility warning. Direct UPS status, restart persistence, and shutdown/failover behavior remain distinct acceptance gates. No live deployment or hardware test was performed.
