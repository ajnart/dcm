# BookStack catalog decision — 2026-09-29

Decision: keep BookStack at discovery support; do not add a shared Compose recipe or headless adapter yet. A loopback port alone would still leave the publicly known administrator active for any local client or private route until a separate rotation step succeeds.

The LinuxServer [image guide](https://github.com/linuxserver/docker-bookstack/blob/master/README.md) documents its Compose service on container port 80, persistent `/config`, MariaDB dependency, `APP_URL`, `APP_KEY`, database settings, and `FILE__` environment-file inputs. It explicitly lists the initial login as `admin@admin.com` / `password`. BookStack's [security guide](https://www.bookstackapp.com/docs/admin/security/) requires a preserved 32-byte application key; the LinuxServer image guide calls for its `base64:` key form.

BookStack [commands](https://www.bookstackapp.com/docs/admin/commands/) document `php artisan bookstack:create-admin --initial`: it updates the default administrator if present, creates one if no administrator exists, and exits with code 2 rather than replacing an existing non-default administrator. `--generate-password` returns the generated password on stdout. Shared setup now has exact-owner container exec with private stdin and bounded stdout, but a lost response can leave a changed password without a saved credential. `--password=...` puts a saved secret in process arguments. The documentation does not establish password-from-stdin or password-file input, nor a safe replay after lost stdout. Adding the recipe first would permit starting a reachable instance with the default login. A future route must checkpoint before this command, save a generated password only in owner-only handoff storage, verify login, and fail closed on exit 2 or ambiguous replay.

The [BookStack API](https://www.bookstackapp.com/docs/admin/hacking-bookstack/) is documented from a running instance at `/api/docs`. [BookStack's API announcement](https://www.bookstackapp.com/blog/beta-release-v0-28-0/) says a user with “Access system API” permission creates a named, expiring token in their profile; the token ID and secret are shown once and requests inherit that user's permissions. This is not an initial-admin bootstrap route or evidence of a safe unattended token-creation endpoint. API-token setup therefore remains a separate authenticated handoff/acceptance step.

No image version/digest was selected and no live instance, Docker run, login, token, restart, or backup restore was tested. The [LinuxServer package listing](https://github.com/linuxserver/docker-bookstack/pkgs/container/bookstack/versions) exposes version tags but is not sufficient evidence that a selected digest is current with [upstream BookStack releases](https://github.com/BookStackApp/BookStack/releases); verify both before pinning. A future recipe needs a verified image pin and MariaDB version, private origin/APP_URL agreement, secret-file bindings, exact-owner bootstrap, and independent acceptance for login, content round-trip, persistence, and database-plus-uploads restore.
