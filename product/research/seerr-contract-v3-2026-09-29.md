# Seerr v3.5.0 per-app setup contract

- Checked: 2026-09-29
- Scope: source-level contract review of Seerr's catalog manifest, the canonical media Compose service and bootstrap script, and the CLI per-app setup interface.
- Status: suitable API routes exist, but the current per-app setup context is insufficient for a safe Seerr adapter without a narrow dependency/choice/secret input extension. No runtime, browser, Docker, or test validation was performed.

## Decision

Implement Seerr as a bounded `SetupAdapter` that owns only first-run authentication, connection setup, and a private API-key reference. Keep all HTTP mutations behind the setup engine's exact approval and checkpoint mechanisms; return only a non-secret verified checkpoint. Do not count HTTP readiness or `initialized: true` alone as setup acceptance.

The catalog pins `ghcr.io/seerr-team/seerr:v3.5.0`, while the canonical `docker-compose.yml` still runs `:latest`. A v3.5.0-specific adapter needs a matching version-pinned Seerr recipe (or a verified digest) before its route assumptions are deterministic. The existing Compose service has `init: true`, `TZ`, `/app/config`, port 5055, the public-settings healthcheck, and `unless-stopped`; upstream's Docker guide also documents `security_opt: no-new-privileges`, `cap_drop: [ALL]`, and writable config owned by UID/GID 1000. Preserve a private host binding in the catalog recipe rather than copying the harness's unqualified port mapping.

## Minimum adapter and context contract

Follow `SetupAdapter` in `.agents/skills/self-host/workflows/selfhost/references/catalog/types/setup.ts`: `appId: "seerr"`, `credentialCommand: "app handoff"`, `apiKey: "saved-by-onboarding"`, `firstRun`, `ready`, and preferably a read-only `inspect`. `ready` should mean only that the exact app project has a saved, rechecked first-run record; functional behavior and restart persistence remain separate acceptance claims, as the setup engine already states.

The current `SetupContext` does not carry the inputs Seerr needs. It has no resolved dependency identities, no owner-choice object, and no way to read credentials/API keys from another selected app. Its secret methods are app-local (`readAdminPassword`, app config XML key, and app API-key methods); its approval callback can approve an action but cannot collect its parameters. Before implementing Seerr, add the smallest typed input surface for:

- the resolved media-server provider and its internal/external endpoints;
- a private reference reader for that dependency's login credential and for selected Radarr/Sonarr API keys;
- explicit library IDs, Radarr/Sonarr profile and root-folder selections, external URLs, and the automatic-search choice.

The input must carry references/choices, not secret values in plans, status, or checkpoints. Resolve candidate profiles/root folders from each `/test` response, then require the chosen values in the approved plan; if no choice is available, defer rather than choosing silently. Persist only non-secret stage, IDs, and file paths/references in the checkpoint. Never persist passwords, API keys, cookies, or request bodies in checkpoint data or logs.

Seerr's manifest currently declares `capability:media-server`, `sonarr`, and `radarr`. The catalog expands the two app IDs but only reports the abstract capability; `runFirstRunSetups` receives app IDs and does not pass the resolved provider. Since this route contract is specifically Jellyfin, either resolve and pass an explicit Jellyfin choice for v1, or narrow v1 to a literal Jellyfin dependency. Do not treat the capability marker as if it selected Jellyfin. Sonarr and Radarr are direct required dependencies; if either is unavailable, defer. Keep Plex/Emby out of this v1 adapter unless their separate login/library routes are implemented and verified. A short Docker service name is valid only when Seerr and that dependency actually share a network; otherwise the setup plan must supply a reachable internal URL rather than assuming `radarr`, `sonarr`, or `jellyfin` resolve across Compose projects.

The setup engine already supplies useful safety boundaries: exact-project live status before HTTP, an exact saved loopback origin, GET/HEAD-only inspection, per-request approval for mutations, owner-only secret files, and `beforeSendCheckpoint` for one-time requests. Use distinct one-time action IDs for the two possible Jellyfin login requests. A received exact no-host error can advance the checkpoint and permit the separately approved hostful attempt; a timeout/ambiguous response must stay attempted and must not be replayed blindly.

## v3.5.0 request and readback sequence

All paths below are under `/api/v1`. Require JSON shape/status checks and safe error summaries; never include credentials or response bodies in progress text.

| Step | Request | Required contract |
| --- | --- | --- |
| State | `GET /settings/public` | Public, read-only. Require a boolean `initialized`; it is a routing signal, not proof of a fresh database or a completed setup. |
| Login / resume | `POST /auth/jellyfin` | First send `{username, password, serverType: 2}` (`2` is the current harness's Jellyfin enum value) with no `hostname`; `email` is optional and, if supplied, must be owner-selected. Require 200, a user response, and capture `connect.sid` only in memory. If and only if the response is HTTP 500 with JSON `error: "No hostname provided."`, make one separately approved retry with owner-approved `{hostname, port, urlBase, useSsl}` fields. v3.5.0 rejects a supplied hostname when one is already saved (`"Jellyfin hostname already configured"`), so do not retry arbitrary 4xx/5xx or change a saved endpoint. |
| Admin key | `GET /settings/main` with the session cookie | Require a non-empty `apiKey`; v3.5.0 omits it for non-admin users. Save the returned key with `context.secrets.writeApiKey`, retain only its private path, and never call `POST /settings/main/regenerate` to obtain it: that route rotates the key. The official docs also specify that `API_KEY` can override the generated key; if the recipe uses that override, it must be backed by the same owner-only secret reference. |
| Jellyfin endpoint | `GET /settings/jellyfin` | After login, validate the actual saved internal host/port/TLS/base path. For this Compose graph, require the selected dependency's reachable internal URL (for example `jellyfin:8096`) and reject conflicts rather than overwrite them. An external/browser URL is a separate owner choice; only if supplied, update `POST /settings/jellyfin` with `{externalHostname}` and GET it back. |
| Libraries | `POST /settings/jellyfin/library/sync`; then optional `PUT /settings/jellyfin/library/{libraryId}` with `{enabled:true}`; then `GET /settings/jellyfin/library` | Sync returns the library array and preserves existing enabled flags. Enable only exact owner-selected IDs, verify each selected ID is enabled after readback, and do not disable unrelated libraries. v3.5.0 removed the old GET `?sync`/`?enable` behavior; use the POST sync and per-ID PUT routes. |
| Arr service check | `GET /settings/radarr` and `/settings/sonarr`; `POST /settings/{radarr|sonarr}/test` | Read current instances first. For a new/test connection use `{hostname, port, apiKey, useSsl, baseUrl}` from the resolved dependency and private key reference. Select a returned profile and root folder only from the explicit plan. Use Compose DNS/service routing only when the services share a network, not `localhost`; public/browser URLs remain separate. |
| Arr save/readback | `POST /settings/{radarr|sonarr}` for create; `PUT /settings/{radarr|sonarr}/{id}` for update; GET the matching settings collection | Create returns 201 and update returns 200. Payload must include the chosen `name`, endpoint/API-key fields, `activeProfileId`/`activeProfileName`, `activeDirectory`, `is4k`, and `isDefault`; Radarr additionally requires `minimumAvailability`, while Sonarr requires `enableSeasonFolders` and may need its anime profile/directory fields. Preserve compatible existing instances rather than duplicating or overwriting them. Keep `preventSearch`/automatic-search behavior an explicit owner choice. |
| Finalize | `POST /settings/initialize` | Call once, last, only after endpoint, selected libraries, Arr writes, and GET readbacks pass. Require HTTP 200 and a final `GET /settings/public` with `initialized: true`. |

The source says first-user admin creation requires no existing Seerr users and a Jellyfin account with administrator privileges. Thus a successful HTTP login is not enough: require `/settings/main` to return the admin API key and stop if it does not. The tagged auth route saves the initial Jellyfin host and token during successful first-admin authentication, which is why a no-host-first retry can resume a partially completed host setup without resending or overwriting the host.

## Resume and acceptance rules

1. On every run, read exact-project status and public settings first. If initialized, inspect the saved key and current settings; do not replay first-run mutations just because a checkpoint is missing.
2. On an uninitialized setup, try Jellyfin login without host fields. The exact `No hostname provided.` response is returned before the route's authentication/configuration work; record that observed state, then ask approval for the one hostful retry. Any other error is terminal for that run.
3. After successful login, use the captured session cookie to obtain the initial API key, persist it privately, then use the saved key for later reads if desired. A 403 from API-key preflight is ambiguous: middleware both rejects a bad key and resolves a correct key against Seerr user ID 1, which does not exist until first-user creation. Never interpret that 403 as proof of a pristine install.
4. For any write with ambiguous transport outcome, retain its one-time attempted checkpoint and inspect; do not blindly repeat. `inspect` is read-only by type, so if the login response was lost before the key was saved, report `needs-inspection` rather than fabricating completion.
5. Return an adapter checkpoint with stage, exact project identity, selected non-secret IDs, and API-key file reference only. Handoff shows the path by default; display the secret value only through the user's deliberate `app handoff --show` request. Container health, route HTTP 200, setup-ready, API functionality, and restart persistence are separate claims.
