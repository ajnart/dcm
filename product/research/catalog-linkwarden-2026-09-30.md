# Linkwarden first-run boundary (2026-09-30)

The pinned catalog image is `ghcr.io/linkwarden/linkwarden:v2.16.3`. Its existing recipe prepares the private app, PostgreSQL, and Meilisearch, but has no deterministic first-run adapter. Do not interpret a running container as a configured account.

Official documentation establishes these routes, but its rendered API pages do not expose request/response fields:

- [`POST /api/v1/users`](https://docs.linkwarden.app/api/create-user) registers a user. The page does not show the required username, email, and password body, first-user authorization behavior, or returned identity.
- [`POST /api/v1/session`](https://docs.linkwarden.app/api/create-a-new-session) creates a session. Its page does not show request fields, response token/cookie form, or the unverified-email behavior beyond a 401 description.
- [`POST /api/v1/tokens`](https://docs.linkwarden.app/api/create-token) creates a named expiring token. Its page does not show the body or one-time token response. [`GET /api/v1/tokens`](https://docs.linkwarden.app/api/get-tokens) lists authenticated user's tokens, but does not establish recovery of a lost token secret.
- [`GET /api/v1/users/me`](https://docs.linkwarden.app/api/get-current-user) is the authenticated identity route. The [API introduction](https://docs.linkwarden.app/api/api-introduction) describes bearer JWT authentication.
- [Environment variables](https://docs.linkwarden.app/self-hosting/environment-variables) document `NEXT_PUBLIC_DISABLE_REGISTRATION=true`, default `false`, and the `/api/v1/auth` suffix on `NEXTAUTH_URL`. Registration closure is a deployment configuration change, not a proven runtime API operation. The docs do not establish that setting it after first-user creation works without a build/restart, nor whether it closes the API route in v2.16.3.

The account write is one-time from the adapter's perspective. A safe implementation needs the pinned v2.16.3 route/schema source and a bounded replay plan: persist an attempted checkpoint before posting, then verify the saved password through a documented session exchange and identity read. Token creation additionally requires saving its raw one-time value before any subsequent call; if the write succeeds but the response is lost, do not blindly create another token. A separate, proven registration-closure route is required before reporting private first-run ready.

The official v2.16.3 tag (`474dd11632b32db30cde52460b2711ecadb1886e`) was subsequently inspected directly. [`PostUserSchema`](https://github.com/linkwarden/linkwarden/blob/v2.16.3/packages/lib/schemaValidation.ts) requires a 3–50-character lowercase username and an 8–2048-character password when mail is absent; the recipe does not configure mail. [`POST /api/v1/users`](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/lib/api/controllers/users/postUser.ts) returns the created user under `response` with status 201. [`PostSessionSchema`](https://github.com/linkwarden/linkwarden/blob/v2.16.3/packages/lib/schemaValidation.ts) requires username and password; the [session controller](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/lib/api/controllers/session/createSession.ts) returns `response.token` with status 200. Token creation requires `{name, expires}` where `expires` is the numeric `TokenExpiry` enum (0–4), and the [controller](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/lib/api/controllers/tokens/postToken.ts) returns the one-time `response.secretKey`. [`GET /api/v1/users/me`](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/pages/api/v1/users/me.ts) accepts bearer authentication and returns the account under `response`.

The closure blocker remains: the pinned [`postUser`](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/lib/api/controllers/users/postUser.ts) rejects unauthenticated signup when `NEXT_PUBLIC_DISABLE_REGISTRATION=true`, with no first-user exception. With that variable absent, unauthenticated signup remains open after owner creation. The current shared `SetupContext` cannot change the owned Compose environment and restart the app under a separate approval, so a headless adapter in this app folder alone cannot establish a private, registration-closed first run. An adapter must not mark this app ready on account and token readback alone. No `setup.ts` was added; the recipe remains a deployment candidate, not a configured shared setup or accepted archive service. No live instance was exercised.
