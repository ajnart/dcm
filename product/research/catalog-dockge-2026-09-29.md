# Dockge catalog review — 2026-09-29

## Upstream contract

- The [official Compose example](https://github.com/louislam/dockge/blob/master/compose.yaml) uses `louislam/dockge:1`, port 5001, persistent `/app/data`, a bind-mounted `/var/run/docker.sock`, and a writable stacks directory. Its `DOCKGE_STACKS_DIR` must be an absolute path whose host and container bind paths are identical. The [README](https://github.com/louislam/dockge/blob/master/README.md) describes `/opt/stacks` as the default and says new/imported projects live beneath it. The image tag `:1` is a moving major tag, not a fixed release/digest.
- The upstream [installation guide](https://github.com/louislam/dockge/blob/master/README.md#how-to-install) leads to a browser at port 5001. An upstream [first-run report](https://github.com/louislam/dockge/discussions/525) shows the empty-database setup page asking for username and password. That report is not a supported headless setup API contract. An upstream [API discussion](https://github.com/louislam/dockge/discussions/161) describes the lack of an API; no documented stable first-admin/API-key route was found in the official installation material. Do not infer one from internal Socket.IO events.
- Current [server source](https://github.com/louislam/dockge/blob/master/backend/dockge-server.ts) emits a Socket.IO `setup` event when the user table is empty. The [socket handler](https://github.com/louislam/dockge/blob/master/backend/socket-handlers/main-socket-handler.ts) accepts `setup(username, password, callback)`, rejects weak passwords or an existing user, and exposes `login({ username, password }, callback)` for verification. These internal routes are source evidence, not a documented stable HTTP API; the shared HTTP adapter cannot use them as-is.
- [Docker's daemon security guidance](https://docs.docker.com/engine/security/) explains that a web service able to instruct Docker can create arbitrary containers and mount host paths. [Daemon-socket guidance](https://docs.docker.com/engine/security/protect-access/) treats Docker API credentials as root-equivalent. A loopback UI bind does not narrow the daemon permissions granted by a socket mount.

## Catalog decision

Keep `dockge` at discovery support. Refresh only its source-backed image and lifecycle facts; add no `recipe.json` or `setup.ts`. A generic shared recipe would either omit the daemon and be a nonfunctional Compose manager, or mount the host socket and silently grant host-wide control. The required writable stacks bind could also let Dockge change Compose files outside this product's one-owned-project mutation boundary. The existing private port, mount, and account primitives cannot express a reviewed, restricted Docker API authority, an exact owned stacks tree, and an independent privilege-expansion approval. A browser-created account or HTTP 200 would not prove safe management scope. Homarr remains a URL-tile possibility only, not a dedicated integration claim.

## Follow-up to make it installable

1. Design an explicit Docker authority owner and approval: exact daemon endpoint, its scope and isolation, credentials/socket lifecycle, and failure behavior. Do not silently configure a TCP daemon or use an unrestricted socket proxy as a cosmetic workaround.
2. Define an exact stacks-directory ownership and import policy. Dockge's required same-path bind needs to be confined to an operator-approved tree; pre-existing/unowned Compose projects must not be adopted or upgraded automatically.
3. Pin and verify one image version/digest, keep the UI private, and determine a documented, replay-safe first-admin path. If no supported headless path exists, keep onboarding manual and do not claim shared setup readiness. A Socket.IO implementation would need a checkpoint before first-account creation and saved-credential login verification.
4. Validate fresh install, account authentication, authorized-stack management, refusal of unowned stacks, restart persistence, and recovery on a disposable host. No Docker or live acceptance checks were run for this review.
