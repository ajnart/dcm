# BookStack catalog boundary — 2026-09-30

## Promotion review (2026-09-30)

Decision: **blocked**. Keep BookStack at discovery; do not publish a shared Compose recipe or headless setup adapter yet. This review checked the current [BookStack administrator command contract](https://www.bookstackapp.com/docs/admin/commands/) and [LinuxServer image contract](https://docs.linuxserver.io/images/docker-bookstack/) against the repository's v2 recipe schema and `SetupContext` interface. It did not run an image or test a fresh instance.

The image and database topology are documented, but the requested first-owner/password/API-key contract is not expressible safely here. `bookstack:create-admin --initial` can replace the seeded admin, but `--password` places the saved password in process arguments. `--generate-password` emits a new secret on stdout; `SetupContext.secrets` can write an API key but cannot replace the already-generated admin-password file. A crash between rotation and any hypothetical persistence makes replay indeterminate. The recipe schema's `seeded-admin-rotation` also fixes `username: "admin"`, while BookStack's seeded login is an email address. Neither `manual-first-email` nor the initial-email bootstrap kind describes a seeded-account rotation. The [official security guidance](https://www.bookstackapp.com/docs/admin/security/) requires replacing the known initial credentials before exposure.

API-key creation remains a separate unproven step. BookStack describes [authenticated API access](https://www.bookstackapp.com/docs/admin/hacking-bookstack/) and user-created tokens, but the reviewed sources do not establish a pinned, headless token-creation request with one-time-secret capture, replay behavior, and protected identity readback. Do not infer those from web forms or the existence of `/api/docs`.

Promotion needs an email-based seeded-rotation contract, a private password-input or atomic generated-password persistence path, and pinned source-backed login/token routes with ambiguous-retry handling. A focused fresh-instance acceptance run would then have to prove the saved owner login, rejection of the public seed, token readback, and restart persistence. No such run was performed.

## Official deployment facts

- LinuxServer's [BookStack image contract](https://github.com/linuxserver/docker-bookstack/blob/master/README.md) documents `APP_URL`, `APP_KEY`, `DB_HOST`, `DB_PORT`, `DB_USERNAME`, `DB_PASSWORD`, `DB_DATABASE`, a persistent `/config`, and container port 80. It requires MariaDB and seeds `admin@admin.com` / `password`. The BookStack image has a [versioned release](https://github.com/linuxserver/docker-bookstack/releases/tag/v26.05.3-ls277); the paired LinuxServer MariaDB image has a [versioned release](https://github.com/linuxserver/docker-mariadb/releases/tag/11.8.8-r0-ls226). These tags are candidates, not live image or fresh-install validation.
- [BookStack's command documentation](https://www.bookstackapp.com/docs/admin/commands/) says `bookstack:create-admin --initial` updates the default administrator if present, creates one only when none exists, and exits 2 when other users exist. `--generate-password` prints the generated password on stdout; `--password` places the chosen password in command arguments. [Security guidance](https://www.bookstackapp.com/docs/admin/security/) requires changing the initial email and password.
- BookStack uses an email identity, not the shared `seeded-admin-rotation` recipe's fixed `admin` username. The shared `manual-first-email` model can record an email but does not express that it is replacing a publicly seeded administrator.
- The [official install guide](https://www.bookstackapp.com/docs/admin/installation/) describes signing in with the seeded account and changing its details immediately. It does not document a direct-HTTP setup or rotation endpoint. BookStack's [API documentation entry point](https://www.bookstackapp.com/docs/admin/hacking-bookstack/) requires an existing authenticated user's token; it cannot bootstrap that token from the seeded account. Treating the web login and profile forms as a stable API would require a pinned request, CSRF/session, mutation, and role-readback contract that these sources do not provide.

## Why a recipe and adapter are not published yet

The shared setup interface does support exact-owner container exec, private stdin, bounded/redacted stdout, and a checkpoint before a one-time command. It only exposes `readAdminPassword()` for the pre-generated handoff password; it cannot atomically replace that private password with `--generate-password` stdout. A crash after BookStack changes the seeded account but before that stdout is saved makes a retry ambiguous and loses the credential. Passing the pre-generated password with `--password` would expose it in container process arguments, against the repository's private-command boundary. The existing recipe schema also cannot accurately label an email-based seeded rotation. Publishing a v2 recipe with a generated handoff password would imply that the password can authenticate when it cannot.

The safe next contract needs a source-backed, secret-safe password-input method or atomic generated-password capture and persistence, plus an email-based seeded-rotation onboarding kind. The adapter must inspect the initial state, checkpoint before mutation, prove the new email/password login, reject the public seed, and refuse ambiguous existing accounts. On retry, successful login with the intended credentials would be a useful observation, but a failed login does not establish whether the initial mutation never ran, changed only one field, or affected a different existing account. [BookStack's API-token guidance](https://www.bookstackapp.com/blog/beta-release-v0-28-0/) says users need the API permission, create named/expiring tokens in their profile, and see the token secret only once. The current UI is under [My Account > Access & Security](https://www.bookstackapp.com/blog/bookstack-release-v23-10/). No token-creation route or replay semantics were established here, so none is claimed. Keep the app at discovery and guide first setup manually on a private origin until those boundaries exist.
