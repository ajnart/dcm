# Headscale shared-Compose assessment — 2026-09-29

Decision: retain guided support; do **not** add `recipe.json` or `setup.ts` yet. The [v0.29.4 release](https://github.com/juanfont/headscale/releases/tag/v0.29.4) is current, but this pass did not verify a registry digest or run a container. A pinned image is only one part of a functional control plane.

The [official container page](https://headscale.net/stable/setup/install/container/) shows versioned images, a read-only `/etc/headscale/config.yaml` mount, persistent `/var/lib/headscale` for SQLite and key state, `serve`, and private example port mappings. It labels the page community-maintained and tells operators to edit a configuration matching the chosen image version. The [configuration guide](https://headscale.net/stable/ref/configuration/) likewise requires a version-matched YAML file; the [v0.29.4 example](https://raw.githubusercontent.com/juanfont/headscale/v0.29.4/config-example.yaml) includes `server_url`, listeners, SQLite path, DERP, DNS, and TLS choices. Its default `server_url` and listener are loopback examples, not a usable remote tailnet endpoint. The [requirements](https://headscale.net/stable/setup/requirements/) call for a public IP and HTTPS on port 443 for clients, with additional ports depending on selected features. DNS, TLS, public edge ownership, and config values must be reviewed together; a loopback `/health` response would prove only local server liveness.

The current shared v2 recipe can mount selected host paths and volumes but cannot render a reviewed, version-matched Headscale YAML configuration from exact domain, TLS/proxy, DERP, DNS, and storage choices before first start. Pointing `server_url` at a guessed public name or shipping the upstream loopback sample would misrepresent a working control plane. The public edge also requires a separate DNS/TLS/443 approval and an independent client-registration test. This is a distinct edge-control-plane route, not a routine private single-app recipe.

Headscale has no first web administrator to create. Its [API guidance](https://headscale.net/stable/ref/remote-cli/) documents `headscale apikeys create`, Bearer authentication, and that the generated key is shown only once; listing keys cannot recover it. Even an exact-owned container exec with private stdin would need an approved output-to-mode-0600 handoff and lost-output recovery policy before claiming deterministic API-key setup. Key creation is not node enrollment, and an API key should not be generated without a selected consumer. No key, node, or network change was made here. Acceptance would require the exact HTTPS client URL, authenticated API check if selected, actual node enrollment/mesh reachability, and protected state backup plus isolated restore.
