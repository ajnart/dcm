# Scrypted shared Compose assessment — 2026-09-29

Decision: keep Scrypted at discovery; do not add `recipe.json` or `setup.ts`. No image, container, first-admin login, camera stream, or restart was exercised.

The [current Linux Docker guide](https://docs.scrypted.app/install/linux-docker.html) directs operators to its installer script and default `ghcr.io/koush/scrypted` image, not a fixed version tag. The [official Compose source](https://raw.githubusercontent.com/koush/scrypted/main/install/docker/docker-compose.yml) uses `network_mode: host`, persists `/server/volume`, and defines a separate Watchtower service with `/var/run/docker.sock` plus update authority. The image variants and optional GPU/USB passthrough need host-specific choices. Scrypted's [installation guidance](https://docs.scrypted.app/installation.html) explicitly says Docker needs host networking and warns about collisions with other host-network services. Its Compose source notes that HomeKit mDNS on host networking may require disabling the host Avahi daemon; the alternate bridge mode requires an Avahi socket mount and AppArmor change. Those are not interchangeable private-bridge defaults.

The shared recipe/Compose boundary rejects host networking and Docker socket mounts, and it does not grant device or AppArmor privilege expansion. Its fixed image-tag and private published-port model cannot represent the upstream topology as-is. Omitting Watchtower or switching to bridge networking could be a separate, source-backed design, but is not a verified equivalent to the documented install. Do not run the upstream installer inside this app's apply boundary: it can install Docker, change a host service, and remove existing containers.

The [Docker installation guide](https://github.com/koush/scrypted/wiki/Installation:-Docker-Compose-Linux) points to `https://localhost:10443/` for interactive setup. [User guidance](https://docs.scrypted.app/maintenance/access.html) describes additional local users in the management console; it does not document a version-pinned headless first-admin/password or API-key creation route for the default container. The Home Assistant add-on's special `homeassistant` user is not evidence for the standalone Docker image. No generated administrator credential or API key should be handed off until the standalone route is verified.

Next boundary: identify a supported, immutable image release; design and separately approve exact host-network/mDNS, port, device, NVR storage, and update ownership; and verify a version-pinned first-admin/login procedure plus persistence and camera streaming on an isolated Linux host. Keep NVR license and hardware acceptance separate from basic server liveness.
