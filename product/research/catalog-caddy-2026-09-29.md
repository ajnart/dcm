# Caddy shared recipe review — 2026-09-29

The official Caddy image documents a Compose service with a mounted Caddyfile and persistent `/data` and `/config` volumes. The 2.11 image source sets `XDG_DATA_HOME=/data` and `XDG_CONFIG_HOME=/config`; it does not set a `USER`, so its default process can read the generated owner-only Caddyfile. Sources: [official image](https://hub.docker.com/_/caddy), [2.11 Dockerfile](https://github.com/caddyserver/caddy-docker/blob/master/2.11/alpine/Dockerfile).

The candidate pins `caddy:2.11.4`, mounts a reviewed Caddyfile, and publishes only container port 2015 to the selected loopback host port. `GET /health` returns an empty 200 using Caddy's documented [`respond` directive](https://caddyserver.com/docs/caddyfile/directives/respond); all other paths return 404. This is a readiness observation, not an ingress route. The Caddyfile disables the [admin API](https://caddyserver.com/docs/caddyfile/options#admin) so it cannot be reached from another container; configuration changes require an approved replacement/restart rather than `caddy reload`.

No public ports, DNS name, TLS certificate, upstream, Docker socket, or auth policy is selected. [Automatic HTTPS](https://caddyserver.com/docs/automatic-https) can add listeners and certificate work when a hostname is configured, so adding a real route must separately approve DNS/TLS/80/443/auth ownership and then verify the backend and restart persistence. The shared recipe does not automate that later ingress transition. Image pull, fresh-instance behavior, and restart persistence remain unverified without a live host.
