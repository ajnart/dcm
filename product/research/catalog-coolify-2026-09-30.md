# Coolify catalog boundary — 2026-09-30

Decision: retain discovery-only support. Do not add `recipe.json` or `setup.ts` yet. The official self-hosted flow installs a deployment control plane, not an isolated frontend container. Its installation owns multiple Compose files and host configuration; Coolify then reaches connected Docker servers over SSH. A recipe that starts only the dashboard would misrepresent a working installation.

The official [self-hosted guide](https://coolify.io/docs/start-with-self-hosted) uses the upstream installer and expects a running dashboard, first administrator, and saved installation secrets. The upstream [Compose guidance](https://github.com/coollabsio/coolify/discussions/3712) mounts `/var/run/docker.sock` and uses the base plus production Compose files and an environment file. This repository's bounded recipe contract does not model an explicit Docker socket/host-authority grant, the full upstream installer ownership, or safe adoption of its generated resources. Installing it inside an existing shared Compose project would cross that project's mutation boundary. A pinned image alone does not resolve those gaps.

Headless acceptance is also incomplete. The first administrator must be claimed on a fresh private instance and its login verified. [API tokens](https://coolify.io/docs/core/security/credentials/api-tokens) are created by an authenticated user after instance API access is enabled; a token is team-bound, permission-scoped, and secret. No reviewed, version-pinned first-admin and token creation adapter exists here, so `setup.ts` would be speculative. The [SSH key flow](https://coolify.io/docs/core/security/credentials/ssh-keys) requires generating a private key, authorizing its public key on the selected server account, and checking that connection. This is a separate host-authority approval, not a silent onboarding side effect.

Before any managed recipe: review an exact upstream version and its Compose/environment/secret contract; isolate or explicitly approve Docker socket authority and SSH account access; determine ownership of existing Docker networks, proxy, and ports; keep the dashboard private until first-admin verification; implement checkpointed admin and least-privilege API-token flow with private handoff; verify local-server SSH and a bounded deployment; test restart persistence and a rollback path. [Firewall guidance](https://coolify.io/docs/core/infrastructure/servers/firewall) names dashboard/realtime/terminal ports 8000/6001/6002 and proxy ports 80/443; public exposure needs its own DNS/TLS/ingress approval. [Instance backups](https://coolify.io/docs/core/backup-and-recovery/instance-backup) exclude application data and need the separately protected `APP_KEY`; recovery needs an isolated restore, including SSH key material when migrating.

No Docker installation, first-account flow, token creation, SSH authorization, backup restore, or live acceptance was attempted for this catalog review.
