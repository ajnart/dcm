## Scope and result

Nextcloud is not missing a headless first-run implementation, but its standalone command surface is incomplete. The experimental v2 recipe has bounded Compose apply; the [image docs](https://github.com/nextcloud/docker/blob/master/README.md) allow initial admin provisioning without the web wizard; and an existing first-run adapter checks the installed instance, authenticates the saved admin through [OCS](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/OCS/ocs-api-overview.html), and writes/reads a checkpointed [WebDAV](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html) probe. The full interactive recipe installer invokes this adapter. `app shared setup` can also run direct adapters for a completed shared-project owner. There is no standalone `app setup --id nextcloud` or `app login-check --id nextcloud` action after a direct `app plan/apply` sequence.

The exact image tag `35.0.1-apache` is listed in [Docker Official Images](https://github.com/docker-library/official-images/blob/master/library/nextcloud) with source commit `6edd06e23466ed44d48e3d467b09e0c5fc0ffc17`; the [version-specific Dockerfile](https://raw.githubusercontent.com/nextcloud/docker/6edd06e23466ed44d48e3d467b09e0c5fc0ffc17/35/apache/Dockerfile) sets Nextcloud to `35.0.1`. This establishes tag/source provenance, not registry bytes or a platform digest. The catalog correctly leaves `image.status` at `verify`; recipe maturity is experimental and acceptance remains per-project.
