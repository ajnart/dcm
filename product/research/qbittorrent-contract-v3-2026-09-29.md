# qBittorrent first-run contract v3 (2026-09-29)

- Checked at: `2026-09-29`
- Scope: local source + official upstream contract review only. No Docker, image pull, browser, API call, credential access, or runtime acceptance.
- Sources below are first-party qBittorrent, Hotio, and Docker documentation/source.

## Findings

1. **Pin the image contract consistently.** The qBittorrent catalog manifest pins `ghcr.io/hotio/qbittorrent:release-5.2.3`, while the canonical media Compose file uses mutable `:latest` ([manifest](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/qbittorrent/manifest.json#L19-L27), [Compose](../../docker-compose.yml#L45-L59)). This undermines a version-specific first-run contract. Keep the Compose reference aligned with the known manifest version; record/verify the resolved digest separately before claiming runtime provenance.

2. **Treat the WebUI port as one value end-to-end.** Compose currently sets `WEBUI_PORT`, `WEBUI_PORTS`, and the host/container published port from `QBITTORRENT_PORT`. Hotio's runner passes the numeric part of `WEBUI_PORTS` to `qbittorrent-nox --webui-port`; its docs say this variable also controls VPN firewall exposure ([runner source](https://github.com/hotio/qbittorrent/blob/release/root/etc/s6-overlay/s6-rc.d/service-qbittorrent/run#L268), [Hotio docs](https://hotio.dev/containers/qbittorrent/)). Do not publish the peer-listener port as part of WebUI setup. For the protected loopback default, set the host IP explicitly (`127.0.0.1:<host>:<container>`); Docker Compose binds a port without a host IP to all interfaces ([Compose ports reference](https://docs.docker.com/reference/compose-file/services/#ports)). Keep host, container, Hotio WebUI, and bootstrap target ports equal so qBittorrent's Host/Origin checks see the same authority.

3. **The current API identity flow is suitable for resume, with a log freshness gap.** `setup-qbittorrent.ts RUN_ID` is the narrow CLI entry point. It loads the same run, tries the managed username/password first, and only on login failure calls the temporary-password provider; after `app/setPreferences`, it logs in again with the managed identity ([setup wrapper](../../scripts/setup-qbittorrent.ts#L1-L3), [identity state machine](../../scripts/bootstrap-core.ts#L83-L204)). Preserve this ordering and resume the existing `RUN_ID`/`/config`; do not recreate the profile to recover a failed stage.

   The fallback currently reads the complete project log (`docker compose logs --no-color`) and takes the last English match for “temporary password is provided for this session” ([log helper](../../scripts/lib/session-context.ts#L1359-L1391), [parser/use](../../scripts/bootstrap-core.ts#L111-L121), [fetch loop](../../scripts/bootstrap-core.ts#L167-L189)). That can select an old startup line when a Compose project/profile is reused. Record a run-scoped qBittorrent service start watermark, then request only `docker compose logs --since <watermark> --timestamps --no-color qbittorrent`; Compose supports these filters ([Docker logs reference](https://docs.docker.com/reference/cli/docker/compose/logs/)). Allow this fallback only for an explicitly fresh profile with known start provenance. If login fails on a reused profile and freshness cannot be established, stop and preserve the existing failure/resume handoff rather than guessing. Keep the parsed password only in process memory: never print, persist, or attach raw service logs to ordinary evidence.

   Upstream 5.2.3 confirms a temporary random password is generated only when the stored WebUI password is empty and printed for that process; the default WebUI username is `admin` ([`application.cpp`](https://github.com/qbittorrent/qBittorrent/blob/release-5.2.3/src/app/application.cpp#L3772-L3823), [`preferences.cpp`](https://github.com/qbittorrent/qBittorrent/blob/release-5.2.3/src/base/preferences.cpp#L832-L855)). The source wraps the message in `tr()`, while the local parser matches English text; this assumes an English first-run locale or needs a locale-aware parser.

4. **Make login success mean a session cookie, then verify an authenticated read.** qBittorrent's official WebUI API specifies form fields `username`/`password`, cookie auth, `setPreferences`'s `json` field, and exact Origin/Referer host-and-port matching ([WebUI API 5.0](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-%28qBittorrent-5.0%29)). In 5.2.3, upstream names the cookie `QBT_SID_<webui-port>` and emits HTTP 204 for empty successful responses; the current code accepts 200/204 and matches `QBT_SID` with optional numeric suffix ([cookie-name source](https://github.com/qbittorrent/qBittorrent/blob/release-5.2.3/src/webui/webapplication.cpp#L71-L79), [port suffix](https://github.com/qbittorrent/qBittorrent/blob/release-5.2.3/src/webui/webapplication.cpp#L434-L439), [status handling](https://github.com/qbittorrent/qBittorrent/blob/release-5.2.3/src/webui/webapplication.cpp#L339-L376), [local login](../../scripts/bootstrap-core.ts#L72-L109)). The wiki's example says `SID`/200, so the current parser is correct for the pinned 5.2.3 contract but not generic across older releases. Either pin the version or accept both documented legacy `SID` and `QBT_SID_<port>` forms. Verify by logging in with the managed credentials and making an authenticated read; do not read back the password (the official API defines it as write-only).

5. **API-key handling is post-login and secret-bearing.** The API-key guide says Bearer keys cannot call `auth/login` or `logout` and describes UI generation ([official guide](https://github.com/qbittorrent/qBittorrent/wiki/API-Key-Authentication-%28%E2%89%A5v5.2.0%29)). The 5.2.3 source additionally includes `web_ui_api_key` in `app/preferences` and implements `app/rotateAPIKey` by generating, persisting, and returning a key ([preferences response](https://github.com/qbittorrent/qBittorrent/blob/release-5.2.3/src/webui/api/appcontroller.cpp#L317-L330), [rotate/delete](https://github.com/qbittorrent/qBittorrent/blob/release-5.2.3/src/webui/api/appcontroller.cpp#L1280-L1295), [v5.2 WebAPI changelog](https://github.com/qbittorrent/qBittorrent/blob/v5_2_x/WebAPI_Changelog.md#L17-L26)). Thus a script can obtain a key only after password/cookie authentication, and dumping the full preferences object leaks it. Rotating is a state change that invalidates an existing key; do so only when explicitly intended, then store/export it only through an authorized private mode-0600 handoff. The API key does not replace the initial temporary-password login.

## Recommended script contract

`setup-qbittorrent.ts RUN_ID` should remain the service-scoped API-first entry point:

1. Load the recorded run and target the loopback WebUI on `QBITTORRENT_PORT`; send matching `Origin` and `Referer` headers.
2. Try the persisted managed identity first. On success, skip startup-log fallback.
3. Only for a known fresh `/config` and a startup watermark belonging to that container/process, parse a post-watermark temporary-password line and log in as `admin`.
4. Set the managed WebUI username/password and fixed `/data/torrents` paths via `app/setPreferences`; authenticate again with the managed credentials and perform one protected read.
5. On failure, keep the current private handoff/resume flow and same `RUN_ID`. Never display temporary passwords, cookies, API keys, or the preferences object.

This is source-level guidance, not evidence that the image emits accessible fresh logs, the login succeeds live, or transfers resume after restart. Those remain isolated runtime acceptance checks.

## Implementation follow-up

The catalog now has an inspect-only Hotio 5.2.3 Compose recipe and a per-app API setup adapter. The transport identifies the exact running Compose service, checks its project/service labels and current process start, and parses only logs since that start without printing them. The adapter verifies login, configures the saved admin and paths, reads an existing API key or creates one only if absent, then privately stores and checks it. `bun .agents/skills/self-host/workflows/selfhost/scripts/check-qbittorrent-setup.ts` passes fresh, resume, lost-response, and no-replay fixtures. No live image, VPN, Arr connection, or restart check has passed yet; the app remains outside bounded apply.

Follow-up against the pinned [5.2.3 login controller](https://raw.githubusercontent.com/qbittorrent/qBittorrent/release-5.2.3/src/webui/api/authcontroller.cpp): rejected credentials return HTTP 401, not the older example's HTTP 200 `Fails.` body. The adapter and fake-response check now treat 401 as a rejected login so the guarded temporary-password path can run. The pinned [WebUI authority check](https://raw.githubusercontent.com/qbittorrent/qBittorrent/release-5.2.3/src/webui/webapplication.cpp) also compares the Host header's port with the WebUI's local port. The recipe therefore requires the published host port to equal target port 8080; the shared compiler rejects a different host port before planning. A current-start temporary-password log line alone still does not prove a fresh `/config` profile, so live acceptance and profile provenance remain gates before promotion.
