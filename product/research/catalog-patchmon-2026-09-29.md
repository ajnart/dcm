# PatchMon catalog research (2026-09-29)

Decision: update the discovery manifest, but do not add `recipe.json` or `setup.ts`. No shared Compose apply or deterministic first-admin/API-key claim is safe yet.

## Primary-source facts

- [v2.1.3 release](https://github.com/PatchMon/PatchMon/releases/tag/v2.1.3) is the latest listed release; the official image is `ghcr.io/patchmon/patchmon-server`, with full version tags documented in the [Docker README](https://github.com/PatchMon/PatchMon/blob/main/docker/README.md). The manifest names `2.1.3` but retains `status: verify` until registry digest and live image checks.
- The [v2.1.3 production Compose](https://github.com/PatchMon/PatchMon/blob/v2.1.3/docker/docker-compose.yml) has server, PostgreSQL 17, Redis 7, and guacd 1.6.0. It sets a stable server hostname for presence identity, health-gated dependencies, PostgreSQL and Redis volumes, and a guarded guacd runtime. Port 3000 is exposed; this catalog must default it to loopback if a recipe is later supported.
- The [v2.1.3 environment template](https://github.com/PatchMon/PatchMon/blob/v2.1.3/docker/env.example) requires `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `JWT_SECRET`, `SESSION_SECRET`, `AI_ENCRYPTION_KEY`, and a browser-origin-specific `CORS_ORIGIN`. PostgreSQL connection details include a URL with the password. The [first-admin guide](https://patchmon.net/docs/patchmon-operator-guide/first-time-admin-setup) documents `POST /api/v1/auth/setup-admin` for an empty database, with first name, last name, username, email, and policy-compliant password. The first account is a superadmin. The [integration API guide](https://patchmon.net/docs/patchmon-api-integrations-guide) places API credential creation behind an authenticated administrator session; those credentials are distinct from per-host agent keys.

## Exact shared-contract gaps

The v2 recipe now supports generated private files bound to raw server environment values and a typed PostgreSQL URL, so these are no longer the main blocker. Redis's official `--requirepass` command and its healthcheck still interpolate `REDIS_PASSWORD`: the recipe has no secret-safe argv/healthcheck binding. Leaving Redis unauthenticated or putting the password in catalog JSON or Compose argv would weaken the upstream deployment. The schema also lacks the stable server `hostname` and guacd's `tmpfs`, `security_opt`, capability drop, and resource-limit fields. Dropping or silently changing those upstream security/runtime provisions would be a different, unverified deployment. `CORS_ORIGIN` needs the exact selected browser origin; a loopback origin is not a substitute when the browser uses another private address.

`setup.ts` is omitted because no safe recipe can install the service. The published first-admin guide identifies the setup endpoint, but does not establish its exact pinned request/response and independent post-loss identity proof. Before a headless adapter is added, verify those against v2.1.3 source, define inspect-before-write and lost-response replay behavior, and prove fresh-instance login plus restart persistence. API credential creation needs its own authenticated, scoped, one-time-secret capture and replay contract; do not confuse it with first-admin creation or agent enrollment. A browser-created administrator is a valid guided path, but it is not deterministic shared setup. Agent enrollment additionally needs its own explicit host-scoped approval and acceptance; a running server is not proof that a host is monitored or patched.

Next boundary: add a secret-safe Redis command and healthcheck mechanism, explicit hostname and guarded sidecar runtime fields, and selected-origin binding; then build a version-pinned recipe and adapter with focused source and live validation. Until then PatchMon remains discovery-only. No Docker, browser, or live application check was run in this pass.
