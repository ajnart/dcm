# Emby shared-setup decision — 2026-09-29

The vendor-owned [Docker Hub image](https://hub.docker.com/r/emby/embyserver) is `emby/embyserver`. Its [tag list](https://hub.docker.com/r/emby/embyserver/tags) shows a fixed stable `4.10.0.40` tag; `latest` is movable. The image page documents `/config`, owner-selected media mounts, `UID`/`GID`/`GIDLIST`, and HTTP port 8096. Its sample enables host networking for DLNA/Wake-on-LAN and optional GPU devices; those are not implicit requirements or acceptable defaults for a private shared recipe. Any media library path must be owner-selected, never invented from a generic image example.

Emby's [Users documentation](https://emby.media/support/articles/Users.html) says the setup wizard creates the administrator. The project's [user authentication reference](https://github.com/mediabrowser/emby/wiki/User-Authentication) documents `/Users/AuthenticateByName` for checking an existing login and an `AccessToken` on success. It does not document a first-admin creation request. The [installation page](https://emby.media/support/articles/Installation.html) directs users to the installer and does not establish an HTTP first-run schema for the pinned server version. Therefore authentication of an existing account cannot justify claiming a generated initial admin was provisioned.

Decision: retain discovery support and add a deployable private v2 `recipe.json`, but no `setup.ts`. The recipe pins the vendor image and port, stores configuration in a project-owned volume, and requires an exact owner-selected read-only media path. It generates an owner-only first-admin password for the documented browser wizard; shared setup must report pending until a human completes that wizard and authentication is independently checked. The recipe intentionally omits the image's documented optional `UID`/`GID` environment variables because the shared recipe host-identity binding currently permits only `PUID`/`PGID` or `USERMAP_UID`/`USERMAP_GID`; falsely mapping either pair to Emby would be worse than retaining the image default. Verify effective write access to `/config` and read access to the selected media before approval. Host networking, DLNA, GPU devices, and public exposure are not selected.

The exact headless blocker remains: neither the vendor's Users documentation nor its authentication reference establishes a version-pinned first-admin creation HTTP request and response sequence, and no documented persistent API-key creation route was established. `/Users/AuthenticateByName` verifies an existing account and issues an `AccessToken`; it does not create the first account or prove a reusable integration key. Library mapping, indexing, playback, restart persistence, and backup/restore require separate checks. A loopback HTTP response or container start proves none of those. No live Docker, setup wizard, media content, or restore check was run.

## 2026-09-30 recheck

The current [Emby installation guide](https://support.emby.media/support/articles/Installation.html) still instructs the operator to create the initial username and password in the browser startup wizard, then complete library, remote-access, and terms screens before sign-in. The [user authentication reference](https://github.com/mediabrowser/emby/wiki/User-Authentication) documents `/Users/AuthenticateByName` only for an existing user; success yields an access token, not a first administrator.

An [Emby team response in its Developer API forum](https://emby.media/community/topic/94413-create-first-ever-user-without-going-thru-the-wizard-or-having-an-api-key/) says there is officially no process for creating the first user without the wizard. It describes replaying the wizard's requests as unofficial and says there is no documented process for them. That response predates the pinned `4.10.0.40` image and supplies no version-specific request schema or replay semantics. Therefore no safe deterministic `setup.ts` can be added from primary evidence: a pre-send checkpoint cannot resolve an ambiguous lost response, and an existing-login check alone cannot prove who created the administrator. Keep the current recipe's `manual-first-admin` gate and report shared setup pending until the wizard and independent login check are completed. No manifest support promotion, browser, Docker, or live setup was performed in this recheck.
