# Emby shared setup review — 2026-09-30

Decision: keep the existing loopback-only deployment candidate and `manual-first-admin` onboarding. Do not add `setup.ts` or mark Emby configured by shared setup.

The [official installation guide](https://support.emby.media/support/articles/Installation.html) says the startup wizard creates the initial username and password, adds media libraries, reviews remote access, and accepts terms. The [users guide](https://emby.media/support/articles/Users.html) says that wizard-created user has administrative access. Neither guide documents a headless first-admin request or startup credential input for the pinned `emby/embyserver:4.10.0.40` image. The published [user-creation API](https://betadev.emby.media/reference/RestAPI/UserService/postUsersNew.html) explicitly requires an existing administrator, so it cannot bootstrap the first one. The [authentication guide](https://betadev.emby.media/doc/restapi/User-Authentication.html) documents login after an account exists; an access token returned by login is not a separately created API key. The developer reference is updated across releases and does not establish the pinned image's first-run implementation.

An [Emby Team answer](https://emby.media/community/topic/94413-create-first-ever-user-without-going-thru-the-wizard-or-having-an-api-key/) explicitly says first-user creation without the wizard is not officially supported. The suggested alternative is to call the wizard's own API requests unofficially. That answer is from 2021, not a version-specific contract for `4.10.0.40`; it supplies neither request/response shapes nor idempotent replay behavior. An adapter could not safely distinguish a lost successful first-admin write from another account claiming the same name.

The generated `admin-password` file in the recipe is a private handoff for a human completing the wizard, not an automatically installed credential. A `setup.ts` that submits guessed wizard requests or edits Emby's config would cross an unverified, one-time security boundary. API-key creation also remains pending an authenticated, version-pinned route and readback. Keep admin setup, library selection, indexing/playback, and restart persistence as separate manual acceptance steps. Mount only owner-approved media read-only; do not infer library contents, remote access, transcoding, or paid-license entitlements from a running container.

No Docker run, browser action, first-admin write, API-key creation, library scan, playback, or restart verification was performed. The recipe and manifest were left unchanged.

## Direct-HTTP route recheck

The [Emby Team's first-user answer](https://emby.media/community/topic/94413-create-first-ever-user-without-going-thru-the-wizard-or-having-an-api-key/) still explicitly calls headless first-user creation unofficial and says there is no documented process; replaying wizard requests is the suggested hack. The [published authentication reference](https://github.com/mediabrowser/emby/wiki/User-Authentication) starts with an existing account and returns an access token after login. Neither source supplies a `4.10.0.40` first-admin request/response contract, a way to prove ownership after a lost write response, or a persistent API-key creation/readback contract. Accordingly the saved generated password remains a wizard handoff only. No `setup.ts` was added, and shared setup must remain pending until the browser wizard and an independent saved-credential login check are completed.

## Pinned-release source recheck

The vendor's [4.10.0.40 release](https://github.com/MediaBrowser/Emby.Releases/releases/tag/4.10.0.40) publishes binary packages and notes a startup-wizard regression fix, but its release repository [describes itself as binary releases](https://github.com/MediaBrowser/Emby.Releases). The GitHub-generated “Source code” archive for that release is therefore not evidence of the server implementation or an HTTP setup contract. The [public Emby repository](https://github.com/MediaBrowser/Emby) and current developer reference do not establish that the pinned 4.10.0.40 image implements a replay-safe first-owner sequence.

The official [API-key guide](https://dev.emby.media/doc/restapi/API-Key-Authentication.html) instructs an existing administrator to create a key in the dashboard. Its [POST /Auth/Keys reference](https://dev.emby.media/reference/RestAPI/SessionsService/postAuthKeys.html) requires administrator authentication but documents an unknown response body. Neither supplies a version-pinned create-and-readback contract for a saved private key. The [authentication reference](https://github.com/mediabrowser/emby/wiki/User-Authentication) supports checking a wizard-created account with its saved password, but that check alone cannot prove ownership of a first-owner write after an ambiguous response. No source change is warranted: keep the recipe, manifest, and missing adapter as they are.
