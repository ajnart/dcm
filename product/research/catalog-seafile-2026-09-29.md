# Seafile CE 14.0 catalog research (2026-09-29)

## Verified upstream contract

- [Seafile's 14.0 CE installation guide](https://manual.seafile.com/14.0/setup/setup_ce_by_docker/) and its [official Compose template](https://manual.seafile.com/14.0/repo/docker/ce/seafile-server.yml) use `seafileltd/seafile-mc:14.0-latest`, MariaDB 10.11, and Redis. The Seafile container persists `/shared`; MariaDB persists `/var/lib/mysql`. Redis is private and the template does not publish its port. The optional Caddy/SeaDoc components are separate from the core server template.
- The first deployment requires `SEAFILE_MYSQL_DB_PASSWORD`, `INIT_SEAFILE_MYSQL_ROOT_PASSWORD`, `INIT_SEAFILE_ADMIN_EMAIL`, `INIT_SEAFILE_ADMIN_PASSWORD`, `JWT_PRIVATE_KEY` (at least 32 characters), and `SEAFILE_SERVER_HOSTNAME`. It accepts `SEAFILE_SERVER_PROTOCOL=http|https`. The template uses raw environment values, not `*_FILE` variables. The repo's generated mode-0600 raw-secret env binding is the relevant secret contract, while Docker inspection still exposes container environment to host operators. The initial admin values apply to an empty installation; they are not a credential reset on restart.
- [Seafile's account-token API](https://seafile-api.readme.io/reference/post_api2-auth-token) documents `POST /api2/auth-token/` with an email `username` and `password`. [Authentication](https://seafile-api.readme.io/reference/authentication) uses `Authorization: Bearer <account-token>` on current servers. [Account info](https://seafile-api.readme.io/reference/get_api2-account-info) documents `GET /api2/account/info/` with `email` and `is_staff` fields; these could verify the saved admin and provide a private token readback. [Server info](https://seafile-api.readme.io/reference/get_api2-server-info) is an anonymous version endpoint. An account token is a credential and must be saved only through the shared private key handoff.

## Recipe blocker

The shared Compose picker lets the operator select a private host port. Seafile configures generated service/file URLs from separate `SEAFILE_SERVER_HOSTNAME` and `SEAFILE_SERVER_PROTOCOL` values. Its [14.0 CE setup guide](https://manual.seafile.com/14.0/setup/setup_ce_by_docker/) calls the former a *public hostname or domain*, while its [reverse-proxy guide](https://manual.seafile.com/14.0/setup/use_other_reverse_proxy/) recommends publishing Seafile's port 80 behind a separately configured proxy. Neither documents `host:port` in `SEAFILE_SERVER_HOSTNAME` or proves that a nondefault published port appears in all file/sync URLs. Pinning `127.0.0.1` without the selected port would misconfigure nondefault-port links; pinning port 80 would not fit the picker's collision handling. Therefore no `recipe.json` or `setup.ts` is published yet. The exact missing common primitive is a reviewed external-origin/ingress binding (including scheme, authority, selected port, and ownership) with a source-backed Seafile configuration mapping; a typed `local-hostport` compiler binding alone cannot establish upstream support for its value.

To unblock, obtain a current upstream configuration/source contract for custom ports in the hostname or a documented separate external-base-URL input. Then add a three-service v2 recipe with generated admin, DB, root, and JWT secrets, validate the private URL and file-link readback on a fresh instance, and only then add the headless account-token adapter. A successful container start or login alone does not prove sync/file URLs, restart persistence, or backup recovery.
