# Stalwart Mail catalog boundary — 2026-09-29

Decision: update the discovery record with a current official image, but do not add a shared recipe or setup adapter yet. This is not a claim of mail-server acceptance.

[Stalwart's Docker guide](https://stalw.art/docs/install/platform/docker/) publishes `stalwartlabs/stalwart` and recommends a versioned `v0.16` tag rather than `latest`; [v0.16.23](https://github.com/stalwartlabs/stalwart/releases/tag/v0.16.23) was the latest upstream release checked. The image needs distinct persistent `/etc/stalwart` configuration and `/var/lib/stalwart` data mounts. Its example exposes HTTP/HTTPS, SMTP, IMAP, POP3, and ManageSieve ports; the guide explicitly permits publishing only selected ports. Mail delivery requires a separate public ingress/DNS/TLS/reputation plan, not a loopback admin recipe.

[Bootstrap mode](https://stalw.art/docs/configuration/bootstrap-mode/) starts without mail services and offers only the HTTP management surface on port 8080. It prints a temporary `admin` password once to logs. The Docker guide permits `STALWART_RECOVERY_ADMIN=username:password` through an environment file to avoid log extraction, but this is a recovery credential, not the permanent administrator. The setup wizard creates the permanent account and requires a restart. Once HTTPS and the permanent account work, the guide says to remove the recovery variable and disable the HTTP configuration listener. A persistent shared recipe that binds a generated password to `STALWART_RECOVERY_ADMIN` without an approved, checkpointed removal step would leave a standing recovery login.

[Declarative deployment](https://stalw.art/docs/configuration/declarative-deployments/) is a separate multi-stage flow: render `config.json`, start in recovery mode with a secret credential, apply a CLI plan for configuration and objects, then restart without recovery variables. Current recipe primitives cannot safely orchestrate that staged configuration-file render, exact mail-domain choices, recovery-variable removal, and restart. Merely publishing private port 8080 would provide bootstrap access but not a configured mail service. The recipe's maximum eight additional ports also cannot model the entire official ten-port example, though the upstream permits a deliberately selected subset.

[API keys](https://stalw.art/docs/auth/authentication/api-key/) are separately created, long-lived management JMAP credentials with one-time secret display; they are not the bootstrap or permanent admin password and do not authenticate to mail protocols. Do not infer or invent one from an HTTP response. Creating and saving a scoped key would require a documented exact API operation, verified permanent admin identity, one-time-secret checkpointing, and authenticated read-back.

Before promotion: design a bounded, staged private bootstrap with explicit hostname/domain and storage choices, prove permanent admin authentication and removal of recovery access, then separately approve and verify each public mail port, DNS record, TLS path, outbound delivery, inbound delivery, abuse controls, backup restore, and restart persistence. No live container, API call, DNS, or mail round-trip was performed.
