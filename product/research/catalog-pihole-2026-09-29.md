# Pi-hole v6 shared recipe, 2026-09-29

The official [Docker image release](https://github.com/pi-hole/docker-pi-hole/releases/tag/2026.09.0) is `2026.09.0` and includes FTL v6.7.1. The [Docker setup](https://docs.pi-hole.net/docker/) uses `/etc/pihole` for persistent configuration and publishes ports 53 TCP/UDP for DNS separately from port 80 for the web interface. It identifies `NET_ADMIN` as needed for DHCP, not ordinary fresh-instance web administration. The [configuration reference](https://docs.pi-hole.net/docker/configuration/) documents `WEBPASSWORD_FILE` with a Compose secret and `TZ`.

The private recipe publishes only container TCP 80 to host loopback and generates a 48-character owner-only password file. It does not publish DNS port 53, DHCP port 67, or HTTPS port 443; it does not claim network-wide filtering, working client DNS, or a Homarr widget. DNS publication needs a separate owner decision and approval covering host resolver/port conflicts, LAN routing, client query proof, and recovery/failover. A private web login is only web-administration acceptance.

The [v6 API authentication contract](https://docs.pi-hole.net/api/auth/) accepts `POST /api/auth` with JSON password and returns `session.valid` plus a session ID. Its documentation shows `X-FTL-SID` for subsequent reads and `/api/info/version` as a readback endpoint. The adapter uses those exact calls on the saved private origin and stores neither password nor session ID in its checkpoint. A successful login plus version readback proves only this generated credential and API route. Restart persistence, DNS resolution, Homarr connection, and live-image behavior remain unverified without an owned runtime check.

Pi-hole v6 [changed v5 configuration names](https://docs.pi-hole.net/docker/upgrading/v5-v6/); the recipe deliberately avoids legacy `WEBPASSWORD`, old dnsmasq bind mounts, and unsupported capability expansion. Image digest resolution remains an apply-time gate; a pinned tag is not an inspected digest.
