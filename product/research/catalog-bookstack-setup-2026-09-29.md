# BookStack shared setup boundary — 2026-09-29

The [LinuxServer BookStack image contract](https://docs.linuxserver.io/images/docker-bookstack/) specifies `lscr.io/linuxserver/bookstack`, port 80 in the container (6875 in its example), persistent `/config`, and MariaDB with `DB_HOST`, `DB_PORT`, `DB_USERNAME`, `DB_PASSWORD`, and `DB_DATABASE`. It requires `APP_URL` and a 32-byte `APP_KEY`; `FILE__` environment inputs can read values from files. The image documents `PUID`, `PGID`, and `TZ`. Its `latest` tag is movable, and a reviewed immutable/versioned image plus matching MariaDB pin was not established here. The existing manifest therefore remains guided/discovery without a v2 recipe.

The image starts with publicly known `admin@admin.com` / `password`. [BookStack's security guidance](https://www.bookstackapp.com/docs/admin/security/) says to change both the initial email and password before exposure. Its [documented `bookstack:create-admin --initial` command](https://www.bookstackapp.com/docs/admin/commands/) updates the seeded admin if present, creates one if no admin exists, and otherwise exits 2. With `--generate-password`, it prints the new password on stdout. This is a plausible source-backed, idempotent rotation route, but the current shared setup interface has no narrow way to persist that newly generated stdout as the owner-only admin password. Passing a generated password via `--password=...` would put the secret in container argv, which the interface expressly forbids. Creating a second admin without changing the seeded login would leave a known credential active. No `setup.ts` was added.

BookStack's API docs are served by an instance at `/api/docs`, but API tokens are an optional later user action, not a first-run credential or evidence that the seeded admin is gone. Any eventual adapter needs a pinned image, exact-owner checkpoint before `--initial`, private capture and persistence of the generated password, a readback proving the new email/password and denial of the seeded login, and restart-persistence checks. A loopback HTTP 200 only proves reachability.

No Docker pull, Compose start, first-admin rotation, or live acceptance was performed.
