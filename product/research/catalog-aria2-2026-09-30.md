# aria2 shared setup decision — 2026-09-30

Decision: retain discovery support; do not publish a v2 shared Compose recipe or `setup.ts` yet. This is about the aria2 daemon, not AriaNg or another web UI.

The [official aria2 repository](https://github.com/aria2/aria2) distributes the CLI and cross-build Dockerfiles, but does not document an official Linux service image or Compose topology. Its [manual](https://aria2.github.io/manual/en/html/aria2c.html) documents `--enable-rpc`, `--rpc-secret`, `--rpc-listen-all`, the `/jsonrpc` endpoint, and `token:<secret>` as the first parameter of authenticated methods. The RPC secret functions as an API authorization token, not a username/password account or a separately issued API key. `aria2.getVersion` can verify authorized RPC without causing a download; a tokenless call must also be rejected. `system.listMethods` is not an authentication check because it is permitted without a token.

The [snowdreamtech/aria2 image](https://github.com/snowdreamtech/aria2) is a third-party packaging option, not an official aria2 image. It documents a fixed `1.37.0-debian` tag and `RPC_HASH` environment secret; when omitted, the image generates a token and directs operators to read logs. Neither log retrieval nor a secret in process arguments is an owner-only generated-token handoff. Binding `RPC_HASH` via the shared private env-file primitive would keep it out of catalog JSON but expose it to Docker-inspection users, and current `no-account` onboarding requires an empty private-file set, so it cannot hand off or authenticate a generated RPC token. A static `configFiles` entry cannot safely contain a generated secret.

Unblock only after selecting and pinning a maintained service image and adding a typed token-only onboarding/handoff contract. Prefer an owner-only runtime config generated from a private token file, with no token in argv, catalog, Compose, or logs. Independently prove token-required `aria2.getVersion`, denial without the token, persistent downloads/session behavior, and restart persistence. Keep RPC loopback-bound by default; peer-port and VPN behavior need separate scope and approval. No live deployment was performed.
