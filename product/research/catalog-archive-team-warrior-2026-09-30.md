# ArchiveTeam Warrior catalog review — 2026-09-30

Decision: keep the application at discovery; do not add a v2 shared Compose recipe or no-account setup adapter yet. Correct the manifest's upstream repository from legacy boot scripts to the current [ArchiveTeam Dockerfile repository](https://github.com/ArchiveTeam/warrior-dockerfile). No Warrior was started and no external archiving job was authorized.

The [official image README](https://github.com/ArchiveTeam/warrior-dockerfile/blob/master/README.md) publishes `atdr.meo.ws/archiveteam/warrior-dockerfile`, serves a web UI on port 8001, and allows configuration by UI, environment, or `projects/config.json`. `DOWNLOADER` is a public leaderboard nickname, not an account. `HTTP_USERNAME`/`HTTP_PASSWORD` are optional UI protection. `SELECTED_PROJECT=auto` delegates project choice to ArchiveTeam; it is not a neutral startup setting. The repository's [Compose example](https://github.com/ArchiveTeam/warrior-dockerfile/blob/master/docker-compose.yml) uses the image without a fixed tag and adds Watchtower with a Docker-socket mount. Neither a mutable image nor a socket-mounted auto-updater fits this catalog's bounded apply contract. The [Dockerfile](https://github.com/ArchiveTeam/warrior-dockerfile/blob/master/Dockerfile) labels a build version, but the published example does not establish an immutable image tag/digest for that build.

On first start, [start.py](https://github.com/ArchiveTeam/warrior-dockerfile/blob/master/start.py) writes `projects/config.json` from environment values only if no valid config exists, then starts `run-warrior3` with Warrior HQ. Therefore an environment-only first-run choice can become stale after restart. The image's healthcheck fetches `/index.html`; that proves the UI responds, not that a selected project is archiving, uploads are accepted, or the intended nickname and resource limits apply. An adapter returning ready after HTTP 200 would misstate the actual function.

Required before a recipe: verify an immutable official image reference and exact runtime configuration; bind a selected project and nickname through a separate explicit participation approval; prohibit `auto` unless separately chosen; set and verify bounded concurrency, disk and outbound-bandwidth limits; and identify a stable private read endpoint that proves the selected project and job state without starting or changing work. The shared recipe has no per-service CPU/memory/bandwidth ceiling, and generic no-account readiness has no documented acceptance for archival progress. A no-project, UI-only recipe would not deliver the cataloged volunteer archiving function.

The catalog manifest remains `image.status: verify` and `automation: discovery`. Current source review only; no Docker deployment, image inspection, HTTP request, project selection, or archiving test was performed.
