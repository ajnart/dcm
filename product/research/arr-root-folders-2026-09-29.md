# Sonarr/Radarr root-folder setup contract

- Checked: 2026-09-29
- Status: source contract confirmed; no app instance or Compose apply was used.
- Scope: Sonarr `v4.0.19.2979`, Radarr `v6.4.4.10685`, and the current shared recipes/setup paths.

## Findings

Both pinned controllers expose the v3 API. `GET /api/v3/rootfolder` returns a JSON list (200); `GET /api/v3/rootfolder/{id}` returns one resource (200, or 404 when absent). A resource carries `id`, `path`, `accessible`, `freeSpace`, and `unmappedFolders`. `POST /api/v3/rootfolder` consumes JSON and returns `Created(id)`, i.e. **201 Created** with the created resource. The create payload can be just `{"path":"/container/path"}`. The controller validates the path, including existence and writability, so a missing/non-writable mount path is not a successful setup. After create, list again and require an exact `path` readback; do not treat accepted 200/202 responses as evidence of creation. The pinned shared REST base implements `Created(id)` as `CreatedAtAction` and GET-by-id returns the resource or `NotFound` ([Sonarr](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/Sonarr.Http/REST/RestController.cs), [Radarr](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/Radarr.Http/REST/RestController.cs)); the versioned route prefix is defined by each app's `V3ApiController` ([Sonarr](https://github.com/Sonarr/Sonarr/blob/v4.0.19.2979/src/Sonarr.Http/VersionedApiControllerAttribute.cs), [Radarr](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/Radarr.Http/VersionedApiControllerAttribute.cs)).

The current harness's shared `media-data` bind is mounted inside Arr as `/data`; its bootstrap hard-codes `/data/media/tv` for Sonarr and `/data/media/movies` for Radarr. Seerr repeats those paths. The per-app recipes, however, only declare the selected shared `/data` mount and say to configure the library path against it; neither per-app `setup.ts` currently creates or verifies a root folder. Therefore those two are current harness candidates, not implicit approvals for every standalone/shared app plan. Carry the exact owner-approved **container path** in the non-secret setup plan/checkpoint; never substitute the host bind source. It must already exist and be writable inside that selected mount.

## Safe create/resume shape

The existing `bootstrap-core.ts` does GET-before-POST but accepts `[200, 201, 202]` and does not immediately list/read back the created folder. Root-folder create is not documented as idempotent. For the per-app adapter, use a unique one-time action per app with `approval.once: true` and a `beforeSendCheckpoint` written before the POST (for example, stage `root-folder-create-attempted`, data `{path: approvedContainerPath}`). Keep only the selected non-secret path in that checkpoint. On restart, GET the list first: if the exact path is present, verify and advance the checkpoint; if it is absent after a recorded attempt, stop for inspection instead of replaying POST. The setup transport already requires the pre-send checkpoint for one-time mutations and refuses a repeated action; Seerr's first-admin adapter demonstrates the same inspect-after-ambiguous-outcome pattern ([transport](../../packages/cli/src/control-panel/setup-transport.ts#L609-L665), [Seerr checkpoint flow](../../.agents/skills/self-host/workflows/selfhost/references/catalog/apps/seerr/setup.ts#L142-L200)).

## Seerr quality-profile choice

Both pinned Arr sources expose `GET /api/v3/qualityprofile` as a list of `QualityProfileResource` values with numeric `id` and `name`. Seerr needs an Arr profile ID/name pair when saving its server settings. Resolve candidates from the running Arr's list, surface the chosen pair in the approved plan, and pass that exact pair to Seerr; do not silently assume the name `Any` or infer an ID. The current bootstrap does select a unique `Any` from Seerr's test response, which is convenient for its fixture but not a user-approved/profile-independent contract.
