# Kopia catalog assessment (2026-09-29)

## Verified upstream facts

- Kopia publishes `kopia/kopia` Docker images with fixed `major.minor.patch` tags. The current upstream release page lists `v0.23.1`; the catalog now records `docker.io/kopia/kopia:0.23.1`. [Installation](https://kopia.io/docs/installation/) [Release](https://github.com/kopia/kopia/releases/tag/v0.23.1)
- The official Compose example runs `kopia server start` on port 51515, mounts `/app/config`, `/app/cache`, and optional logs, and passes `KOPIA_PASSWORD` for repository access. It also passes HTTP server username/password on command-line flags. [Installation](https://kopia.io/docs/installation/)
- Repository creation is a separate prerequisite; the repository password encrypts snapshots and cannot be recovered if lost. Repository users are separately added with `kopia server users add` after repository configuration. [Getting started](https://kopia.io/docs/getting-started/) [Repository server](https://kopia.io/docs/repository-server/) [User-add command](https://kopia.io/docs/reference/command-line/common/server-users-add/)
- `server start` documents `--server-username`, `--server-password`, and `--htpasswd-file`, but no `--server-password-file` option. The official sample's plaintext command-line password is unsuitable for this catalog's secret boundary; the server's `--without-password` option is explicitly unsafe for an exposed control API. [Server-start flags](https://kopia.io/docs/reference/command-line/common/server-start/)
- The pinned v0.23.1 server starts by opening the configured repository before it serves HTTP. It refuses unsafe unauthenticated network binding unless an explicitly dangerous override is used. [Pinned server source](https://github.com/kopia/kopia/blob/v0.23.1/cli/command_server_start.go)
- Kopia's UI can create or connect a filesystem repository only after an exact storage path and encryption password are supplied. Upstream requires the operator to provision remote/cloud storage first, and says the password cannot be recovered. A local Docker volume alone is not an off-host backup target. [Repositories](https://kopia.io/docs/repositories/) [Getting started](https://kopia.io/docs/getting-started/)

## Catalog decision and exact gap

No v2 shared-Compose recipe or headless `setup.ts` is added. The shared recipe can describe a private port and persistent mounts, but its onboarding forms cannot safely generate the pinned server's HTTP credential into argv or construct a protected htpasswd file before Compose start. Using `--without-password`, even with a host-loopback published port, would leave the container listener unauthenticated on the Compose network. Starting without repository configuration also fails before HTTP is served, so a deterministic UI-first bootstrap cannot solve the ordering problem.

A bounded implementation needs an exact off-host repository target and credential choice, a pre-start repository create/connect stage with loss-safe replay, and a secret-safe HTTP authentication mechanism supported by the pinned image and shared engine. It must verify the saved admin login and repository connection, then separately prove a snapshot and isolated restore from the selected target. Container readiness, an HTTP response, or an authenticated UI alone is not backup acceptance. The catalog remains `guided`; this is an explicit framework/approval gap, not a claim that Kopia itself cannot be deployed securely.
