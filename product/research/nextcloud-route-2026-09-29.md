# Nextcloud headless setup route

Checked 2026-09-29. Source-only research; no image pull, Docker, browser, live API, or host inspection was performed. Image tags below are current candidates, not resolved digests or deployment verification.

## Finding

A blank Nextcloud data volume can be installed without the web wizard: provide both `NEXTCLOUD_ADMIN_USER` and `NEXTCLOUD_ADMIN_PASSWORD`, plus a complete supported database variable set, before the first app start. `_FILE` variants are supported for both admin fields and the MySQL/MariaDB connection fields. The image entrypoint reads these only while `installed_version` is `0.0.0.0`; they do not recover or rotate credentials on an existing install. Reject a partially configured DB rather than risk the image's SQLite fallback. [Image README](https://github.com/nextcloud/docker/blob/master/README.md) · [entrypoint](https://github.com/nextcloud/docker/blob/master/docker-entrypoint.sh)

## Candidate Compose contract

| Service | Candidate image / exact behavior | Persistent state and exposure |
|---|---|---|
| `db` | `mariadb:12.3.3`; initialize with `MARIADB_DATABASE_FILE`, `MARIADB_USER_FILE`, `MARIADB_PASSWORD_FILE`, `MARIADB_ROOT_PASSWORD_FILE`; use InnoDB, `READ-COMMITTED`, and binlog disabled or `BINLOG_FORMAT=ROW`. | `db:/var/lib/mysql`; internal network only. MariaDB init variables are ignored once its data directory is initialized. |
| `redis` | `redis:8.10.2-alpine3.23`; no published port. | Ephemeral cache/locking service; internal network only. |
| `app` | `nextcloud:35.0.1-apache`; `MYSQL_HOST=db`, `MYSQL_DATABASE_FILE`, `MYSQL_USER_FILE`, `MYSQL_PASSWORD_FILE`; `NEXTCLOUD_ADMIN_USER_FILE`, `NEXTCLOUD_ADMIN_PASSWORD_FILE`; `REDIS_HOST=redis` (and `REDIS_HOST_PASSWORD_FILE` if password-protected); set `NEXTCLOUD_TRUSTED_DOMAINS` only to the approved host. Apache listens on container port 80. | `nextcloud:/var/www/html`; publish only as `127.0.0.1:<chosen-port>:80` for private access. Data directory defaults to `/var/www/html/data`. |
| `cron` | Same Nextcloud image and `nextcloud:/var/www/html` mount as `app`, with `entrypoint: /cron.sh`. Pass the Redis host and any Redis password-file setting here too. | No published port. |

The topology is in the upstream [Apache + MariaDB Compose example](https://github.com/nextcloud/docker/blob/master/.examples/docker-compose/insecure/mariadb/apache/compose.yaml), which is explicitly under `insecure/`; use it for service/volume structure, not as a hardened recipe or for its floating tags. The upstream [Docker README](https://github.com/nextcloud/docker/blob/master/README.md) documents the `_FILE` variables, first-run admin setup, Apache variant, and `occ` invocation. MariaDB's official image documents its `MARIADB_*_FILE` inputs and first-initialization behavior in its [image README](https://hub.docker.com/_/mariadb).

Secret scope: DB root secret only to `db`; application DB user/password to `db` and `app`; admin username/password to `app` only; Redis password to `redis`, `app`, and `cron` if enabled. Keep generated admin credentials in the explicitly requested private handoff artifact; ordinary evidence contains only its path. Compose file-backed secrets are host bind mounts: Compose ignores requested `uid`, `gid`, and `mode` for these sources, and Nextcloud requires secret files readable by `www-data` UID 33. Validate effective host/container readability without printing payloads before apply. Do not put secret values in Compose interpolation, command arguments, logs, or screenshots. [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/) · [Compose service reference](https://docs.docker.com/reference/compose-file/services/)

## Version provenance and fit

As checked on 2026-09-29, Nextcloud Server [v35.0.1](https://github.com/nextcloud-releases/server/releases/tag/v35.0.1) is the current release and the Docker Official Images [manifest](https://github.com/docker-library/official-images/blob/master/library/nextcloud) lists `35.0.1-apache`. The image project describes itself as community-maintained; the tag's inclusion in Docker Official Images is separate from Nextcloud Server release ownership. MariaDB's [official manifest](https://github.com/docker-library/official-images/blob/master/library/mariadb) lists `12.3.3`; Nextcloud 35's [system requirements](https://docs.nextcloud.com/server/stable/admin_manual/installation/system_requirements.html) list MariaDB 12.3 as supported. Redis' [official manifest](https://github.com/docker-library/official-images/blob/master/library/redis) lists `8.10.2-alpine3.23`; Nextcloud's [caching guidance](https://docs.nextcloud.com/server/stable/admin_manual/configuration_server/caching_configuration.html) recommends Redis for distributed cache and file locking (and APCu for local cache).

Use those explicit tags as candidates, then resolve and record platform-specific image digests at setup time. Digests were not resolved here. MariaDB's listed architectures are narrower than Nextcloud's; inspect target architecture before selecting the recipe. Floating `apache`, `nextcloud`, `mariadb:lts`, or `redis:alpine` references are not reproducible pins.

## Credential and functional verification contract

- Preserve the generated admin password before first start; Nextcloud does not provide a supported password read-back. If a password is lost later, the supported recovery is `occ user:resetpassword --password-from-env <uid>` with `OC_PASS` supplied through the private apply boundary, not argv; `occ user:list` can confirm the UID. Avoid `occ config:list system --private`. [OCC users](https://docs.nextcloud.com/server/stable/admin_manual/occ_users.html) · [Docker `occ` usage](https://github.com/nextcloud/docker/blob/master/README.md)
- Public unauthenticated `GET /status.php` returns JSON including `installed`, `maintenance`, `needsDbUpgrade`, and `versionstring`. Require HTTP 200, `installed=true`, `maintenance=false`, `needsDbUpgrade=false`, and the expected version; HTTP 200 alone is not acceptance. [status.php source](https://github.com/nextcloud/server/blob/master/status.php)
- `GET /ocs/v1.php/cloud/capabilities` gives a version read but is public; it cannot prove that a supplied Basic credential authenticated. Verify `admin` against `GET /ocs/v1.php/cloud/users` with `OCS-APIRequest: true` and `Accept: application/json`: the documented user-list endpoint is admin-only, and a successful OCS response must include `admin`. [OCS API overview](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/OCS/ocs-api-overview.html) · [upstream capabilities controller](https://github.com/nextcloud/server/blob/master/core/Controller/OCSController.php)
- For storage functionality, authenticated WebDAV `PROPFIND /remote.php/dav/files/{uid}/` with `Depth: 0` should return `207 Multi-Status` with a successful home-resource property response. Stronger isolated smoke: `PUT`, `GET`, then `DELETE` a uniquely named probe file at `/remote.php/dav/files/{uid}/<probe>` and verify exact contents before deleting. [WebDAV](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html) · [RFC 4918](https://www.rfc-editor.org/info/rfc4918/)
- Set background job mode with `occ background:cron`; run the official `/cron.sh` sidecar or host cron at the documented five-minute cadence. Cron is recommended over AJAX. [Background jobs](https://docs.nextcloud.com/server/stable/admin_manual/configuration_server/background_jobs_configuration.html) · [OCC apps](https://docs.nextcloud.com/server/stable/admin_manual/occ_apps.html)

## Safety, test plan, and unknowns

Keep DB and Redis unpublished and on the app's project network; do not bind the Docker socket or broad host paths. Bind the web port to loopback unless a separate public-ingress approval names the DNS/TLS/auth owner. Docker warns that a port without a host IP binds all interfaces. Use named volumes by default; if a host data path is explicitly chosen, check exact path ownership, UID 33 write access, capacity, and that it is dedicated before apply. Do not use broad teardown or `down -v`. For recovery acceptance, back up configuration, data, database, custom apps, and themes and prove restoration in an isolated project; a successful backup job or live endpoint is not a restore test. [Compose port binding](https://docs.docker.com/reference/compose-file/services/) · [Nextcloud backup](https://docs.nextcloud.com/server/stable/admin_manual/maintenance/backup.html) · [restore](https://docs.nextcloud.com/server/stable/admin_manual/maintenance/restore.html)

Fresh-isolated acceptance plan (not run): use a unique Compose project and new named volumes; preflight platform, free loopback port, digest resolution, Compose version, and secret-file readability; start only its DB/Redis/app/cron services; prove no wizard through `status.php`; check the protected OCS admin user list and WebDAV probe-file round trip; verify cron mode and at least one scheduled invocation; restart and verify persisted file/account; then restore the DB + app volumes into a separate isolated project and repeat functional checks. Never reuse an existing Nextcloud project or volumes for this test.

Unresolved before implementation: host architecture/platform; Compose version and secret-file UID mapping; chosen private hostname/port and whether a separately approved ingress exists; chosen data root/capacity; platform-specific image digests; whether Redis authentication is needed; and SMTP/notification setup. No live deployment, digest, or host acceptance claim is made.

## Implemented structural boundary

The v2 `multi-service-compose` recipe now encodes `db`, `redis`, `app`, and `cron`, including bounded argv `entrypoint`/`command` and one explicitly shared named volume for the app and cron services. The focused recipe and Compose-volume checks pass. Nextcloud remains an inspect-only candidate: image pulls, file readability inside the containers, first-admin login, WebDAV, cron mode, restart persistence, and restore have not been verified on a fresh instance.
