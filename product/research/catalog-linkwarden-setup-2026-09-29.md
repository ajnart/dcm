# Linkwarden v2.16.3 headless setup decision (2026-09-29)

No `setup.ts` is added. The shared `SetupContext` has the necessary HTTP request, pre-send checkpoint, secret-file, and cookie-header primitives in principle, but the pinned Linkwarden contract is not yet sufficient to make a safe replayable first-admin and API-token adapter.

## Source-backed route inventory

- The [pinned Compose file](https://github.com/linkwarden/linkwarden/blob/v2.16.3/docker-compose.yml) is the existing recipe source. Its recipe generates an admin password and privately binds port 3000.
- Official API pages name `POST /api/v1/users` for signup, `POST /api/v1/session` for login, `POST /api/v1/tokens` for token creation, and `GET /api/v1/users/me` for authenticated readback: [signup](https://docs.linkwarden.app/api/create-user), [session](https://docs.linkwarden.app/api/create-a-new-session), [token](https://docs.linkwarden.app/api/create-token), [current user](https://docs.linkwarden.app/api/get-current-user). The available rendered pages omit request schemas and response fields. The session page notes that a `401` can mean correct credentials but unverified email, so a generic response check is not enough.
- The [pinned users route](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/pages/api/v1/users/index.ts) delegates signup to [`postUser`](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/lib/api/controllers/users/postUser.ts). The controller rejects unauthenticated registration only when `NEXT_PUBLIC_DISABLE_REGISTRATION=true`; it has no first-user-only exception. The existing recipe does not set that variable. Starting with it enabled permits more unauthenticated accounts; starting with it disabled prevents the first owner. Account creation alone therefore cannot establish that public registration is closed.
- The pinned [session route](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/pages/api/v1/session/index.ts) can return `EMAIL_NOT_VERIFIED`. Its [credential verifier](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/lib/api/verifyByCredentials.ts) only requires verification when both mail variables are configured; without mail, username/password login is allowed. The pinned [token route](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/pages/api/v1/tokens/index.ts) requires an authenticated user, and its [controller](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/lib/api/controllers/tokens/postToken.ts) returns `secretKey` only on token creation.

## Exact blockers

1. Design a separately approved, scoped restart of the owned Compose project that flips `NEXT_PUBLIC_DISABLE_REGISTRATION` only after first-owner creation, then directly prove unauthenticated signup is denied. The current `SetupContext` cannot change the pinned service environment or perform that restart; the first-run adapter must not silently assume this transition.
2. Confirm the recipe's absence of mail variables remains the deployed contract, and verify signup schema, authentication/token payload and one-time return, and protected readback before coding the adapter. If mail is added, first-owner verification becomes a separate gate.
3. Define lost-response recovery after the one-time signup and token writes. A pre-send checkpoint must mark both as attempted; resume must authenticate the saved generated password and recover a token only if upstream exposes it, otherwise stop for review rather than creating another account or key.
4. Verify the resulting account, saved token, archive round-trip, and restart persistence independently. Neither HTTP 200 nor Compose liveness proves these checks.

Review was source-only, including the pinned v2.16.3 controllers named above. No test, Docker action, or live Linkwarden request was run.
