# Syncthing shared-Compose candidate (2026-09-29)

The [official image](https://github.com/syncthing/syncthing/blob/main/README-Docker.md) is `syncthing/syncthing`; the catalog already pins `2.1.4`. Its persistent mount is `/var/syncthing`, its runtime UID/GID are selected through `PUID`/`PGID`, and its GUI defaults to `0.0.0.0:8384` inside the container. The recipe publishes the GUI on host loopback only. The [upstream Dockerfile](https://github.com/syncthing/syncthing/blob/main/Dockerfile) exposes 8384/TCP, 22000/TCP+UDP, and 21027/UDP and checks `/rest/noauth/health`; [that endpoint](https://docs.syncthing.net/rest/noauth-health-get.html) proves only `{"status":"OK"}`. The optional peer ports are not acceptance evidence. Upstream recommends host networking for LAN discovery; a shared bridge may impair LAN reachability, so a real approved peer/file round-trip remains required.

The source-level shared adapter uses the official image's own `/bin/syncthing cli config gui apikey get` via exact-owned-container read command. The [CLI documentation](https://docs.syncthing.net/users/syncthing) states that `cli config` accesses the live configuration using local API authentication, and the [v2.1.4 Dockerfile](https://raw.githubusercontent.com/syncthing/syncthing/v2.1.4/Dockerfile) installs `/bin/syncthing`. The [official v2.1.4 release](https://github.com/syncthing/syncthing/releases/tag/v2.1.4) identifies the pinned image. No XML scraping or Arr-specific key reader is used. The transport binds the command to the exact owned running container and redacts its stdout. The adapter requires empty GUI user/password before saving the generated key privately; the one-time [PATCH `/rest/config/gui`](https://docs.syncthing.net/rest/config) is checkpointed before sending. It then verifies keyed config access, Basic authentication with the saved admin password, and anonymous GUI denial. If a key was saved before a write checkpoint, the adapter may continue only while GUI authentication is still pristine; once a write was attempted, replay verifies the saved login and never blindly resends the mutation. The static docs describe the generated `cli config` hierarchy but do not spell out this exact leaf invocation, and no pinned image was run; this is source-level, fail-closed behavior, not live acceptance.

The [GUI config documentation](https://docs.syncthing.net/users/config.html) confirms `user`, bcrypt `password`, `apikey`, and Basic auth behavior. [Syncthing's REST API](https://docs.syncthing.net/dev/rest.html) requires the key for management requests. An already configured GUI is refused, not overwritten. No public GUI exposure is approved by this candidate. Peer reachability and restart persistence remain unverified even if headless account setup reports ready.

Validation is source/schema-level only: no Docker image, fresh profile, peer network, API login, or persistence was exercised.
