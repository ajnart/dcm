# Sonarr and Radarr Compose/API route evidence (2026-09-29)

## Scope and finding

This covers only the Sonarr and Radarr Compose catalog entries and their candidate setup adapters. Both recipes now pin a LinuxServer stable image tag, keep the web UI loopback-bound by default, persist `/config`, and require an explicit absolute host selection for a shared `/data` bind. That mount preserves the existing harness's in-container path convention (`/data/media/tv`, `/data/media/movies`, and `/data/torrents`) without guessing a host path. The shared catalog validator now accepts their LinuxServer PUID/PGID bindings and manual-first-admin recipes; validation passed. The setup adapters remain unregistered candidates until the pinned images pass fresh-instance acceptance.

The adapters are unregistered candidate sidecars, not live acceptance proof. Their `inspect` method rechecks policy and a saved login checkpoint without mutating; keep the candidate route inspect-only until fresh-image acceptance. The candidate `firstRun` method obtains the 32-hex API key from the exact owned service's private `/config/config.xml`, saves it through the existing private-secret helper, GETs host config, and PUTs the GET-derived resource to `/api/v3/config/host/{id}` only when Forms auth is not already configured. It then reads back policy and POSTs the saved admin password to `/login`, accepting only the success redirect. On resume it repeats login verification without rewriting policy or the API key. This still does not configure root folders, qBittorrent, Prowlarr sync, indexers, or prove restart persistence.

## Current-source evidence

- The [Sonarr OpenAPI document](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/Sonarr.Api.V3/openapi.json) describes itself as the v3 API for Sonarr v3 and v4. It defines `GET /api/v3/config/host`; the update operation is `PUT /api/v3/config/host/{id}` and `HostConfigResource` includes the ID, authentication settings, username, password, and confirmation. Its authentication enums include `forms` and `enabled`. The adapter therefore derives the ID from the GET response and does not reuse the older collection-level PUT.
- The [Radarr OpenAPI document](https://raw.githubusercontent.com/Radarr/Radarr/develop/src/Radarr.Api.V3/openapi.json) currently documents the same GET-derived-ID PUT route and resource fields. The [official Radarr API docs](https://radarr.video/docs/api/) still publish the v3 contract. However, an [official Radarr issue for 6.0.4.10291](https://github.com/Radarr/Radarr/issues/11390) records `/api/v3/rootfolder` redirecting while the reporter suspected an API v4 redirect. That is not direct evidence that this host-config endpoint redirects, but it is a version-sensitive warning. Exact Radarr image behavior still needs a fresh-container check; the private transport does not follow redirects.
- The [Sonarr security documentation](https://wiki.servarr.com/sonarr/settings/general#security) and [Radarr security documentation](https://github.com/Servarr/Wiki/blob/master/radarr/settings.md#security) recommend application authentication; current Servarr guidance cautions against disabling local authentication behind an incorrectly trusted proxy. The candidate selects Forms authentication and leaves the UI private/loopback-bound.
- The pinned [Sonarr v4.0.19.2979 login controller](https://raw.githubusercontent.com/Sonarr/Sonarr/v4.0.19.2979/src/Sonarr.Http/Authentication/AuthenticationController.cs) accepts form fields at `POST /login`, redirects a failed login to `loginFailed=true`, and redirects success to the configured root after issuing a Forms session. [Radarr's current controller](https://raw.githubusercontent.com/Radarr/Radarr/develop/src/Radarr.Http/Authentication/AuthenticationController.cs) has the same behavior; the exact Radarr image tag has not yet passed live route verification. The shared private transport exposes only a bounded relative `Location` header for this check, never session-cookie content.
- The pinned [Sonarr host-config controller](https://raw.githubusercontent.com/Sonarr/Sonarr/v4.0.19.2979/src/Sonarr.Api.V3/Config/HostConfigController.cs) and [Radarr host-config controller](https://raw.githubusercontent.com/Radarr/Radarr/v6.4.4.10685/src/Radarr.Api.V3/Config/HostConfigController.cs) return HTTP 202 Accepted for the ID-specific update. Both candidate adapters now require that response, record a one-time pre-send checkpoint, and reconcile a lost response through API readback instead of repeating the password-setting PUT. Existing different authentication is preserved for inspection.
- LinuxServer's [Sonarr image documentation](https://docs.linuxserver.io/images/docker-sonarr/) and [Radarr image documentation](https://docs.linuxserver.io/images/docker-radarr/) document ports 8989 and 7878, `/config`, PUID/PGID/TZ, and stable `latest` tags. The recipes instead pin version tags currently shown on the [Sonarr package page](https://github.com/linuxserver/docker-sonarr/pkgs/container/sonarr/versions) and [Radarr package page](https://github.com/linuxserver/docker-radarr/pkgs/container/radarr): `version-4.0.19.2979` and `version-6.4.4.10685`. These are tags, not verified immutable digests; recheck before planning an update.

## Existing behavior and route mismatch

The canonical media setup in [`scripts/bootstrap-core.ts`](../../scripts/bootstrap-core.ts#L285) uses `GET /config/host` followed by `PUT /config/host` without an ID, then configures `/rootfolder` and discovers/tests/creates the download client through `/downloadclient/schema`, `/downloadclient/test`, and `/downloadclient`. The Sonarr and Radarr setup wrappers delegate to that shared routine. The current official OpenAPI documents the host-config PUT only at `/api/v3/config/host/{id}`. Keep the old route as historical harness evidence; do not treat it as the current candidate contract.

The candidate's bounded delta is therefore intentionally smaller than the existing harness: API key capture and authenticated Forms policy only. Recipe acceptance calls out the outstanding library/downloader checks. In particular, a chosen shared host path is operator input; the catalog does not infer it or assert that its `media` and `torrents` directories already exist.

## Not verified

Focused fake-response checks passed for first setup, safe resume without a second auth PUT, rejected login, lost-response reconciliation, conflicting existing auth, deferred approvals, and saved checkpoint inspection. Radarr's current v3/v4 runtime route behavior also remains unresolved beyond the published OpenAPI and issue evidence above.
