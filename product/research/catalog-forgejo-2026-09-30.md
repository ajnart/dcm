# Forgejo 16.0.5 first-run setup boundary — 2026-09-30

Decision: keep Forgejo guided and do not add `setup.ts`. Compose start and the generated private password file do not establish an administrator account.

The [pinned v16.0 CLI reference](https://forgejo.org/docs/v16.0/admin/command-line/) documents `admin user create` with a required username, password, and email plus `--admin`. Its password inputs are `--password` (process argv) and `--random-password`; it documents no file, stdin, or secret-environment input for this command. Expanding the saved password from private stdin into `--password` would still put it in the Forgejo process argv. A random CLI password would not match the recipe's saved handoff credential. The recipe also has no reviewed email choice.

The [v16.0 Docker installation guide](https://forgejo.org/docs/v16.0/admin/installation/docker/) directs first-run installation through the web interface; it does not specify a bounded HTTP first-admin contract, including route, CSRF, session, and replay behavior. The [v16.0 API guide](https://forgejo.org/docs/v16.0/user/api/usage/) documents HTTP Basic authentication for an existing account and `POST /api/v1/users/{username}/tokens` for token creation. Its token secret is returned only once. That route cannot bootstrap an administrator, and it should not be invoked before verified account ownership or without one-time-secret checkpointing.

The [v16.0 configuration reference](https://forgejo.org/docs/v16.0/admin/config-cheat-sheet/) defines `INSTALL_LOCK` only as control of access to the installation page. It does not establish an HTTP installer automation contract or make account creation through the authenticated API possible before the first account exists. The application also needs a real administrator email choice; deriving one from the username would invent identity data.

Unblock only with a pinned, source-proven first-admin secret input that does not expose the saved password in argv, or a separately reviewed first-run HTTP flow with exact route/session/CSRF semantics, a non-secret email choice, pre-send checkpointing, and authenticated read-back of the same saved credential and admin role. An API token is a separate approved action with one-time capture and verification; the admin password is not an API token.

No container, browser, login, token, restart, or Git round-trip was exercised. The existing recipe and manifest remain unchanged and Forgejo remains a deployment candidate, not configured-app acceptance.

## Shared-owner recheck

The v16 CLI has two additional `admin user create` switches worth recording: `--random-password-length` and `--access-token` (with name and scopes). They can create a random password and token without placing their values in argv, but they do not solve this shared owner's contract: the recipe has already generated its private admin password, and `SetupContext.secrets` has no method to replace that password with the CLI-generated one. Capturing either secret from CLI stdout before durable private storage would also need an explicit pre-send checkpoint and uncertain-outcome recovery path. The CLI's separate `generate-access-token --raw` has the same one-time-output issue and is not a first-admin route.

## Pinned installer-source recheck

The [v16.0.3 installer handler](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.3/routers/install/install.go) does accept an admin name, email, and password in its installation form, so HTTP could keep the password out of process argv. However, `SubmitInstall` first writes configuration and migrates the database, then calls `CreateUser`. On `ErrUserAlreadyExist`, it fetches the existing user by name and sets the long-term-auth cookie and session UID without verifying the submitted password. It then shuts down the installation server. The recipe's actual pinned image is v16.0.5, whose [installer handler](https://codeberg.org/forgejo/forgejo/src/tag/v16.0.5/routers/install/install.go) retains this behavior. A response-loss retry could therefore cross an ownership boundary; success cookies or redirects cannot prove that the generated password owns the account. The existing recipe also has no reviewed admin email. Do not implement a blind installer POST or replay it after uncertainty. A future adapter needs a pre-send checkpoint, an exact no-existing-user precondition, a non-secret email choice, and independent authenticated read-back of the saved password and admin role before claiming ownership. The post-install server restart and configuration changes also need bounded recovery behavior.

The documented `--password` argument remains the only way to set the recipe's saved password through the CLI; neither the v16 CLI nor the Docker installation guide documents a stdin/file password input. The installation guide still directs initial onboarding in a browser. The API's BasicAuth token endpoint presupposes an account and returns the token only once. Therefore no deterministic `setup.ts` can be added within these files without changing the shared secret/transport contract or accepting an unreviewed web onboarding flow. Keep `support.automation` as `guided`, `adapterSkill` null, and the recipe's account and repository acceptance pending.
