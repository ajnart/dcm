# Beszel 0.20.0 headless setup decision

No `setup.ts` adapter is published. The pinned Hub recipe has `manual-first-email` onboarding, but its `admin@example.test` identity is a placeholder, not an operator-selected address. The shared setup context can read the generated password and make approved HTTP requests; it cannot change that recipe identity or establish that a successful regular-user login is an administrator.

The [official user-account guide](https://beszel.dev/guide/user-accounts) distinguishes Beszel Hub users from PocketBase superusers. The [REST API guide](https://beszel.dev/guide/rest-api) documents regular-user password authentication, while the [environment guide](https://beszel.dev/guide/environment-variables) documents `USER_EMAIL` and `USER_PASSWORD` initial-user creation without guaranteeing the resulting Hub role or separate superuser state. The upstream [role issue](https://github.com/henrygd/beszel/issues/2013) reports that environment-created accounts can be ordinary users; this is a warning, not a pinned 0.20.0 API contract. Beszel's [0.20.0 hub source](https://github.com/henrygd/beszel/blob/v0.20.0/internal/hub/hub.go) shows the Hub's PocketBase-backed user hooks. The [health guide](https://www.beszel.dev/guide/healthchecks) limits `/api/health` to Hub health, not account authorization or monitoring.

Before a headless adapter is safe, establish a version-pinned first-user HTTP route and response contract, prove the selected email has the Hub `admin` role through an authenticated readback, define whether the PocketBase superuser must also be provisioned, and bind a real operator-selected email into the reviewed plan and saved handoff. The documented `superuser upsert` CLI is not suitable for the current container transport because it takes a password argument, which would place a secret in argv. A one-time HTTP write would also need a pre-send checkpoint and login-based replay recovery.

The existing recipe's Hub health check remains valid but narrow. No agent, fresh metrics, restart persistence, or live first-account behavior was verified. No Docker or browser action was taken.
