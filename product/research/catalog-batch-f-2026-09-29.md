# Catalog batch F: first-run feasibility (2026-09-29)

Scope: `peanut`, `photoprism`, `pihole`, `plex`, `portainer`, `postgresql`, `prometheus`, `renovate`, `restic`, `scrypted`. Prometheus now has a no-account recipe and a read-only first-run adapter. The remaining apps need contract work, user choices, or explicit privilege approval before a safe complete path can be claimed.

| App | Source-backed constraint / missing choice before a safe recipe + deterministic first-run adapter |
| --- | --- |
| PeaNUT | Upstream Compose mounts `/config` and uses port 8080, but a useful setup needs an existing NUT server and its connection choices. Its example warns that the image runs as UID/GID 1000 and does not support PUID/PGID. NUT credentials must not enter catalog data or ordinary setup inputs. The current onboarding union has no "no local admin, configure external NUT" form. [Upstream README](https://github.com/Brandawg93/PeaNUT/blob/main/README.md) |
| PhotoPrism | The documented initial `PHOTOPRISM_ADMIN_PASSWORD` is a plain environment value, has no documented `_FILE` companion, and affects only first startup. The current generated-private-file contract cannot safely feed that setting, and retry after a lost first-start outcome needs direct account verification. Originals path and SQLite/MariaDB choice also need review. [Compose guide](https://docs.photoprism.app/getting-started/docker-compose/), [configuration](https://docs.photoprism.app/getting-started/config-options/) |
| Pi-hole | v6 does support `WEBPASSWORD_FILE`, making a private-file admin password plausible, and `/api/auth` can verify it. Yet service acceptance requires owned LAN port 53 TCP/UDP, DNS upstream choice, and a deliberate client cutover; loopback-only DNS would not satisfy that goal. The recipe onboarding union assumes a username whereas Pi-hole's documented API authenticates by password/session. Do not represent a DNS cutover as web login. [Docker configuration](https://docs.pi-hole.net/docker/configuration/), [API auth](https://docs.pi-hole.net/api/auth/), [2026.09.0 release](https://github.com/pi-hole/docker-pi-hole/releases/tag/2026.09.0) |
| Plex | A deterministic first-run must resolve Plex account claim/sign-in, owned library paths, and remote-access choice; the shared app adapter has no user OAuth/claim-token handoff. Keep remote access off absent separate approval. [Vendor install guidance](https://support.plex.tv/articles/200288586-installation/) |
| Portainer | Upstream supports `--admin-password-file`, but its ordinary local Docker deployment grants the container access to `/var/run/docker.sock`. That is a root-equivalent, cross-project mutation boundary forbidden as a casual catalog default. A reviewed remote endpoint/agent topology and exact authority would be a different recipe. [Install guide](https://docs.portainer.io/start/install-ce/server/docker/linux), [CLI options](https://docs.portainer.io/advanced/cli) |
| PostgreSQL | The official image supports first-cluster `POSTGRES_PASSWORD_FILE`, but the shared setup transport verifies only HTTP, not PostgreSQL wire authentication, migrations, backups, or an isolated restore. The required major version is selected by the consuming app, not a universal standalone default. [Official image](https://hub.docker.com/_/postgres), [PostgreSQL backup docs](https://www.postgresql.org/docs/current/backup.html) |
| Prometheus | Added `prom/prometheus:v3.15.0`, a loopback-only port 9090 and named `/prometheus` volume. The upstream image starts with sample configuration; the adapter checks documented `HEAD /-/ready` and `GET /api/v1/status/buildinfo` without an account or mutation. This proves only ready-to-query at the pinned version. Real scrape targets, retention, authentication or approved private ingress, and restart persistence are separate acceptance work. [Pinned release](https://github.com/prometheus/prometheus/releases/tag/v3.15.0), [Docker installation](https://prometheus.io/docs/prometheus/latest/installation/), [management API](https://prometheus.io/docs/prometheus/latest/management_api/), [HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/), [basic auth](https://prometheus.io/docs/guides/basic-auth/) |
| Renovate | A usable self-hosted run needs the exact Git platform, endpoint, repository discovery policy, and scoped token. It is a bounded job rather than a persistent first-admin HTTP service, which the current recipe/onboarding and HTTP setup interfaces assume. [Self-hosted configuration](https://docs.renovatebot.com/self-hosted-configuration/) |
| restic | The official workflow is repository `init`, snapshots, checks, and isolated `restore`, with repository and encryption secret choices. A persistent HTTP admin service is inapplicable, and a successful snapshot is not restore proof. [Introduction](https://restic.readthedocs.io/en/stable/010_introduction.html), [installation](https://restic.readthedocs.io/en/stable/020_installation.html) |
| Scrypted | The official Compose topology requires host networking and may need devices/accelerators; NVR storage and license choices are separate. Current recipe networking is scoped bridge publishing, so translating the upstream host-network example would change device-discovery semantics and approval scope. [Official Compose guide](https://github.com/koush/scrypted/wiki/Installation:-Docker-Compose-Linux), [official Compose file](https://github.com/koush/scrypted/blob/main/install/docker/docker-compose.yml) |

Suggested narrow contract additions before retrying the remaining apps: (1) onboarding variants for password-only and jobs; (2) app-owned, private generated configuration file mounts with explicit format and no secret interpolation; (3) a typed local TCP/database verification surface for PostgreSQL; (4) reviewed network/privilege/device gates for LAN DNS, Docker API, and cameras. Each app still needs a pinned image, fresh-instance contract verification, and direct acceptance before its recipe can imply anything beyond a candidate.

Validation on this branch: `bun build .../prometheus/setup.ts --target=bun --outfile=/dev/null` passed. The JSON schema accepts `no-account`, but `validateAppRecipe` in the shared runtime validator still falls through to the initial-admin branch and rejects this recipe with `first-admin file onboarding is invalid`; that common-contract fix belongs outside this batch. Full catalog validation was also blocked by unrelated concurrent app image-status edits. No live container or fresh-instance acceptance was run.
