# PostgreSQL shared catalog candidate — 2026-09-29

The [Docker Official Image](https://hub.docker.com/_/postgres) documents `POSTGRES_PASSWORD_FILE`, first-cluster initialization, and the PostgreSQL 18+ data-volume target `/var/lib/postgresql`. The [18.6 tag](https://hub.docker.com/_/postgres/tags?name=18.6) is pinned here. The recipe generates a private 48-character password, hands off its file path with the fixed `postgres` superuser identity, and mounts one project-owned volume. The password variable initializes an empty cluster only; it does not rotate an existing database password. Each consuming application must independently select a compatible PostgreSQL major version.

The v2 recipe contract requires exactly one published primary port. This candidate therefore defaults to `127.0.0.1:5432`, not a LAN or public bind. A separate approved access design is required for remote clients. Compose start and [`pg_isready`](https://www.postgresql.org/docs/18/app-pg-isready.html) prove only availability, not password authentication. The first-run adapter uses the shared exact-owned container command seam: it sends the saved password only through private stdin, rejects a deliberately wrong password, and runs a read-only TCP `psql` query with the saved password. This proves the account inside the owned container, not reachability through the published host port.

Before promotion, authenticate from a separate client through the published loopback TCP port, distinguish a fresh initialized cluster from an adopted volume, and check replay after restart. Prove a consistent backup and isolated restore using the [PostgreSQL backup guidance](https://www.postgresql.org/docs/18/backup.html). Major-version upgrades require a separate migration plan; changing the image tag is not a data-format migration. No live PostgreSQL container or restart was exercised in this pass.
