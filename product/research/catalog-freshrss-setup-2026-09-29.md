# FreshRSS 1.30.0 shared setup — 2026-09-29

Decision: do not add `apps/freshrss/setup.ts` with the present secret boundary. Keep the existing guided recipe and browser first-admin acceptance. No live container or login was exercised.

The [pinned Docker guide](https://github.com/FreshRSS/FreshRSS/blob/1.30.0/Docker/README.md) documents either browser installation or `cli/do-install.php` followed by `cli/create-user.php --user ... --password ...`. Its `FRESHRSS_INSTALL` and `FRESHRSS_USER` first-run environment inputs expand into CLI arguments. The [pinned entrypoint](https://raw.githubusercontent.com/FreshRSS/FreshRSS/1.30.0/Docker/entrypoint.sh) confirms that expansion. The [pinned create-user implementation](https://raw.githubusercontent.com/FreshRSS/FreshRSS/1.30.0/cli/create-user.php) accepts `password` and optional `api-password` as parsed options; it has no stdin or password-file option. The current exact-container command seam can deliver private stdin, but that does not make this upstream CLI consume it. Passing the generated password through argv or `FRESHRSS_USER` would expose it through process arguments or container environment inspection.

FreshRSS form login and mobile API credentials are distinct. The optional `--api-password` in `create-user.php` is a password for API access, not a returned/generated API key. Do not create or report it as an API key or enable the API during first-admin setup without a separate request. A custom PHP program calling internal `FreshRSS_user_Controller::createUser()` with stdin could avoid argv, but that is not a documented stable onboarding interface and would need its own version-pinned review and verification contract.

Next boundary: an upstream-supported password-file/stdin first-user command, or an independently verified private browser/HTTP onboarding flow that transmits the generated password in request body and proves subsequent form login. Replay must distinguish an owned fresh installation from an existing user before any first-write attempt. Restart persistence and feed data remain separate acceptance checks.

2026-09-30 pinned HTTP installer review: [FreshRSS 1.30.0 `app/install.php`](https://raw.githubusercontent.com/FreshRSS/FreshRSS/1.30.0/app/install.php) accepts `passwordPlain` in the step-3 POST body (lines 187-205, 233-241), so HTTP transport could keep the generated password out of argv. However, step 3 calls `recursive_unlink(USERS_PATH . '/' . default_user)` before creating the user (lines 218-220). It is destructive if the installer is replayed against an existing `admin`, and a preflight HTTP response alone cannot establish absence or ownership of that directory. Earlier steps also write the system configuration and initialize the database (lines 91-179); the full session-based sequence and login/readback have not been independently verified on the pinned image. Do not add a shared adapter or change `manual-first-admin` based on the POST field alone. A safe route needs exact-project fresh-state proof before step 3, one-time checkpointing before every installer write, and successful form-login replay verification; no live exercise was authorized in this review.
