# Tdarr shared-Compose assessment — 2026-09-29

Decision: keep Tdarr discovery-only; do not add a shared recipe or headless adapter yet. The [official Docker guide](https://docs.tdarr.io/docs/installation/docker/run-compose/) offers both a combined server/internal-node image and a separate node image. Both need identical media and transcode-cache paths; the node initiates outbound communication on server port 8266, while the UI uses 8265. No inbound node port is required. The [official version guide](https://docs.tdarr.io/docs/releases/changing-version/) currently pairs server and node tags at `2.81.01`, and the [server package](https://github.com/haveagitgat/Tdarr/pkgs/container/tdarr) lists newer `2.85.01`; a recipe must pin a compatible pair rather than mix `latest` and a fixed tag.

The [authentication guide](https://docs.tdarr.io/docs/other/authentication/) says `auth` is disabled by default. Setting `auth=true` prompts for a username/password in the web UI and requires an API key for separate nodes. It documents `seededApiKey`, but this is a node/API credential, not a first-admin password. Thus a `no-account` recipe may only describe the deliberately unauthenticated mode and must not invent an admin or API key. In shared Compose, a loopback host bind does not isolate the unauthenticated server from peer containers on the shared bridge. A separate-node recipe with authentication needs a source-backed, generated first-admin and node-key handoff that the present recipe onboarding kinds cannot express without a UI step. The official [server status endpoint](https://docs.tdarr.io/docs/troubleshooting/) is `GET /api/v2/status` on port 8266 and can support only narrow server-liveness verification; it does not prove node registration, library permissions, or transcode safety.

The media bind would need an exact owner-selected absolute path mounted at the same target (for example `/media`) in server and node, with an explicit shared writable group. The transcode cache needs a separate project-owned shared writable volume mounted at the same target (`/temp`) in both. Server state (`/app/server`), configs (`/app/configs`), and logs (`/app/logs`) need persistent project-owned storage, with configs/logs shared with the node as documented. GPU/device passthrough is a separate approval, not a default. Most importantly, the [transcode-cache guide](https://docs.tdarr.io/docs/library-setup/transcode-cache/) says completed output is copied back over the source. A shared recipe must not turn on a worker against live media merely because Compose starts; library selection, policy, test-on-copy, and recoverable-original gates are required before processing.

Safe follow-up: establish an exact pinned image pair and no-worker default, choose either a combined container or a separately authenticated node topology, then prove the chosen first-run auth and node registration on a disposable media copy. If retaining `no-account`, explicitly accept shared-bridge exposure and verify the documented status endpoint without claiming an account. No Docker, browser, or live media test was performed here.
