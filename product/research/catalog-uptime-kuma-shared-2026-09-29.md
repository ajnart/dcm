# Uptime Kuma v2.5.5 shared recipe boundary

The catalog recipe now describes a pinned, private, single-service v2 Compose candidate with a project-owned `/app/data` volume and a generated owner password. It does not claim that shared setup can create or verify the first owner.

The tagged [Compose example](https://github.com/louislam/uptime-kuma/blob/2.5.5/compose.yaml) and [release](https://github.com/louislam/uptime-kuma/releases/tag/2.5.5) anchor the image, port 3001, persistence mount, and runtime user. The [installation guidance](https://github.com/louislam/uptime-kuma/wiki/%F0%9F%94%A7-How-to-Install) requires local storage with POSIX locking, not NFS.

On empty storage, the tagged [database setup server](https://github.com/louislam/uptime-kuma/blob/2.5.5/server/setup-database.js#L61-L170) first exposes `GET /setup-database-info` and `POST /setup-database` for SQLite selection. The [first-owner server handler](https://github.com/louislam/uptime-kuma/blob/2.5.5/server/server.js#L646-L679) then uses Socket.IO `needSetup` and `setup` events; [login](https://github.com/louislam/uptime-kuma/blob/2.5.5/server/server.js) is also Socket.IO. The existing standalone `uptime-onboarding-api.ts` implements these version-pinned events and verifies login, including a checkpoint before one-time writes.

The shared setup contract currently exposes bounded HTTP requests and fixed container commands, but no Socket.IO/WebSocket client or exact-origin socket approval boundary. Its adapter is therefore marked `sharedOwner: false`: a shared Compose apply is deployment only, and `app shared setup` must report this app as pending. Reusing the standalone route against a different shared owner would bypass that owner's credential and approval checkpoint, so it is not safe to call it directly. Promotion needs an owner-bound Socket.IO transport or a scoped bridge that preserves generated credential, one-time attempt, exact-origin, and readback semantics. Monitor state and restart persistence remain separate, unverified checks.
