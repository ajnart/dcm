# Kopia shared-setup decision — 2026-09-30

The [official installation guide](https://kopia.io/docs/installation/) publishes `kopia/kopia` container images and links its [Compose sample](https://github.com/kopia/kopia/blob/v0.23.1/tools/docker/docker-compose.yml). The catalog pins `kopia/kopia:0.23.1`. The sample starts `kopia server start` with `--server-username` and `--server-password` on the command line, sets `KOPIA_PASSWORD` separately for the repository, and includes powerful privileges and a whole-host read-only mount. Those privileges and mounts are not acceptable implicit defaults for a private shared recipe.

Correction: the [pinned v0.23.1 server flags](https://github.com/kopia/kopia/blob/v0.23.1/cli/command_server.go#L28-L31) explicitly accept `KOPIA_SERVER_USERNAME` and `KOPIA_SERVER_PASSWORD`. The existing owner-only `secretEnvironment` binding can inject a generated UI/server password without argv exposure or an htpasswd primitive. This login credential is separate from `KOPIA_PASSWORD`, which unlocks the repository.

The remaining blocker is repository bootstrap. [Pinned startup](https://github.com/kopia/kopia/blob/v0.23.1/cli/command_server_start.go#L162-L198) opens a configured repository and returns an error before binding HTTP if that open fails; asynchronous connection is off by default. The [repository-server guide](https://kopia.io/docs/repository-server/) requires creating and configuring a repository before server startup. The [pinned create command](https://github.com/kopia/kopia/blob/v0.23.1/cli/command_repository_create.go#L105-L148) initializes storage with a separate repository password and connects it. The shared recipe cannot yet represent the selected destination, repository secret, first-run initialization, ownership check, and safe replay as a bounded pre-start operation. `--async-repo-connect` only defers the failure.

Decision: do not add `recipe.json` or `setup.ts` until that bootstrap boundary exists. Then verify private startup, saved UI-admin login, anonymous denial, and replay. These prove server access only; snapshot policy, app-consistent capture, an off-host copy, and an isolated restore remain separate backup acceptance. No Docker startup, repository mutation, snapshot, or restore was performed.

## Pinned-source recheck

The `v0.23.1` [server flag definitions](https://github.com/kopia/kopia/blob/v0.23.1/cli/command_server.go#L28-L31) confirm that Basic-auth credentials can come from environment variables, but they do not initialize a repository. The [pinned server startup code](https://github.com/kopia/kopia/blob/v0.23.1/cli/command_server_start.go#L162-L198) still requires a connected repository before ordinary HTTP startup. Thus a generated UI password and later HTTP login check cannot bridge the missing pre-start repository creation and replay boundary. Leave the guided manifest unchanged and shared setup unavailable; do not equate server login with snapshot or restore acceptance.
