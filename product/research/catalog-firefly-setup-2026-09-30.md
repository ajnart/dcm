# Firefly III v6.7.2 shared setup recheck — 2026-09-30

Decision updated: a source-backed shared adapter now attempts first-owner registration, saved-password login, one-time token creation, and token identity readback through pinned HTTP routes. This is source-level automation only; no container, browser, restart, or application acceptance test was run.

The [pinned registration controller](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/app/Http/Controllers/Auth/RegisterController.php) verifies `email`, `password`, and `password_confirmation`, creates a user, logs that user into the web guard, then redirects. In default single-user mode it refuses registration once the user count is nonzero. This is a first-owner web-session flow, not a password-only `admin` bootstrap. The recipe uses a fixed example email; the operator must replace it with a real recovery address before relying on password reset.

The [pinned route table](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/routes/web.php) places `GET/POST /register` and `GET/POST /login` behind the guest middleware and `GET /profile/oauth` plus `POST /oauth/personal-access-tokens` behind `user-full-auth`. The [pinned OAuth controller](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/app/Http/Controllers/Profile/OAuthController.php) initializes the personal-access grant client on the profile GET when absent; the adapter labels that side-effecting GET as an approved write before attempting a token POST. The GET's count check permits a safe replay if its response is lost. The POST creates a token for the authenticated user and returns its plaintext only in that response; the token-list action returns records, not plaintext. If the creation response is lost, repeating the POST creates another live token. The shared checkpoint prevents that duplicate write but cannot recover the lost plaintext.

The recipe now uses `manual-first-email` and fixed `admin@example.test` with a generated private password. The [pinned registration form](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/resources/views/auth/register.blade.php) and [login form](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/resources/views/auth/login.blade.php) expose the CSRF and form fields used by the adapter. The authenticated [profile email form](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/resources/views/profile/change-email.blade.php) provides a saved-login identity readback. The [pinned about-user API](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/app/Api/V1/Controllers/System/AboutController.php) and [user transformer](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/app/Transformers/UserTransformer.php) expose the token owner's email and role. The [registration listener](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/app/Listeners/Security/System/HandlesNewUserRegistration.php) assigns `owner` to the first user.

The adapter checkpoints before registration and before token creation. A lost registration response is reconciled by logging in with the saved credentials; a lost token response is **not** retried because the plaintext is not listed again. The saved token must authenticate as the expected `owner`, and an anonymous `/register` read must show registration closed. The example email is not a recovery inbox; replacing it with a real address requires a separate reviewed account change. The pinned pages, token JSON shape, queue timing, and Docker image remain unverified at runtime, so this adapter must not be described as live-accepted or restart-persistent.
