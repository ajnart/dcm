# Firefly III shared first-run setup — 2026-09-29

Decision: do not add `catalog/apps/firefly-iii/setup.ts`. The pinned `fireflyiii/core:version-6.7.2` recipe is a private Compose candidate, not a verified headless account-bootstrap route. No container was started.

The [official multi-user guidance](https://github.com/firefly-iii/docs/blob/main/docs/docs/how-to/firefly-iii/features/multi-user.md) says the first self-registered user becomes owner and further registration is disabled by default. The [v6.7.2 web routes](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/routes/web.php) identify registration, login, and authenticated personal-access-token actions; they are web-session routes, not an unauthenticated first-owner API. A personal token requires an authenticated user, so it cannot establish the first owner. The recipe's `admin` label is not a Firefly login: registration requires the owner's actual email and the saved generated password.

The current `SetupContext` has bounded HTTP requests, response cookies, checkpoint-before-send, and private password/key storage. Those primitives alone do not establish the pinned web form's CSRF/session fields, a replay-safe first-registration rule after an ambiguous response, or independent proof that the saved email/password belongs to the sole owner. The optional personal-token route also needs an authenticated session and a recoverable one-time token handoff; retrying creation after a lost response could leave an unknown live token. Upstream's [API routes](https://github.com/firefly-iii/firefly-iii/blob/v6.7.2/routes/api.php) do not document an unauthenticated owner bootstrap. These are identity and credential boundaries, not transport-only gaps.

Keep shared setup pending. A safe adapter needs pinned-controller verification of form, CSRF, cookies, registration-close and token semantics; an approved real owner email; a pre-write checkpoint; login plus owner-identity readback on retry; and private token capture or explicit omission of token creation. A live first-account/login check, ledger round-trip, cron caller, restart persistence, and isolated restore remain separate acceptance work. HTTP 200 or a running container proves none of them.
