# PatchMon catalog research — 2026-09-30

Scope: current upstream `main` at commit `055760620b1398d63d657279d9ec001fb6a6cc83`, plus the latest official release metadata checked on 2026-09-30. Sources are limited to PatchMon's official repository and release pages.

## Supported topology and images

- Docker is the preferred and officially supported self-hosted deployment. The production Compose project is named `patchmon` and contains four services on one `patchmon-internal` bridge network: `server`, `database`, `redis`, and `guacd`. Only `server` publishes a host port, `${PORT:-3000}:${PORT:-3000}`. The server waits for healthy PostgreSQL, Redis, and guacd. [README](https://github.com/PatchMon/PatchMon#self-hosted---docker-officially-supported) · [Compose](https://github.com/PatchMon/PatchMon/blob/main/docker/docker-compose.yml)
- Exact upstream images in the current production Compose file:
  - `ghcr.io/patchmon/patchmon-server:latest`
  - `postgres:17-alpine`
  - `redis:7-alpine`
  - `guacamole/guacd:1.6.0`
- Persistent named volumes are `postgres_data` at `/var/lib/postgresql/data` and `redis_data` at `/data`. Frontend assets and agents are embedded in the server image; there is no separate frontend service. [Docker README](https://github.com/PatchMon/PatchMon/blob/main/docker/README.md) · [Compose](https://github.com/PatchMon/PatchMon/blob/main/docker/docker-compose.yml)
- Upstream defines server tags `latest`, `x.y.z`, `x.y`, `x`, and unstable `edge`; its Compose intentionally tracks `latest`. The latest stable GitHub release checked for this note is `v2.1.3` (published 2026-08-15), so a reproducible catalog pin should use `ghcr.io/patchmon/patchmon-server:2.1.3`, while retaining the other exact tags above. [Tag policy](https://github.com/PatchMon/PatchMon/blob/main/docker/README.md#images) · [v2.1.3](https://github.com/PatchMon/PatchMon/releases/tag/v2.1.3)

## First run, admin, password, and API credentials

- There are no documented default admin credentials. First run is browser-driven at `http://localhost:3000`: create the initial admin account. The corresponding public, rate-limited endpoint is `POST /api/v1/auth/setup-admin`; it requires `firstName`, `lastName`, `username`, `email`, and `password`, creates a `superadmin`, and refuses creation once an admin exists. `GET /api/v1/auth/signup-enabled` is public; normal login is `POST /api/v1/auth/login`. [Quick start](https://github.com/PatchMon/PatchMon#quick-start) · [router source](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/server/router.go) · [auth handler](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/handler/auth.go)
- Password policy is configuration-driven; the shipped example documents a default minimum length of 8 with uppercase, lowercase, number, and special-character requirements enabled. These are commented defaults, not a generated password. [env.example](https://github.com/PatchMon/PatchMon/blob/main/docker/env.example)
- General integration API credentials are created after admin login through the JWT/session-protected `POST /api/v1/auto-enrollment/tokens`, requiring `can_manage_settings`. Set metadata `integration_type` to `api`; optional scopes are validated only for that type. The response returns `token_key` and plaintext `token_secret`, while only a bcrypt hash of the secret is stored. [router source](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/server/router.go) · [credential handler](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/handler/auto_enrollment.go)
- Do not confuse integration credentials with a host's agent credential. Adding/enrolling a host produces a per-host API key for the agent. Auto-enrollment instead uses `X-Auto-Enrollment-Key` and `X-Auto-Enrollment-Secret` on `POST /api/v1/auto-enrollment/enroll`. [Enrollment overview](https://github.com/PatchMon/PatchMon#enrolling-hosts) · [credential handler](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/handler/auto_enrollment.go)

## Health and API authentication

- `GET /health` is public and outside `/api/v1`. It checks both PostgreSQL and Redis, returns HTTP 200 with `healthy` only when both pass, otherwise HTTP 503 with `unhealthy`. `?format=json` or `Accept: application/json` returns structured component status. This is the correct unauthenticated service-health probe. [router and health handler](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/server/router.go)
- The integration API lives under `/api/v1/api/*` and uses HTTP Basic authentication, not Bearer auth: username = generated `token_key`, password = generated `token_secret`. Middleware also requires an active, unexpired credential whose metadata has `integration_type: "api"`, applies optional IP allow-lists, and route handlers enforce scopes such as `host:get`. [API auth middleware](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/middleware/api_auth.go) · [router source](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/server/router.go)
- `GET /api/v1/openapi.json` is public. Swagger UI at `/api/v1/api-docs/` is JWT/session protected. The repository README's broad phrase “REST API ... with JWT authentication” therefore describes the UI/session API generally; it does not replace Basic auth for the scoped integration API. [README](https://github.com/PatchMon/PatchMon#platform) · [router source](https://github.com/PatchMon/PatchMon/blob/main/server-source-code/internal/server/router.go)

## Exact blockers / catalog cautions

- The pinned [v2.1.3 production Compose](https://github.com/PatchMon/PatchMon/blob/v2.1.3/docker/docker-compose.yml) passes the generated Redis password in `redis-server --requirepass` and in the Redis healthcheck. The shared recipe only accepts fixed, non-secret argv healthchecks and commands; it cannot bind a private file into those arguments. Removing Redis authentication or embedding the password in catalog JSON/Compose would change the security contract, so no v2 shared recipe is published.
- That Compose file gives `server` a stable hostname for Redis-backed presence identity. It also runs `guacd` with read-only root, a 64 MiB `/tmp` tmpfs, `no-new-privileges`, all capabilities dropped, CPU/memory limits, and a shell-form healthcheck. Current recipe/runtime fields cannot represent that exact guarded sidecar or server hostname. Omitting it is an unverified topology change, not a safe shortcut. The browser-specific `CORS_ORIGIN` from the [v2.1.3 environment template](https://github.com/PatchMon/PatchMon/blob/v2.1.3/docker/env.example) must also match a reviewed origin; loopback alone is insufficient for other private clients.
- Upstream production Compose does not pin the PatchMon server, PostgreSQL, or Redis to immutable digests; `latest` and major tags can move. The catalog must choose whether to follow upstream mutability or pin `2.1.3`/digests under its own update policy.
- There is no bootstrap environment variable for an initial admin username/password in the official Compose or environment template. Fully unattended admin provisioning would need to call the public one-time setup endpoint and handle the credential as a secret; it must not be invented as a declarative Compose setting.
- API credentials cannot be known before an authenticated admin creates them, and the plaintext secret is returned at creation time. A catalog entry can document the route and auth shape but cannot ship a working default API credential.
- No Docker execution was performed. Image architecture availability and live response bodies were not independently exercised; the findings above are source-backed only.

Decision: keep the existing discovery-only manifest and do not add `recipe.json` or `setup.ts`. Even with the public one-time admin route and later authenticated API-key route identified, those mutations cannot verify a service that the shared planner cannot deploy under the official security contract. A future adapter also needs a pre-send one-time checkpoint and login-based recovery after an ambiguous setup response; API-token creation needs immediate owner-only capture of its once-returned plaintext secret.
