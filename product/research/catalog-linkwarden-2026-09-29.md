# Linkwarden v2.16.3 first-run assessment (2026-09-29)

The existing v2 recipe pins Linkwarden v2.16.3 with PostgreSQL and Meilisearch, a generated private admin password, and a loopback-only published port. This note assesses only whether a deterministic headless `setup.ts` can safely consume that credential. [Pinned Compose](https://github.com/linkwarden/linkwarden/blob/v2.16.3/docker-compose.yml)

Official API pages identify `POST /api/v1/users` for registration, `POST /api/v1/session` for authentication, `POST /api/v1/tokens` for token creation, and `GET /api/v1/users/me` for a current-user read. The public pages available here do not render request body schemas, response fields, session cookie/CSRF requirements, or a first-user-only registration guard. The pinned route file confirms `POST /api/v1/users` delegates to `postUser`, but its controller behavior and request shape were not confirmed. [Create user](https://docs.linkwarden.app/api/create-user) [Create session](https://docs.linkwarden.app/api/create-a-new-session) [Create token](https://docs.linkwarden.app/api/create-token) [Current user](https://docs.linkwarden.app/api/get-current-user) [Pinned user route](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/pages/api/v1/users/index.ts)

The official environment reference says `NEXT_PUBLIC_DISABLE_REGISTRATION` defaults to `false`, and `NEXT_PUBLIC_ADMIN=1` identifies a numeric administrator ID. The recipe does not set registration disabled before account creation. A successful first signup therefore would not itself prove that later signup is closed. [Environment reference](https://docs.linkwarden.app/self-hosting/environment-variables)

The pinned `POST /api/v1/users` route checks demo mode, then delegates directly to `postUser`; the route itself has no first-user or registration-disabled guard. An upstream issue reports that `NEXT_PUBLIC_DISABLE_REGISTRATION=true` still permitted signup on a deployed instance, so changing that variable alone cannot be treated as verified closure. This report is not proof of the pinned v2.16.3 image's runtime behavior; it is a reason to require a direct negative signup check before claiming a closed instance. [Pinned user route](https://github.com/linkwarden/linkwarden/blob/v2.16.3/apps/web/pages/api/v1/users/index.ts) [Upstream registration issue](https://github.com/linkwarden/linkwarden/issues/1485)

No `setup.ts` is added, and the recipe's existing onboarding/acceptance declarations remain aspirational rather than a claim of working headless setup. An adapter would have to submit a sourced signup payload, checkpoint before that one-time write, independently verify the generated credential, safely obtain a session, create a token, validate that token against a protected read, and close/recheck registration without replacing the exact owned Compose project unsafely. It must also handle a response lost after signup without claiming an unknown account. The docs' route names alone are insufficient to infer these contracts. Compose readiness, account acceptance, token acceptance, archive round-trip, and restart persistence remain separate checks.
