# Project manifest contract

Auth-store paths are not secret payloads: an environment pair
`<PREFIX>_AUTH_DEFAULT_ACCESS=deny-all` and `<PREFIX>_AUTH_FILE=/mounted/data/database`
may point to a normalized file below a writable persistent mount. Without that
deny-all pair and mount, file-backed variables still require an exact declared
`/run/secrets` target. Plaintext passwords and tokens remain rejected.
The paired `<PREFIX>_CACHE_FILE` may name a different normalized file beneath
the **same** writable persistent mount. It cannot reuse the auth database path,
point outside that mount, or widen another `*_FILE` variable into an exception.

The input is UTF-8 JSON, at most 2 MiB, with `schemaVersion: 1`. Every object uses the exact keys below; unknown or missing keys fail validation. Collections are bounded to 512 entries so a curated multi-app project can use one manifest; nesting, labels, text, and paths remain bounded.

```json
{
  "schemaVersion": 1,
  "project": {
    "dockerContext": "default",
    "id": "private-demo",
    "owner": "private-demo",
    "root": "/srv/selfhost-projects",
    "directory": "/srv/selfhost-projects/private-demo",
    "ownership": "new"
  },
  "services": [
    {
      "id": "web",
      "image": "docker.io/library/nginx:1.27.4",
      "restart": "unless-stopped",
      "readOnly": true,
      "user": "1000:1000",
      "environment": [{ "name": "SESSION_KEY_FILE", "value": "/run/secrets/session_key" }],
      "ports": [{ "hostIp": "127.0.0.1", "published": 18080, "target": 8080, "protocol": "tcp", "purpose": "application", "publicApproved": false }],
      "mounts": [{ "source": "/srv/selfhost-data/private-demo", "target": "/data", "readOnly": false, "shared": false, "owner": "private-demo", "ownership": "new" }],
      "networks": ["private"],
      "secretRefs": [{ "name": "session-key", "ref": "local/private-demo/session-key", "target": "session_key", "filePath": "/srv/selfhost-projects/private-demo/secrets/session-key" }]
    }
  ],
  "networks": [{ "id": "private", "name": "private-demo-private", "driver": "bridge", "internal": true, "owner": "private-demo", "ownership": "new", "subnet": "10.240.0.0/28" }],
  "observed": { "checkedAt": "2026-08-28T10:00:00Z", "project": null, "ports": [], "paths": [], "networks": [] }
}
```

## Field rules

- Optional `ownerDirectory` is exact `{kind:"docker-stack-directory",officialUrl,appId,sourceSha256}`. The installed app's `owner-directory.json`, fixed image, official source and current app/shared implementation bytes bind it. It generates only `<project.directory>/data/<appId>/stacks`: one unshared writable bind whose container target is the identical absolute source, plus `DOCKGE_STACKS_DIR` naming that path. Numeric non-root container UID/GID must equal the actual current owner of all private mode-0700 directory ancestors; preparation creates only that exact directory and never chowns or repairs existing paths. Shared startup/setup replays the saved recipe and requires separately approved management-mTLS authority whose exact DNS identity, private IPv4 and port match the source-bound Docker CLI TLS mapping, with a fresh fixed `/info` identity whose Engine ID matches the observed selected local rootful system Unix daemon. Socket metadata and context are checked before/after; remote, Docker Desktop, rootless and user-remapped daemons are unsupported. This gate binds the manager's paths to that observed daemon identity, not arbitrary remote bind paths or a filesystem-namespace attestation. Host-wide Docker control remains explicitly disclosed; it is not confinement, stack acceptance or permission to mutate an existing stack.
- Optional service `dockerCliTls` carries one source-hashed catalog claim for
  the Docker CLI's fixed certificate directory contract. Only its three declared
  owner-issued file IDs may map to `ca.pem`, `cert.pem` and `key.pem`; arbitrary
  secret filenames remain rejected. The service must carry exactly those local
  file references, `DOCKER_CERT_PATH=/run/secrets` and `DOCKER_TLS_VERIFY=1`, with
  no Docker context, config-directory or TLS-mode override. The pinned official
  CLI source and complete declared app sources are replayed independently by
  the canonical owner. This claim is credential transport provenance, not
  consent for Docker authority or proof of endpoint identity. Separate management
  approval and startup gates still apply. Its exact `endpoint` is
  `{serverName,privateIpv4,port}`: a bounded DNS identity, RFC1918 IPv4 and TCP
  port. `DOCKER_HOST` must match that DNS/port. Rendering emits one fixed
  `extra_hosts` DNS-to-IP mapping only from this profile; arbitrary host mappings
  remain rejected. The directory guard compares these fields to the actual
  separately approved management authority before fresh daemon identity checks.
  The mapping, private file references and source claims appear in review and
  bind the full-manifest approval. Loaded policy-byte drift requires restart.

- Optional `runtimeResources` is exact `{profile:"tun-net-admin",officialUrl,appId,sourceSha256}`. An installed app's exact `runtime-resources.json` declaration binds the app/main service, fixed publisher image reference and listed official source. The source SHA-256 covers its bounded current JSON/TypeScript source graph, including static or derived recipe sources. The shared compiler issues the claim only for the matching recipe request; canonical validation independently rechecks installed source and the exact image pin. This single fixed profile grants only `NET_ADMIN` and `/dev/net/tun:/dev/net/tun:rwm` in the container network namespace. Arbitrary capabilities, devices, host namespaces, host-root binds, privileged mode and Docker sockets remain forbidden. It cannot combine manual-job profiles or `capDrop`. Claims appear in plans and full-manifest approvals. Startup requires an existing non-symlink Linux TUN character device (10:200), an exact local system Unix Docker endpoint and a rootful non-user-remapped daemon; remote, rootless, user-remapped, proxy and user sockets are unsupported. No host changes, device creation or module loading are performed. This does not prove peer membership, VPN/provider authentication, fail-closed egress or application acceptance.
- Optional service `fileEnvironmentConsumers` carries one to twelve exact
  `{name,target,format:"file-path",officialUrl,appId,source:"owner"}` records from
  a reviewed catalog owner-file binding. Each uppercase name must match its
  exact `/run/secrets/<target>` environment value and declared service secret.
  HTTPS evidence must exactly match `sources` in the installed app manifest.
  This is typed provenance, not permission for arbitrary credential values or
  a general `/run/secrets` environment exception. It remains in plan claims and
  canonical approval hashes, but is not a Compose runtime field. Omission leaves
  existing normalized manifests and hashes unchanged. Owner issuance and upstream
  path syntax must be reviewed at the recipe boundary; this metadata is not
  remote-scope, license validity, TLS authorization, or application acceptance.
- `project.dockerContext` names the exact observed Docker context used later by preflight and lifecycle commands. `project.directory` must equal `project.root/project.id`. Both are absolute normalized paths; broad system roots are rejected. `verified-existing` requires an exactly matching `observed.project`; `new` requires no observed project.
- A service has only the shown keys, plus optional `ownership: "new" | "verified-existing"` for selected app addition. Images need an explicit non-floating tag or sha256 digest. The `dev` channel is accepted only with an exact sha256 digest; unpinned `dev` and other floating labels remain rejected. `user` must normally be a non-root numeric `uid:gid`. Environment names that imply credentials must move to `secretRefs`; interpolation and recognizable credential material are rejected. A `*_FILE`, `*_SECRETFILE`, or `FILE__*` variable must exactly name `/run/secrets/<target>` for a declared service secret. A documented file-URI consumer may instead receive `file:/run/secrets/<target>`; it must match a declared secret, and the recipe owns evidence for that upstream syntax. Neither form contains the secret payload.
- The static environment policy `^[A-Z][A-Z0-9_]*_LOG_CREDENTIALS$` accepts only the literal string `"false"`, disabling documented credential logging without carrying credentials. `true`, Boolean values, arbitrary payloads, lowercase variants, and other credential-bearing names are rejected. The catalog must retain pinned upstream evidence for the policy's actual meaning; this name/value validation alone is not proof that an app suppressed logs.
- Services may add `command` and `entrypoint` as non-empty argv arrays of at most 32 bounded strings. Shell strings, interpolation, and secret-bearing arguments are rejected. A command may reference an exact declared private configuration at `/run/secrets/<target>`, either positionally or through a non-sensitive `--option=`; only its path, never its contents, is recorded. `init: true` renders Compose's minimal init process only when the source recipe explicitly requires it. They may add `healthcheck` with exact fields `{test,intervalSeconds,timeoutSeconds,startPeriodSeconds,retries}`. `test` must be an argv array beginning with `CMD`; intervals are 1–3600 seconds, timeout 1–300 seconds, start period 0–3600 seconds, and retries 1–20. Optional `networkAliases` use the attached-network contract below.
- `shmSizeBytes` is an optional integer from 1 MiB through 1 GiB. Rendering writes the exact byte count as numeric Compose `shm_size`; omission preserves the image/runtime default.
- `profiles` accepts only `["self-host-manual"]`, and only with `restart: "no"` and no published ports. It marks an inert, prepared manual job: ordinary apply and selected add do not execute it; selected start/recreate refuse it. Automatic services cannot depend on manual jobs, preventing implicit startup. Preparation does not authorize a backup, upgrade, repository write, or other job operation. `hostname` is an optional single lowercase DNS label, at most 63 characters; it fixes container identity without host DNS changes. Both fields are visible in plan claims and bound into the canonical manifest and approval fingerprints. Source: [Compose profiles](https://docs.docker.com/compose/how-tos/profiles/).
- `manualProbe` is optional exact `{argv,officialUrl}` on a manual-profile job without named-volume mounts. The shared catalog registry permits only the exact publisher image/version/digest, fixed two-element version argv and matching HTTPS evidence for Restic, Borgmatic and Renovate. No arbitrary executable, shell, option, backup/init operation, remote scope, or repository write is accepted. Probe intent is visible in claims and bound into the full manifest approval; it is not a Compose runtime field and ordinary apply remains inert.
- `capDrop` accepts only `["ALL"]`, reducing container capabilities without permitting individual selection or capability expansion. `readOnly: true` restricts the image filesystem; explicit writable mounts and scratch tmpfs remain separate reviewed claims. No-new-privileges remains mandatory for every service. `memoryLimitBytes` is an optional integer from 64 MiB through 16 GiB, rendered as `mem_limit`. `cpuLimit` is an optional number from 0.1 through 16 in tenth increments, rendered as `cpus`. These settings are surfaced in plan claims and bound into the canonical manifest/approvals; omission preserves existing hashes and runtime defaults. Limits are not reservations or acceptance evidence. Sources: [Compose cap_drop](https://docs.docker.com/reference/compose-file/services/#cap_drop), [memory limits](https://docs.docker.com/reference/compose-file/services/#mem_limit), [CPU limits](https://docs.docker.com/reference/compose-file/services/#cpus).
- `ulimits` accepts only exact `{nofile:{soft,hard}}`, with integer limits from 1024 through 1048576 and `soft <= hard`. Both values are reviewed in service claims and bound into the canonical manifest and selected approvals. Rendering writes the exact Compose soft/hard mapping; omission preserves runtime defaults and existing manifest hashes. Unlimited values, other resource limits, host changes, and arbitrary options are unsupported. Host/runtime limits may still prevent startup; planning does not prove daemon acceptance. Source: [Compose ulimits](https://docs.docker.com/reference/compose-file/services/#ulimits).
- `tmpfs` is an optional array of at most eight exact `{target,sizeBytes,mode}` records for non-persistent container scratch paths. Targets must be normalized absolute container paths outside protected `/proc`, `/sys`, `/dev`, and `/run` namespaces, without whitespace, colons, or commas. Duplicate or nested tmpfs paths and overlaps with persistent mount targets or `/run/secrets` are rejected. `sizeBytes` is an integer from 1 MiB through 1 GiB; `mode` is an integer from 0 through 1023 (`01777`), allowing the sticky bit but excluding setuid and setgid. Entries sort by target and render only as Compose `tmpfs` sequence strings `<target>:size=<bytes>,mode=<octal>`. No host source, device, privilege, arbitrary mount option, UID, or GID is accepted. Omission leaves the canonical manifest hash and rendered document unchanged. An empty array renders no tmpfs mounts. Scratch data disappears when the container stops, may reach host swap, and counts against container memory; this is not persistence or a secret-storage guarantee. Sources: [Compose tmpfs](https://docs.docker.com/reference/compose-file/services/#tmpfs), [Docker tmpfs options and limitations](https://docs.docker.com/engine/storage/tmpfs/).
- `dependsOn` is an optional array of exact `{service,condition}` records. Conditions are `service_started`, `service_healthy`, or `service_completed_successfully`. Every named service must exist, the graph must be acyclic, and `service_healthy` requires the dependency to declare a healthcheck.
- Numeric non-root `user` remains the default policy. `user: "image-default"` is allowed only with `imageUserEvidence: {"officialUrl":"https://...","reason":"..."}`. The URL must be an HTTPS publisher source without credentials or a fragment; reason must be `upstream-init-requires-default-user`, `image-declares-nonroot-user`, or `official-image-runtime-contract`. This exception is surfaced in the plan for review. Rendering then omits `user`, leaving the image's declared user or default container root in effect. Container root does not grant host control without separately forbidden privileges or host resources.
- `user: "0:0"` is a separate rootless-only exception. It requires `project.dockerContext: "rootless"` and the exact evidence `rootlessUserEvidence: {"officialUrl":"https://docs.docker.com/engine/security/rootless/","reason":"host-user-mapped-container-root"}`. The plan surfaces both the container-root user and evidence, rendering keeps the explicit `0:0`, and lifecycle preflight requires that exact context to report Docker's rootless security option before Compose runs. The exception is invalid for every other context or without the fixed evidence. In rootless Docker, container UID/GID 0 maps to the invoking host user rather than host root; subordinate container IDs map into the configured subordinate ranges.
- Port IPs are literal IP addresses or `*`. Private/loopback binds need `publicApproved: false`. Public binds are allowed only for `purpose: application` with `publicApproved: true`; administration, database, management, and Docker API purposes and protected port numbers never become public here.
- Bind sources and container targets are absolute normalized paths. A read-write source must be owned by the project. Reuse requires `verified-existing` and an exact observed owner. Exact source sharing is allowed when every claimant is read-only with `shared: true` and the same optional `shareGroup`. If any claimant writes, every claimant must set `shared: true`, use the same explicit `shareGroup`, and retain identical project ownership; each mount keeps its own read-only mode. A `shareGroup` is invalid on an unshared mount. Other equal or nested overlaps conflict. Before lifecycle preflight, every bind source must already be a regular non-symlink file or directory so Docker cannot create it implicitly.
- A mount may instead use exact `{kind:"volume",name,target,readOnly,owner,ownership}`. Its name must be `<project.id>-<mount-id>`, and its owner and `project.owner` must equal `project.id`. Distinct services in that same project may mount one named volume only with identical target, read-only mode, owner, and ownership state; the volume is declared and preflighted once. A service cannot mount it twice. External or driver-option volumes are unsupported. A legacy bind mount may omit `kind` or set `kind:"bind"`; normalization keeps the old bind-only manifest hash unchanged. When any named volume is selected, `observed.volumes` is required (use `[]` for fresh absence). Each observed volume has exact `{name,driver,owner,labels}`; `labels` has `com.docker.compose.project`, `com.docker.compose.volume`, `io.selfhost.project`, and `io.selfhost.volume`, each a string or `null` if absent. A verified-existing volume requires the exact name, local driver, project owner, and all four ownership labels. An observed name claimed as new conflicts.
- Networks use the bridge driver. A new network must be project-owned and absent from observations. It may select an explicit `subnet` only as a canonical RFC1918 IPv4 network CIDR with a prefix from `/24` through `/28`; selected subnets must not overlap. A verified existing network must have an exact observed owner and cannot select a subnet because its IPAM is outside this project's creation boundary. Host networking is unsupported.
- A service may declare `networkAliases: [{"network":"app-private","alias":"db"}]` for an attached network. Alias names are bounded service labels and must identify only one service on that network, including implicit service names. App-private networks can therefore retain an upstream dependency hostname when multiple recipes are combined into one Compose project. Shared-front aliases need distinct app names. Aliases do not grant exposure or create a network.
- Each `secretRefs` entry contains the opaque `name`, provenance `ref`, and container `target`. Omitting `filePath` preserves an external, planning-only reference. Supplying `filePath` binds a local source and must use an absolute normalized path strictly below `<project.directory>/secrets/`. The manifest references that path only; it never contains or reads the payload.
- A service may declare `envFilePath` as an absolute normalized `.env` path strictly below `<project.directory>/secrets/`. This is for official images that accept a secret only as an ordinary environment variable. The manifest and rendered Compose contain the path, never the value. The CLI recipe compiler permits only bounded `{name,fileId}` bindings to generated private files; its apply preparation creates or verifies a current-user-owned mode-0600 env file without replacing an existing file. Environment values remain visible to the container runtime and to processes with container inspection privileges.
- Local lifecycle preflight supports only file-bound secrets. Every source must be a current-user-owned, mode-0600, non-empty regular file of at most 64 KiB with no symlink traversal and one hard link. External references remain valid for portable planning and rendering, but this local lifecycle rejects them with an actionable error because it does not provision an external secret platform.
- Observed records have exact shapes: project `{id,directory,owner}`, port `{hostIp,published,protocol,owner}`, path `{path,owner}`, and network `{name,owner}`.

Planner status is `pass`, `blocked`, or `conflict`. A non-pass plan exits with status 3 and remains read-only.
